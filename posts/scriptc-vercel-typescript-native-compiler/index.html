What Is Scriptc? — Vercel Labs’ Zero-Runtime TypeScript Compiler#

Scriptc is an experimental compiler from Vercel Labs that takes ordinary TypeScript code and produces native executables — with no Node.js, no V8, and no JavaScript engine required at runtime. Released on July 22, 2026, Scriptc represents a radical departure from how TypeScript has been deployed for the past decade. Instead of transpiling to JavaScript and running it inside a VM, Scriptc compiles TypeScript directly to machine code via C and LLVM backends. The result is a standalone binary that starts in roughly 2 milliseconds, occupies 170–200KB of disk space, and consumes 1–4MB of resident memory — a fraction of what Node.js requires. Install it with a single npm command (npm install -g scriptc), and your existing TypeScript projects compile without code changes.

The Three-Tier Compilation Model: Static, Dynamic, Rejected#

Scriptc’s most honest and innovative feature is its three-tier compilation model. Rather than claiming to compile everything perfectly, Scriptc categorizes every piece of TypeScript code into one of three tiers.

Tier 1: Compiled Statically (Default)#

The default compilation mode produces a fully static binary. No runtime engine is embedded. This works for the vast majority of TypeScript code — classes, closures, async/await, generics, discriminated unions, exception handling, and the full Node API surface including fs, path, process, child_process, os, crypto, http, net, tls, fetch, and zlib. In a coverage analysis of a sample application, Scriptc analyzed 4,481 statements and found that 4,451 (99%) compiled statically. This means nearly all real-world TypeScript can run without any dynamic fallback.

Tier 2: Runs Dynamically (–dynamic)#

For code that requires dynamic evaluation — eval(), new Function(), dynamic import(), or npm dependencies that rely on runtime metaprogramming — Scriptc offers the --dynamic flag. This embeds a stripped-down QuickJS engine (~620KB) into the binary. The dynamic island handles the small fraction of code that cannot be statically analyzed, while the rest of the program runs as native code. Dependencies are bundled into the binary at build time, so the resulting executable is still self-contained — typically around 3MB with embedded packages.

Tier 3: Rejected at Compile Time#

Some patterns are genuinely incompatible with ahead-of-time compilation. Scriptc rejects these at compile time with clear error messages rather than silently producing incorrect output. This includes certain reflection-heavy patterns and code that depends on V8-specific behavior. The rejection is a feature, not a bug — it guarantees that what compiles, compiles correctly.

Performance Benchmarks: Startup Time, Binary Size, Memory#

The performance numbers are where Scriptc makes its strongest case. On M-series Macs, Scriptc’s static binaries start in approximately 2 milliseconds. Compare that to Node.js, which takes roughly 47 milliseconds to boot — a 23x difference. For serverless and edge functions that are frequently cold-started, this is transformative.

The binary size comparison is equally striking. A Node.js Single Executable Application (SEA) weighs 60–100MB because it bundles the entire V8 runtime. Scriptc’s static binary is 170–200KB — roughly 400x smaller. Even with the embedded QuickJS engine and npm dependencies, a dynamic Scriptc binary is around 3MB, still 20–30x smaller than a Node SEA.

Memory consumption follows the same pattern. Node.js processes typically use 67–116MB of resident memory. Scriptc static binaries use 1–4MB. For deployments at scale — thousands of microservices or edge functions — this memory efficiency translates directly into cost savings.

Language and API Surface Coverage#

Scriptc aims for full TypeScript language compatibility, and the coverage is impressive for a project that is only days old. The compiler handles:

  • Classes and inheritance — including extends, implements, and abstract classes
  • Closures and lexical scoping — first-class functions, arrow functions, and captured variables
  • Async/await and Promises — full event loop integration
  • Generics — type parameters, constraints, and conditional types
  • Discriminated unions and pattern matching — type narrowing with switch/if
  • Exception handling — try/catch/finally with stack traces
  • Standard library — Array, Map, Set, Promise, WeakRef, FinalizationRegistry

On the Node API side, Scriptc implements a substantial subset of the Node.js standard library: fs (sync and async), path, process, child_process, os, crypto, http, net, tls, fetch, and zlib. The --dynamic flag extends this to any npm package that doesn’t rely on native Node addons.

The compiler uses the real TypeScript compiler for type-checking, so your existing tsconfig.json and type definitions work as expected. Scriptc is not a new type system — it is a new backend for the same TypeScript you already write.

Correctness Strategy: Differential Testing and Memory Safety#

One of the most ambitious aspects of Scriptc is its approach to correctness. The project maintains a corpus of over 800 differential tests. Every program in the corpus runs under Node.js and as a native Scriptc binary. The stdout, stderr, and exit codes must match byte-for-byte. This is not a “mostly works” guarantee — it is a rigorous, automated verification that Scriptc’s output behaves identically to Node.js.

The testing infrastructure covers:

  • Differential test corpus — 800+ programs covering language features and API calls
  • Diagnostic tests — verifying error messages and edge cases
  • Snapshot tests — ensuring output stability across compiler changes
  • CI/CD pipeline — automated on every commit

Memory safety is enforced through AddressSanitizer (ASan) and a reference count audit on every change. Because Scriptc generates C code that is then compiled with Clang, it inherits Clang’s memory safety tooling. The reference counting system for the runtime is audited to prevent use-after-free and memory leaks.

How to Get Started with Scriptc#

Getting started with Scriptc is straightforward, especially if you already have a TypeScript project:

# Install Scriptc globally
npm install -g scriptc

# Compile a TypeScript file to a native binary
scriptc build src/index.ts -o my-app

# Run it
./my-app

# Check what compiles statically vs dynamically
scriptc coverage src/index.ts

# Compile with dynamic support for npm dependencies
scriptc build src/index.ts --dynamic -o my-app-dynamic

Prerequisites: Scriptc requires Clang to be installed. The primary development target is macOS arm64 (Apple Silicon), with cross-compilation support for Linux and Windows. The scriptc coverage command is particularly useful — it analyzes your codebase and reports exactly which statements compile statically, which need the dynamic engine, and which are rejected.

The Competitive Landscape: Porffor, PerryTS, and the Native TypeScript Movement#

Scriptc is not the first attempt to compile TypeScript to native code, but it may be the most practical. The emerging “native TypeScript” ecosystem includes several projects:

Scriptc’s main differentiator is its three-tier model and the depth of its Node API coverage. While Porffor targets WebAssembly (which has its own runtime overhead), Scriptc produces true native binaries. And while ts2c requires manual memory management and supports a limited subset of TypeScript, Scriptc handles the full language automatically.

Vercel’s involvement is also significant. As the company behind Next.js, Edge Functions, and a major cloud platform, Vercel has a direct incentive to make TypeScript deployment faster and cheaper. Scriptc could eventually power Vercel’s edge runtime, replacing the current V8-based isolation with native binaries.

Use Cases: Edge Computing, AI Agents, CLI Tools, and Microservices#

Edge Computing and Serverless Functions#

The most obvious use case for Scriptc is edge computing. Cold starts are the bane of serverless architectures. A 2ms startup time means that every invocation is effectively warm. For platforms like Vercel Edge Functions, Cloudflare Workers, or AWS Lambda@Edge, Scriptc could reduce p99 latency by an order of magnitude.

AI Agent Code#

AI agents are increasingly written in TypeScript. Scriptc could compile agent code into tiny, fast binaries suitable for deployment on resource-constrained edge devices or in high-density server environments. The 1–4MB memory footprint means hundreds of agent instances can run on a single machine.

CLI Tools#

Command-line tools written in TypeScript currently require Node.js to be installed. With Scriptc, you distribute a single binary. No runtime dependency, no npx, no version conflicts. The 170KB binary size is comparable to Rust or Go CLI tools.

Microservices#

For lightweight microservices that don’t need the full Node.js ecosystem, Scriptc offers dramatic resource savings. A fleet of 100 microservices running on Node.js would consume 6.7–11.6GB of RAM. The same fleet with Scriptc would use 100–400MB — a 95% reduction.

Limitations and Current Gaps#

Scriptc is an experimental project, and it has real limitations:

  • macOS arm64 only — The primary target is Apple Silicon. Cross-compilation to Linux and Windows is available but less tested.
  • No native addons — npm packages that use native Node.js addons (C++ bindings) cannot be compiled statically. The --dynamic flag handles some cases, but performance may suffer.
  • Young project — As of July 27, 2026, Scriptc is only 5 days old. The codebase has 750 GitHub stars and 10 forks. It has not been battle-tested in production.
  • Limited ecosystem — No IDE plugins, no debugging support, no profiling tools specific to Scriptc binaries.
  • “Claudisms” controversy — Hacker News commenters noted that the README appears to be AI-generated, raising questions about documentation accuracy and long-term maintenance.
  • No Windows native support — Windows builds require cross-compilation from macOS.
  • Dynamic tier performance — Code running in the QuickJS dynamic island is significantly slower than native code. If your application has a hot path that falls into the dynamic tier, the performance advantage diminishes.

Verdict — Is Scriptc Ready for Production?#

Scriptc is not ready for production today, but it is one of the most promising TypeScript projects in years. The three-tier compilation model is a thoughtful solution to a hard problem. The performance numbers — 2ms startup, 170KB binaries, 1–4MB RSS — are genuinely impressive. The differential testing strategy gives confidence that what compiles, compiles correctly.

For early adopters, Scriptc is worth experimenting with today. CLI tools, single-purpose edge functions, and AI agent code are good candidates. For production workloads, wait for Linux native support, broader npm ecosystem compatibility, and a longer track record of stability.

Vercel’s involvement suggests that Scriptc has institutional backing and a clear path to maturity. If the project continues at its current pace, it could fundamentally change how TypeScript is deployed — not as JavaScript with types, but as a genuine systems programming language.

Frequently Asked Questions#

What is Scriptc and how does it differ from regular TypeScript compilation?#

Scriptc is a compiler from Vercel Labs that converts TypeScript directly into native machine code without requiring Node.js or a JavaScript engine at runtime. Unlike traditional TypeScript compilation (which transpiles to JavaScript and runs in V8), Scriptc produces standalone executables that start in ~2ms and use 1–4MB of memory.

Does Scriptc support all TypeScript features?#

Scriptc supports the full TypeScript language including classes, closures, async/await, generics, discriminated unions, and exception handling. It also implements a substantial subset of the Node.js API (fs, path, http, crypto, fetch, and more). A coverage analysis showed 99% of statements in a sample app compiled statically.

How does the –dynamic flag work?#

The --dynamic flag embeds a stripped-down QuickJS engine (~620KB) into the binary to handle code that requires runtime evaluation, such as eval(), new Function(), dynamic import(), or npm dependencies with metaprogramming. The rest of the program still runs as native code, and dependencies are bundled at build time.

How does Scriptc compare to Node.js in terms of performance?#

Scriptc’s static binaries start in ~2ms versus Node.js’s ~47ms (23x faster). Binary sizes are 170–200KB versus 60–100MB for Node SEA (400x smaller). Memory usage is 1–4MB versus 67–116MB for Node.js (20–30x less). Go binaries are comparable in size (~2MB) and startup (~1ms) but require writing in Go instead of TypeScript.

Is Scriptc free and open source?#

Yes, Scriptc is available as an open-source project under the Vercel Labs organization on GitHub. It can be installed via npm (npm install -g scriptc) and requires Clang for compilation. The primary development target is macOS arm64, with cross-compilation support for Linux and Windows.
