What Is Kontext CLI and Why Does It Matter for AI Coding Agents?#

Kontext CLI is a Go-based credential broker that intercepts AI coding agent tool calls and injects credentials at runtime without ever exposing secrets to the agent itself. It solves a critical security gap: as developers increasingly trust AI agents like Claude Code and Cursor to read, write, and execute code, those agents need access to APIs, databases, and cloud services — but handing them raw credentials creates unacceptable risk. Kontext bridges that gap with a daemon-based architecture that enforces policy, detects anomalous access patterns, and maintains a full audit trail.

What Is Kontext CLI? — Overview and Core Mission#

Kontext CLI, created by Kontext Security (founded by Jens Ernstberger and announced March 14, 2026), is an open-source credential broker purpose-built for AI coding agents. Written in Go 1.25 and licensed under MIT, it reached v0.15.1 by July 21, 2026 — a release cadence that signals aggressive development. The project has accumulated 210 GitHub stars, 7 forks, and 26 open issues as of July 2026.

The core mission is straightforward: AI agents should never hold credentials. Instead, when an agent needs to call an authenticated API, Kontext intercepts the request, evaluates it against policy, retrieves the credential from the macOS Keychain (or other secure stores), injects it at the network level, and logs every detail. The agent completes its task without ever seeing the secret.

This approach is fundamentally different from giving an agent an API key in a .env file or environment variable. With Kontext, the credential is ephemeral, scoped, and audited — three properties that traditional secret management tools do not provide for AI agent workflows.

Architecture Deep Dive — Daemon, Hooks, Policy Engine, and Local Judge#

Kontext’s architecture has four layers that work together to provide runtime credential security.

The Daemon#

Kontext runs as a background daemon on the developer’s machine. It listens for credential requests from AI agents, manages the secure keychain storage, and coordinates policy evaluation. The daemon is installed via Homebrew on macOS (the primary supported platform) and runs persistently, meaning credential brokering happens with zero latency overhead once the daemon is warm.

Agent Hooks (PreToolUse / PostToolUse)#

Rather than operating as a proxy that all traffic passes through, Kontext hooks directly into the AI agent’s tool execution lifecycle. It implements PreToolUse and PostToolUse hooks that intercept API calls before they reach the network. This hook-based architecture is more precise than proxy-based approaches because it operates at the semantic level — Kontext knows what tool the agent is calling, what parameters it intends to send, and what credential it needs.

The Policy Engine#

Kontext features a dual-layer policy engine:

  1. Deterministic Policy (Allow/Deny Rules): Administrators define explicit rules about which agents can access which credentials under which conditions. These are static, predictable rules — “Claude Code may read GitHub API tokens but not AWS production keys” — that provide a hard security boundary.

  2. Probabilistic Risk Detection (Local Judge): This is Kontext’s standout innovation. A local LLM judge (running via llama.cpp on the developer’s machine) evaluates each credential request for anomalous patterns. If an agent that normally requests GitHub tokens suddenly asks for an AWS production key, the local judge flags it. This probabilistic layer catches zero-day threats and policy gaps that deterministic rules cannot address.

RFC 8693 OAuth 2.0 Token Exchange#

Kontext uses RFC 8693-compliant OAuth 2.0 Token Exchange for credential injection. This is a standards-based approach rather than a proprietary protocol, which means it integrates with existing identity infrastructure. The token exchange protocol allows Kontext to request a token on behalf of the agent, receive a scoped, time-limited credential, and inject it into the agent’s request — all without the agent ever handling the raw secret.

Key Features — Credential Injection, Audit Trails, and Dual-Layer Policy#

Credential Injection at Runtime#

The core feature is transparent credential injection. When an AI agent makes an API call that requires authentication, Kontext intercepts the call, retrieves the appropriate credential from the macOS Keychain, and injects it into the request headers. The agent never sees the credential — it only sees the successful API response.

Full Audit Trails#

Every credential access is logged with agent identity, tool used, credential accessed, timestamp, and policy decision. This creates a complete audit trail that satisfies compliance requirements (SOC 2, ISO 27001) and enables post-incident forensics. For organizations that need to demonstrate control over AI agent access to sensitive systems, this audit capability is essential.

Deterministic + Probabilistic Policy#

As described in the architecture section, the combination of deterministic allow/deny rules and probabilistic risk detection is unique in the credential broker space. Most competitors offer one or the other — Kontext offers both. The local judge runs entirely on the developer’s machine, so no data leaves the local environment for risk evaluation, preserving privacy.

No Reasoning Capture#

Kontext explicitly does not capture the agent’s reasoning or conversation content. It only observes tool calls and credential requests. This is an important privacy feature: the credential broker sees what credentials are requested and whether the request is authorized, but it does not see the code the agent is writing or the conversation context.

OneCLI (2,535 stars)#

OneCLI is the dominant player in the space by community size. It is a TypeScript-based credential gateway with a built-in vault that supports MCP, Node.js, Rust, and Postgres backends. OneCLI’s broader scope — vault plus gateway — makes it a more comprehensive solution, but it lacks Kontext’s probabilistic risk detection and RFC 8693 compliance. OneCLI’s Apache-2.0 license and 145 forks indicate a very active community.

Postern (9 stars)#

Postern is a Go-based credential-brokering HTTPS proxy for AI agents. It brokers 1Password and Bitwarden secrets at request time, meaning agents call authenticated APIs without ever holding credentials. Postern’s proxy-based approach is architecturally simpler than Kontext’s daemon + hook architecture, but it is also less precise — a proxy sees all traffic, not just tool calls. Postern’s smaller scope focuses primarily on password manager integration.

Sesame OSS (5 stars)#

Sesame OSS is a minimal, source-available, self-hosted edition of the Sesame credential broker. It includes a broker, dashboard, and CLI, all Python-based. The source-available license (not fully open source like Kontext’s MIT license) may be a consideration for organizations that require permissive licensing. Sesame’s self-hosted focus appeals to enterprises that want full control over their infrastructure.

Tailscale Aperture#

Tailscale Aperture is a unified AI governance platform for AI agents and users, offering self-serve centralized AI access, usage, and spend management. It is part of Tailscale’s broader zero-trust networking platform. Aperture is enterprise-focused and less suited for individual developers or small teams who want a lightweight, CLI-first tool. It also lacks the local-first, privacy-preserving architecture that Kontext offers.

Vouchr (4 stars)#

Vouchr is a self-hostable, Slack-native credential broker for AI agents. Its TypeScript codebase and Slack integration as the primary interface make it a niche tool for teams that live in Slack. Vouchr’s Slack-native approach is fundamentally different from Kontext’s CLI-first, agent-hook architecture.

Security Model Analysis — Local-First, Keychain Storage, Redaction, No Reasoning Capture#

Kontext’s security model has several important properties:

Local-First Architecture#

The daemon, policy engine, and local judge all run on the developer’s machine. Credentials are stored in the macOS Keychain, not in a cloud vault. This means that even if Kontext Security’s cloud service were compromised, an attacker would not gain access to your credentials. The local-first design is a significant security advantage over cloud-based credential brokers.

Credential Redaction#

When Kontext injects a credential into an agent’s request, it redacts the credential from the agent’s logs and output. The agent sees the API response but not the credential that made it possible. This prevents accidental credential leakage through agent conversation logs, which are often shared or stored in chat histories.

No Reasoning Capture#

Kontext does not capture or transmit the agent’s reasoning, conversation, or code. It only observes tool call metadata — which tool, which parameters (excluding credential values), and the policy decision. This is a deliberate design choice that preserves developer privacy and avoids creating a new vector for intellectual property leakage.

Keychain Storage#

Credentials are stored in the macOS Keychain, which provides hardware-backed encryption on Apple Silicon Macs. This is the same secure storage used by macOS for Wi-Fi passwords, application secrets, and certificates. Kontext does not maintain its own credential store — it leverages the platform’s built-in secure storage.

Community and Development Velocity — GitHub Activity, Release Cadence, Contributors#

Kontext CLI was created in April 2026 and has already reached v0.15.1 by July 21, 2026 — approximately 15 releases in under 4 months. This release cadence indicates a highly active development team that is shipping features and fixes rapidly.

The project has 210 GitHub stars and 7 forks. While this is modest compared to OneCLI’s 2,535 stars, it is respectable for a project that is only a few months old. The Show HN post received 70 points and 11 comments on Hacker News, indicating genuine community interest.

The small number of forks (7) relative to stars (210) suggests that the project is still in its early adoption phase — many developers are watching but few are contributing code. This is typical for security tools, where the barrier to contribution is higher than for general-purpose developer tools.

Strengths and Limitations — macOS Focus, Go Performance, MCP Integration#

Strengths#

Go Performance: Kontext is written in Go, which gives it a performance advantage over TypeScript-based competitors like OneCLI. Go’s compiled binary starts instantly, uses minimal memory, and has predictable garbage collection — important for a daemon that runs continuously on a developer’s machine.

Dual-Layer Policy Engine: The combination of deterministic rules and probabilistic risk detection is genuinely innovative. No other credential broker in the space offers a local LLM judge for anomaly detection. This is Kontext’s strongest differentiator.

Standards Compliance: RFC 8693 OAuth 2.0 Token Exchange is a well-established standard. Using a standard rather than a proprietary protocol means Kontext can integrate with existing identity infrastructure and is easier to audit.

MIT License: The permissive MIT license means no restrictions on commercial use, modification, or redistribution. This is important for enterprises that need legal clarity.

Limitations#

macOS-Only: As of July 2026, Kontext is macOS-only with Homebrew installation. Linux and Windows support are not yet available. This is a significant limitation for developers who work on Linux (a large portion of the AI/ML developer community) or Windows.

Early Stage: At v0.15.1, Kontext is still pre-1.0. The API and architecture may change. The small community (7 forks) means fewer community-contributed integrations and less community support.

Limited Agent Support: Only Claude Code and Claude Cowork are supported. Goose, Codex, and Cursor are planned but not yet available. Teams using other agents will need to wait.

No Built-in Vault: Unlike OneCLI, which includes a built-in vault, Kontext relies on the macOS Keychain. This works well on macOS but limits portability and means Kontext cannot manage credentials that are not in the Keychain.

Verdict — Who Should Use Kontext CLI and When#

Kontext CLI is the right choice for:

  • Claude Code users who need runtime credential security without exposing secrets to the agent
  • Security-conscious developers who want a local-first, privacy-preserving credential broker
  • Teams that need audit trails for AI agent credential access (compliance requirements)
  • Developers on macOS who want a lightweight, Go-based daemon with minimal overhead
  • Early adopters who want the most innovative credential broker with probabilistic risk detection

Kontext CLI may not be the right choice for:

  • Linux or Windows developers — macOS-only support is a hard blocker
  • Teams using Goose, Codex, or Cursor — these agents are not yet supported
  • Organizations that need a built-in vault — OneCLI’s vault + gateway model may be more appropriate
  • Enterprises that need a platform-level solution — Tailscale Aperture offers broader governance

The credential broker space for AI coding agents is still young, and Kontext’s dual-layer policy engine and local-first architecture give it a strong competitive position. As the project matures, adds Linux support, and expands agent integrations, it has the potential to become a standard tool in the AI developer’s security stack.

Frequently Asked Questions#

How does Kontext CLI differ from giving an AI agent an API key in a .env file?#

Kontext injects credentials at runtime without the agent ever seeing the secret. With a .env file, the agent reads the credential directly, which means it can leak it through logs, share it in conversation, or misuse it. Kontext also enforces policy, detects anomalous access patterns, and maintains a full audit trail — none of which are possible with environment variables.

Does Kontext CLI work with any AI coding agent?#

Currently, Kontext supports Claude Code and Claude Cowork. Support for Goose, Codex, and Cursor is planned but not yet available. The hook-based architecture means new agent integrations follow a defined pattern, but each requires implementing the PreToolUse/PostToolUse interface for that agent’s SDK.

Is Kontext CLI free to use?#

Yes, the Kontext CLI is open source under the MIT license and completely free to use. The Starter tier includes the full CLI, local daemon, basic policy engine, and local audit logs. Paid tiers ($149/mo Pro, $499/mo Scale) add the cloud dashboard for team policy management, advanced audit, SSO, and dedicated support.

How does Kontext’s local judge work and does it send data to the cloud?#

The local judge runs entirely on the developer’s machine via llama.cpp. It evaluates credential requests against learned patterns of normal behavior and flags anomalies. No data leaves the local environment for risk evaluation. The local judge is a privacy-preserving approach to anomaly detection that avoids sending sensitive tool call metadata to a cloud service.

What happens if the Kontext daemon crashes while an agent is running?#

If the daemon crashes, the agent’s credential requests will fail because there is no broker to intercept and inject credentials. The agent will receive an authentication error for any API call that requires a brokered credential. This fail-closed behavior is the secure default — agents cannot access credentials without the daemon’s authorization. Restarting the daemon restores normal operation.
