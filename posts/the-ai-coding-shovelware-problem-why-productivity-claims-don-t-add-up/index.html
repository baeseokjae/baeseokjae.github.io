The AI Coding Shovelware Problem: Why Productivity Claims Don't Add Up

Controlled studies show AI coding tools make developers 19% slower despite feeling 30% faster. Here's why the productivity data doesn't match the hype.

If AI coding assistants truly made developers 10x more productive, we would expect a flood of new software — shovelware — hitting app stores, GitHub, and Steam. Yet public data from Statista, Verisign, SteamDB, and the GitHub Archive shows no measurable increase in software releases or pull request volume since the launch of ChatGPT, Copilot, and Claude Code. Controlled studies tell an even more troubling story: developers using AI coding tools actually completed tasks 19% slower on average, despite feeling 20-30% faster. This is the AI coding shovelware problem — a perception gap so wide it is reshaping engineering management, developer careers, and the future of software quality.

The Shovelware Test — If AI Coding Works, Where’s the Flood?#

The simplest test of AI coding productivity claims is also the most damning. If thousands of developers are suddenly 2x, 5x, or 10x more productive, the market should be drowning in new software. This is the “shovelware test” — named after the flood of low-quality shareware that followed the democratization of desktop publishing in the 1990s.

But the data shows nothing of the sort. Allard de Winter analyzed public data from Statista, Verisign, and SteamDB and found no significant increase in new software releases after 2022 or 2023 — the years when AI coding tools went mainstream. Steam, the largest PC gaming platform, shows a flat trajectory of new game releases. Domain registrations, a proxy for new web applications, show no AI-driven spike. App store submission volumes remain steady.

Mike Judge, a developer who ran a 6-week self-experiment on AI coding productivity, examined the GitHub Archive — a public record of every public GitHub event — and found no visible bump in pull request volume. If AI tools were genuinely multiplying output, the PR graph would show it. It does not.

This absence of shovelware is the first and most powerful piece of evidence that AI coding productivity claims are dramatically overstated. The market is the ultimate arbiter, and the market is not producing more software.

The METR Study That Changed Everything — 19% Slower, Not Faster#

The most rigorous evidence comes from a randomized controlled trial conducted by METR (Model Evaluation and Threat Research), cited extensively across the research community. In this study, developers were randomly assigned to complete coding tasks with and without AI assistance. The results were stark:

MetricWithout AIWith AIDifference
Task completion timeBaseline+19% longer19% slower
Developer self-assessment—Felt 20-30% faster50-point perception gap
Code correctnessBaselineComparableNo significant improvement
Task completion rateBaselineSimilarNo significant improvement

Developers using AI tools took 19% longer to complete the same tasks. Yet when asked how they felt, the same developers reported feeling 20-30% more productive. This 50-point gap between perceived and actual productivity is the central finding of the AI coding productivity debate.

Mike Judge replicated this finding in his own 6-week controlled experiment. He measured his own task completion times with and without AI assistance across a variety of real-world programming tasks. His result: AI appeared to slow him by a median of 21% — almost exactly matching the METR findings.

The consistency between a formal randomized trial and a self-conducted experiment is striking. Two different methodologies, two different populations, same conclusion: AI coding tools are making developers slower, not faster.

Why AI Coding Feels Productive (The Perception Gap)#

If AI tools make developers slower, why do they feel so productive? The answer lies in the psychology of instant gratification. When a developer types a prompt and sees 50 lines of code appear in seconds, the brain releases a dopamine hit of accomplishment. The code compiles. It looks right. It feels like progress.

But the feeling is deceptive. The real work begins after the code is generated: reading it, understanding it, debugging it, integrating it with existing systems, handling edge cases, writing tests, and ensuring security. AI-generated code is often superficially correct but subtly wrong — it compiles but fails on edge cases, it looks reasonable but introduces security vulnerabilities, it works in isolation but breaks when integrated.

This is the “vibe coding” trap. Developers feel productive because they are generating code faster, but they are spending the saved time — and more — on verification, debugging, and refactoring. The generation phase is faster, but the total cycle time is longer.

Algustionesa Yoshi describes this dynamic clearly: AI is like an “amnesiac junior engineer” who needs extensive context engineering to produce anything useful. Every prompt requires careful framing, every output requires thorough review, and the AI forgets everything between conversations. The developer becomes a context engineer and code reviewer rather than a writer — roles that are equally demanding but feel less productive because they produce less visible output.

The Data Doesn’t Lie — GitHub PRs, App Store Releases, SteamDB#

Beyond the METR study, multiple independent data sources converge on the same conclusion:

GitHub Archive (GH Archive): Mike Judge’s analysis of public GitHub event data shows no increase in pull request volume since AI coding tools became widely available. If Copilot and Claude Code were making developers 2-10x more productive, the number of PRs per developer should have risen measurably. It has not.

Statista and Verisign: Allard de Winter’s analysis of new software releases and domain registrations shows flat growth. The post-2022 period, which should have seen an AI-driven explosion of new software, looks statistically indistinguishable from the pre-AI trend.

SteamDB: New game releases on Steam have not accelerated. Game development, which involves significant coding, should have benefited from AI productivity gains if the claims were true.

GitHub’s own 2024 study claimed a 26% increase in PRs merged among Copilot users. However, this study has been widely criticized for conflating quantity with productivity. More PRs could mean more small, fragmented changes — not more output. A developer who submits 10 tiny PRs instead of 2 well-tested ones is not 5x more productive; they are creating more review overhead.

Executive FOMO and the “AI-First” Rebranding Trap#

The perception gap at the individual developer level is dangerous enough. But when it scales to executive decision-making, it becomes destructive. Hacker News discussions and industry reports document a pattern of managers cutting project delivery estimates to 20% of original timelines after declaring an “AI-first” approach.

This is executive FOMO (fear of missing out) driving real business decisions without evidence. Companies are laying off engineers, slashing timelines, and rebranding as “AI-first” — all based on subjective productivity claims that controlled studies contradict.

The consequences are predictable: missed deadlines, burned-out teams, and software quality crises. When a manager tells a team to deliver in 20% of the original timeline because “AI makes you 5x faster,” the team either cuts corners or fails. Either way, the business loses.

The irony is that the same executives who demand data-driven decisions in every other domain are abandoning evidence when it comes to AI coding productivity. The METR study exists. The shovelware test exists. The data is public. The decision to ignore it is a choice.

The Prototype-to-Production Gap#

AI coding tools excel at one thing above all others: prototypes. A developer can describe a feature in natural language and get a working demo in minutes. This is genuinely impressive and genuinely useful.

But a prototype is not production software. The gap between a working demo and a production-ready system is where the vast majority of software engineering effort lives:

  • Edge cases: AI generates the happy path. The 80% of code that handles errors, timeouts, race conditions, and invalid inputs is left to the developer.
  • Testing: AI-generated tests tend to be tautological — they test what the code does, not what it should do. Meaningful test coverage requires human understanding of requirements.
  • Security: Studies show AI-generated code introduces security vulnerabilities at rates comparable to or worse than human-written code. The OWASP Top 10 vulnerabilities appear regularly in AI output.
  • Integration: AI generates code in isolation. Real systems have 14+ year legacy codebases, undocumented dependencies, and implicit assumptions that no AI prompt can capture.
  • Maintenance: Code is read far more often than it is written. AI-generated code that is hard to read, poorly structured, or inconsistently styled creates long-term maintenance debt.

Enterprise codebases with long histories see minimal AI benefit. A 14-year-old Java monolith with 3 million lines of code, custom frameworks, and institutional knowledge embedded in comments and commit messages — AI cannot meaningfully contribute to this environment. The prototype-to-production gap is where AI productivity gains go to die.

When AI Coding Actually Works (And For Whom)#

Despite the sobering data, AI coding tools are not useless. They have genuine, narrow use cases where they deliver real value:

Boilerplate and scaffolding: Generating CRUD endpoints, API clients, configuration files, and repetitive data transformations is where AI shines. These tasks are formulaic, well-documented, and low-risk.

Unfamiliar languages and frameworks: When a developer needs to write code in a language they don’t know well, AI can accelerate the learning curve by generating idiomatic examples. The developer still needs to verify correctness, but the starting point is better than a blank page.

DSL and configuration code: YAML, JSON schemas, Terraform configurations, and other declarative formats are well-suited to AI generation because they follow strict patterns and have clear correctness criteria.

The privileged builder: Hugo Nogueira, who shipped 146,000 lines of production TypeScript in 4 months using Claude Code, acknowledges his own privilege: 10+ years of experience, strong product vision, existing domain knowledge, and the ability to evaluate AI output critically. AI coding tools amplify the productivity of already-excellent developers. They do not turn mediocre developers into excellent ones.

This distinction is crucial. AI tools are a force multiplier for developers who already know what good code looks like. For junior developers, they can be a crutch that prevents the development of fundamental skills.

Context Engineering — The Real Skill Developers Need#

The most valuable skill in the AI coding era is not prompting — it is context engineering. Treating AI as an “amnesiac junior engineer” who needs extensive documentation, clear specifications, and constant course correction is the mental model that produces the best results.

Context engineering means:

  • Writing detailed specifications before generating code
  • Providing examples of the desired output format
  • Breaking complex tasks into small, verifiable steps
  • Maintaining a “context document” that the AI can reference across conversations
  • Reviewing every line of generated code with the same rigor as a human-written PR

This is not easier than writing code yourself. In many cases, it is harder. But it produces better results than the naive “prompt and pray” approach that dominates current AI coding practice.

The developers who will thrive in the AI era are not the best prompt engineers. They are the best system designers, the best code reviewers, and the best context engineers — skills that take years to develop and cannot be shortcut by a chat interface.

The Junior Developer Crisis — Losing Fundamentals to Vibe Coding#

Perhaps the most concerning long-term consequence of the AI coding productivity myth is its impact on junior developers. When new programmers learn to code by accepting AI-generated suggestions without understanding them, they never develop the fundamental skills that make a good engineer:

  • Debugging: AI generates code that compiles. Junior developers never learn to trace through a program’s execution to find bugs.
  • Algorithmic thinking: AI handles the logic. Junior developers never learn to design algorithms from first principles.
  • Code reading: AI generates the output. Junior developers never learn to read and understand existing code — the skill that accounts for the majority of professional development time.
  • System design: AI generates components. Junior developers never learn how components fit together into a coherent system.

The concern, raised by multiple researchers and practitioners in the AI coding debate, is that we are training a generation of developers who can prompt but cannot program. When the AI fails — and it will fail — these developers will lack the foundational skills to diagnose and fix the problem.

This is not a hypothetical concern. It is already visible in online forums where junior developers ask questions that reveal a fundamental misunderstanding of programming concepts, despite having “shipped” AI-generated code.

How to Measure Your Own AI Productivity Honestly#

Given the gap between perception and reality, how should individual developers measure their own AI productivity? The research suggests a simple protocol:

  1. Time-box identical tasks: Pick a task you have done before. Do it once with AI and once without. Measure total time from start to working, production-quality code — not time to first compile.

  2. Track defect rate: Count bugs found in code review and in production for AI-assisted vs. manual code. A 19% time savings is worthless if defect rate doubles.

  3. Measure maintenance cost: Six months later, which code is easier to modify? AI-generated code that is poorly structured creates long-term drag.

  4. Use objective tools: Time tracking software, PR review metrics, and bug tracking data are more reliable than subjective feelings of productivity.

  5. Beware the novelty effect: The first month with a new AI tool feels productive because everything is new. Measure over 3-6 months to get reliable data.

The honest answer for most developers will be: AI helps with specific tasks (boilerplate, unfamiliar syntax, exploration) but does not make you 2x or 10x more productive overall. And that is okay. A 10-20% productivity gain in specific domains is still valuable — it just is not the revolution the marketing claims.

Conclusion — Trust the Data, Not the Hype#

The AI coding shovelware problem reveals a fundamental truth about technology adoption: the hype cycle always precedes the evidence. AI coding tools are useful. They are not revolutionary. The data is clear:

  • Controlled studies show AI makes developers 19% slower, not faster
  • Public data shows no increase in software output since AI tools launched
  • The perception gap between felt and actual productivity is 50 percentage points
  • AI benefits experienced developers with strong fundamentals, not juniors
  • The prototype-to-production gap remains the dominant cost of software development

None of this means AI coding tools are worthless. It means we need to use them with clear eyes, measure their impact honestly, and resist the pressure to make business decisions based on marketing claims rather than data.

The shovelware test is the simplest and most powerful argument in this debate. If AI coding were truly 10x, we would see it everywhere. We do not. The data does not lie — and neither should our assessment of what AI can and cannot do for software development.

Frequently Asked Questions#

Does AI coding really make developers slower? Yes. A randomized controlled trial by METR found that developers using AI coding assistants took 19% longer to complete tasks, despite feeling 20-30% faster. This finding was replicated in independent self-experiments.

Why do developers feel more productive if they are actually slower? The instant code generation creates a dopamine-driven perception of progress. However, the time saved during generation is more than offset by increased time spent on verification, debugging, integration, and refactoring of AI-generated code.

Where is the shovelware if AI coding is so productive? Public data from Statista, Verisign, SteamDB, and the GitHub Archive shows no measurable increase in new software releases or pull request volume since AI coding tools became widely available in 2022-2023.

Is AI coding completely useless? No. AI coding tools excel at boilerplate generation, scaffolding, unfamiliar language exploration, and DSL/configuration code. They are a genuine productivity aid for experienced developers who can critically evaluate AI output.

How can I measure whether AI is actually making me more productive? Time-box identical tasks with and without AI, track defect rates in code review, measure maintenance cost after six months, and use objective tools like time tracking and PR metrics rather than subjective feelings of productivity.
