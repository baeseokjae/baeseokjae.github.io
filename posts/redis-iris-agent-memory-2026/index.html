What is Redis Iris? Context Retriever + Agent Memory Explained#

Redis Iris is a managed context layer for AI agents that combines two core services: Context Retriever and Agent Memory. Context Retriever auto-generates MCP (Model Context Protocol) tools from your entity model — turning database schemas into callable tools without writing a single line of data-access code. Agent Memory provides both short-term session memory (with TTL) and long-term semantic memory with vector search, background fact promotion, and metadata filtering. Together, they solve the “under-informed agent” problem by giving AI agents real-time access to fresh data and persistent cross-session context.

Why Redis Iris for Pydantic AI Agents? The Context Layer Problem#

Pydantic AI is a popular Python framework for building type-safe, structured LLM agents. However, every agent faces the same fundamental challenge: how does it access the data it needs to answer questions? Without a context layer, developers must write custom API calls, manage conversation history manually, and build bespoke retrieval pipelines for every agent. This approach is brittle, repetitive, and does not scale across multiple agents or sessions.

Redis Iris solves this by providing a unified context layer that sits between your Pydantic AI agent and your data. The Context Retriever exposes your database entities as MCP tools that the agent can discover and call dynamically. Agent Memory handles conversation persistence automatically — session memory keeps the current conversation flowing, while long-term memory enables the agent to recall facts from conversations days or weeks ago. The result is a Pydantic AI agent that is genuinely informed, context-aware, and production-ready with minimal custom code.

Step 1 — Set Up Redis Cloud and Context Retriever Surface#

Start by creating a Redis Cloud subscription. The free tier (30 MB) is sufficient for development and demos.

  1. Create a Redis Cloud database at app.redislabs.com. Note your endpoint URL and port.
  2. Provision a Context Retriever surface via the Redis Iris console. This requires:
    • A name for your surface (e.g., “northpeak-outfitters”)
    • Your Redis Cloud database endpoint
    • An entity model definition (JSON schema of your data entities)
  3. Generate an agent key — this is your X-API-Key for authenticating MCP requests. Agent keys can be scoped to specific surfaces and users, enabling multi-tenant access control without custom auth code.
  4. Enable Agent Memory on the surface. This provisions the session and long-term memory stores.

Once provisioned, your Context Retriever surface is accessible at a URL like:

https://gcp-us-east4.context-surfaces.redis.io/mcp

Step 2 — Configure Agent Memory (Session + Long-term)#

Agent Memory has two tiers:

Session Memory (Working Memory):

  • Stores conversation events with a configurable TTL (default: 24 hours)
  • Accessed via add_session_event_async() and search_session_memory_async()
  • Automatically cleaned up after TTL expires — no manual deletion needed

Long-term Memory (Semantic Memory):

  • Stores durable facts with vector embeddings for semantic search
  • Accessed via search_long_term_memory_async() and bulk_create_long_term_memories_async()
  • Supports metadata filters (e.g., filter by user_id, entity type, or confidence score)
  • Facts are auto-promoted from session memory by the managed service in the background

Configuration is minimal — the redis-agent-memory SDK handles connection pooling, retries, and serialization:

from redis_agent_memory import AgentMemoryClient

memory = AgentMemoryClient(
    surface_id="northpeak-outfitters",
    agent_key="your-agent-key",
    session_ttl_seconds=86400  # 24 hours
)

Step 3 — Build the Pydantic AI Agent with MCPToolset#

With Pydantic AI’s native MCP support (available since pydantic-ai-slim>=2.2.0), connecting to Redis Iris is straightforward. The MCPToolset class handles the MCP protocol handshake, tool discovery, and function calling automatically.

from pydantic_ai import Agent
from pydantic_ai.mcp import MCPToolset
from pydantic_ai.models.openai import OpenAIModel

model = OpenAIModel("gpt-4o")
agent = Agent(model=model)

# Connect to Redis Iris Context Retriever
async with MCPToolset.from_url(
    url="https://gcp-us-east4.context-surfaces.redis.io/mcp",
    headers={"X-API-Key": "your-agent-key"}
) as toolset:
    # All ~29 MCP tools are now available to the agent
    agent.register_toolset(toolset)
    
    result = await agent.run_sync(
        "Find all orders for customer John Smith that are still pending"
    )
    print(result.data)

The agent can now call tools like get_customer_by_id, filter_order_by_status, and search_product_by_text without any additional code. Pydantic AI handles the type-safe serialization of tool inputs and outputs.

Step 4 — Wire Agent Memory as search_memory / store_memory Tools#

To give the agent explicit memory access, wrap Agent Memory operations as Pydantic AI tools:

from pydantic_ai import RunContext, Tool
from redis_agent_memory import AgentMemoryClient

memory = AgentMemoryClient(surface_id="northpeak", agent_key="...")

async def search_memory(ctx: RunContext, query: str, user_id: str = "") -> str:
    """Search the agent's long-term memory for relevant context."""
    results = await memory.search_long_term_memory_async(
        query=query,
        metadata_filters={"user_id": user_id} if user_id else None,
        top_k=5
    )
    return "\n".join(
        f"[{r['created_at']}] {r['content']}"
        for r in results
    )

async def store_memory(ctx: RunContext, fact: str, user_id: str = "") -> str:
    """Store a durable fact in long-term memory."""
    await memory.bulk_create_long_term_memories_async([
        {"content": fact, "metadata": {"user_id": user_id, "source": "agent"}}
    ])
    return f"Stored: {fact}"

agent.register_tool(Tool(search_memory))
agent.register_tool(Tool(store_memory))

Now the agent can search its own memory during conversations and store important facts for future sessions. The background promotion service also automatically identifies and promotes durable facts from session memory, so even without explicit store_memory calls, important information persists.

Step 5 — Run the Agent: CLI Chat and Cross-Session Recall Demo#

Here is a complete CLI agent that demonstrates cross-session memory:

import asyncio
from pydantic_ai import Agent
from pydantic_ai.mcp import MCPToolset
from pydantic_ai.models.anthropic import AnthropicModel
from redis_agent_memory import AgentMemoryClient

model = AnthropicModel("claude-sonnet-4-20260501")
agent = Agent(model=model)
memory = AgentMemoryClient(surface_id="northpeak", agent_key="...")

async def main():
    async with MCPToolset.from_url(
        url="https://gcp-us-east4.context-surfaces.redis.io/mcp",
        headers={"X-API-Key": "..."}
    ) as toolset:
        agent.register_toolset(toolset)
        
        # Load previous session context
        past = await memory.search_long_term_memory_async(
            query="customer preferences",
            top_k=3
        )
        for p in past:
            print(f"  [Recall] {p['content']}")
        
        while True:
            user_input = input("\nYou: ")
            if user_input.lower() in ("exit", "quit"):
                break
            
            result = await agent.run_sync(
                user_input,
                system_prompt=f"Previous context: {past}"
            )
            print(f"Agent: {result.data}")
            
            # Auto-store facts
            await memory.add_session_event_async(
                event_type="user_query",
                content=user_input,
                metadata={"response": result.data}
            )

asyncio.run(main())

When you run this agent, it loads relevant long-term memory at startup, enabling cross-session recall. The agent remembers who you are, your preferences, and past interactions — even if you last chatted days ago.

How Context Retriever Auto-Generates MCP Tools (Entity → Tool Mapping)#

The Context Retriever generates four types of MCP tools for each entity in your model:

Tool PatternExampleDescription
get_{entity}_by_idget_customer_by_idFetch a single record by primary key
filter_{entity}_by_{field}filter_order_by_statusFilter records by exact field match
search_{entity}_by_textsearch_product_by_textFull-text search across text fields
find_{entity}_by_{field}_rangefind_order_by_date_rangeRange queries on numeric/date fields

For the Northpeak Outfitters demo with 5 entities (Customer, Product, Order, Shipment, Ticket), this generates approximately 29 MCP tools. Each tool includes a JSON schema derived from the entity model, so Pydantic AI can validate inputs and outputs automatically.

Tool names are sanitized client-side to meet LLM provider constraints. For example, Anthropic requires tool names matching ^[a-zA-Z0-9_-]{1,128}$, so the Context Retriever SDK normalizes names accordingly.

How Agent Memory Works — Session Events, Background Promotion, Semantic Search#

Agent Memory operates on three layers:

1. Session Events (Working Memory) Every user query, agent response, and system event is recorded as a session event with a TTL. These events are searchable within the current session and provide the agent with immediate conversational context. Session events are stored in Redis with automatic expiration.

2. Background Fact Promotion The managed service continuously analyzes session events to identify durable facts — information that is likely to be useful across sessions (user preferences, resolved issues, personal details). These facts are automatically extracted and promoted to long-term memory without developer intervention. The promotion runs as a background process, so there is no latency impact on the agent.

3. Long-term Semantic Memory Promoted facts are stored as vector embeddings with metadata. The search_long_term_memory_async() method performs semantic (vector) search, finding relevant facts even when the query uses different wording than the original fact. Metadata filters allow scoping searches to specific users, entities, or time ranges.

# Semantic search with metadata filtering
results = await memory.search_long_term_memory_async(
    query="prefers express shipping",
    metadata_filters={
        "user_id": "user_123",
        "entity_type": "preference"
    },
    top_k=5
)

Complete Code Walkthrough — agent.py, memory.py, config.py, cli.py#

The reference implementation at github.com/coleam00/redis-iris-agent organizes the code into four modules:

config.py — Central configuration for Redis Cloud connection, Context Retriever URL, Agent Memory surface ID, and LLM model selection. Default model is anthropic:claude-sonnet-4-6.

memory.py — Wraps the redis-agent-memory SDK with convenience methods for session events, long-term memory search, and bulk memory creation. Handles serialization and error handling.

agent.py — Builds the Pydantic AI agent, connects to the Context Retriever via MCPToolset, registers memory tools, and configures system prompts. This is the core orchestration module.

cli.py — A command-line chat interface that loads previous memory at startup, runs the agent loop, and stores session events after each interaction. Demonstrates the full cross-session memory flow.

The total codebase is under 500 lines, illustrating how much Redis Iris abstracts away.

Best Practices — Entity Naming, Tool Sanitization, Multi-User Scoping#

Entity Naming:

  • Use singular nouns for entity names (Customer, not Customers)
  • Keep field names consistent (camelCase or snake_case, but not mixed)
  • Include proper types in your entity model (string, number, date, array)

Tool Sanitization:

  • The Context Retriever SDK automatically sanitizes tool names for LLM provider constraints
  • Test with your target LLM provider — Anthropic and OpenAI have different naming rules
  • Avoid special characters in entity and field names to prevent sanitization conflicts

Multi-User Scoping:

  • Generate separate agent keys for each user or tenant
  • Use metadata filters on Agent Memory searches to scope results by user_id
  • The Context Retriever supports server-side access control via agent key permissions
  • This eliminates the need for custom auth middleware in your agent

Limitations and Preview Caveats#

Redis Iris is currently in preview and marked as a proof-of-concept. Key limitations to be aware of:

  1. Preview status — Both Context Retriever and Agent Memory are not yet production-ready. Expect API changes and potential downtime.
  2. Limited regions — The MCP endpoint is currently only available in gcp-us-east4. Latency may be significant for agents deployed in other regions.
  3. Entity model constraints — Complex relational queries (joins across entities) are not supported. Each tool operates on a single entity type.
  4. No streaming MCP — The current implementation uses streamable-HTTP, not SSE streaming. This may impact real-time applications.
  5. SDK maturity — The redis-agent-memory and redis-context-retriever SDKs are early-stage. Error handling and documentation are still evolving.
  6. Pricing — As a preview service, pricing for production use has not been announced.

Despite these caveats, Redis Iris represents a significant step forward in agent context management and is worth evaluating for your AI agent architecture.

Conclusion — When to Use Redis Iris for Your AI Agents#

Redis Iris is an excellent choice when you are building Pydantic AI agents that need:

  • Live data access without writing custom API or database code
  • Cross-session memory that persists and recalls relevant context automatically
  • Multi-tenant support with server-side access control
  • Rapid prototyping — the Northpeak Outfitters demo can be running in under 30 minutes

It is less suitable for production workloads today (given its preview status), complex multi-entity join queries, or teams that need full control over their retrieval pipeline.

For developers building the next generation of AI agents, Redis Iris demonstrates a compelling vision: agents that are genuinely informed by your data, remember every interaction, and require minimal boilerplate to set up. As the service matures toward production, it could become the default context layer for Pydantic AI agents.

FAQ#

Q: What is the difference between Context Retriever and Agent Memory in Redis Iris? A: Context Retriever auto-generates MCP tools from your entity model, giving the agent live access to your database. Agent Memory manages conversation history — short-term session memory with TTL and long-term semantic memory with vector search and background fact promotion. They are complementary services that together form the Redis Iris context layer.

Q: Does Redis Iris work with any LLM provider? A: Yes. Redis Iris is provider-agnostic. The Context Retriever exposes standard MCP tools, and Pydantic AI supports OpenAI, Anthropic, Google, and custom models. The reference implementation defaults to Anthropic’s Claude Sonnet 4, but you can switch providers by changing the model in your Pydantic AI agent configuration.

Q: How many MCP tools does Context Retriever generate? A: The Context Retriever generates four tool types per entity: get_by_id, filter_by, search_by_text, and find_by_range. For the Northpeak Outfitters demo with 5 entities, this produces approximately 29 MCP tools. The exact count depends on the number of fields in each entity that support each operation type.

Q: Can I use Redis Iris without Pydantic AI? A: Yes. The Context Retriever exposes standard MCP tools over streamable-HTTP, which any MCP-compatible client can consume. However, Pydantic AI’s native MCPToolset support (since pydantic-ai-slim>=2.2.0) provides the most seamless integration. Other frameworks like LangGraph also work with Redis Iris, as demonstrated by several community reference implementations.

Q: Is Redis Iris free to use? A: Redis Iris is currently in preview and marked as a proof-of-concept. You need a Redis Cloud subscription (free tier available) for the underlying database. The Context Retriever and Agent Memory services are available during the preview period, but pricing for production use has not been announced. Check redis.com/iris for the latest pricing information.
