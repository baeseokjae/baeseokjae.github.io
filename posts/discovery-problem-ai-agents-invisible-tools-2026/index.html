Introduction — The Tool That Works But Can’t Be Found#

The AI agent discovery problem describes a growing crisis in multi-agent systems: agents build and install tools that work perfectly in isolation but become invisible to other agents that need them. In a controlled audit by IX Coach and Next AI Labs, 53% of newly installed AI skills failed a discoverability check — they existed, functioned correctly, and produced output, yet no agent could find them when the capability was needed. This is not a performance bug or a reliability failure. It is a discovery failure, and it is silently undermining every organization that deploys AI agents as tool builders.

The Invisible Capability Problem#

An invisible capability is a tool or skill that an AI agent has installed and can use, but that no other agent in the system can discover through normal discovery surfaces. The tool works. The agent that installed it can invoke it. But when a different agent encounters a task that would benefit from that tool, the discovery system returns nothing. No error is thrown. No alert is raised. The requesting agent simply takes a different, often less efficient, path — or fails entirely.

This is fundamentally different from a broken tool or a failed installation. A broken tool produces errors that can be logged, monitored, and fixed. An invisible tool produces nothing at all. It is a silent drain on the system’s effective capability, and because it generates no negative signal, organizations rarely know it exists.

How AI Agents Lose Institutional Knowledge Without Anyone Noticing#

The mechanism is straightforward. An agent is assigned a task — say, generating a compliance report. To complete the task, it installs a skill that queries internal APIs, formats data, and produces the report. The skill works. The report is delivered. The task is marked done.

Later, a different agent is assigned a similar compliance task. It queries the discovery system for available tools. The compliance skill does not appear in the results — perhaps because its trigger metadata was never configured, or because it was registered under a different semantic namespace. The second agent builds its own tool from scratch, duplicating effort. The organization now has two tools that do the same thing, neither aware of the other.

Over time, this pattern repeats across teams, projects, and agent sessions. The organization accumulates a growing collection of invisible capabilities — tools that exist but might as well not exist, because no one and no agent can find them.

The Compounding Effect of Undiscoverable Tools#

The problem compounds non-linearly. Each agent session that builds a tool without verifying its discoverability adds to the invisible pile. The more agents an organization deploys, the faster the pile grows. The more tools each agent builds, the higher the invisibility rate becomes.

Consider a small team running 10 agent sessions per week, with each session producing one new tool. At a 53% invisibility rate, that is roughly 5 invisible tools per week. After one month, the team has 20 invisible capabilities. After six months, 120. After a year, 260 — all silently degrading the system’s effective capability.

At scale, the numbers become staggering. An organization running 1,000 tools with a 53% invisibility rate has over 500 capabilities that are functionally undiscoverable. This is not a minor inefficiency. It is a strategic liability.

The Discovery Audit That Revealed 53% Invisibility#

The most cited data point on the AI agent discovery problem comes from a controlled discoverability audit conducted by IX Coach in partnership with Next AI Labs. The study tested a multi-agent system where agents could install skills from both internal (custom-built) and external (community-sourced) sources. After installation, a separate discovery agent attempted to locate each skill using five standard discovery surfaces.

The results were stark: 53% of newly installed skills could not be found by any discovery method. The skills were present in the system. They were functional. They passed all installation checks. But they were invisible to the discovery layer.

Custom vs. External Skills — A Stark Divide#

The audit revealed a critical distinction. Custom-built skills — tools developed internally by the organization’s own agents — were 100% discoverable. Every custom skill passed all five discovery surfaces. The reason is straightforward: internal development processes naturally include the metadata, naming conventions, and registration steps that make tools findable.

Externally-sourced skills — tools downloaded from community registries, open-source repositories, or third-party marketplaces — were 0% discoverable. Not one externally-sourced skill could be found by any discovery method without manual intervention. These skills arrived with incomplete or missing metadata, inconsistent naming, and no standardized trigger configuration.

This divide creates a perverse incentive: organizations that rely heavily on external tools and community skills — precisely the organizations that benefit most from the AI tool ecosystem — are the ones most affected by the discovery problem.

The Absurdly Small Fix: 3-5 Lines of YAML#

The most surprising finding of the audit is that the fix is remarkably simple. Making a skill discoverable requires only 3-5 lines of YAML trigger metadata. A properly configured skill definition includes:

triggers:
  - keyword: "compliance report"
    synonyms: ["regulatory filing", "audit document", "regulatory compliance"]
  - keyword: "data query"
    synonyms: ["database lookup", "information retrieval"]

These few lines tell the discovery system what the tool does, what keywords should activate it, and what alternative phrases agents might use. Without them, the discovery system has no signal to match against. With them, the tool becomes findable across all five discovery surfaces.

The gap between a 0% discoverable skill and a 100% discoverable skill is three lines of configuration. The fact that this fix is so small makes the scale of the problem — 53% invisibility — even more striking.

The Five Discovery Surfaces and Their Failure Modes#

The IX Coach audit identified five distinct surfaces through which agents discover tools. Each surface has independent failure modes, meaning a tool that is visible on one surface can be completely invisible on another. For a tool to be reliably findable, it must pass all five.

Protocol Auto-Listing#

Protocol auto-listing is the most basic discovery surface. When an agent connects to a tool server, the server advertises its available tools through the protocol handshake. If the tool is not registered with the server, or if the server does not support auto-listing, the tool is invisible at this level.

Failure modes: The tool is installed but not registered with any server. The server does not implement the auto-listing protocol. The tool is registered under a different protocol version than the requesting agent supports.

Trigger Matching#

Trigger matching is the surface most directly affected by metadata configuration. The discovery system compares the requesting agent’s task description against the trigger keywords and synonyms defined in each tool’s metadata. If no trigger matches, the tool is not returned.

Failure modes: No trigger metadata is defined. The trigger keywords do not match the language the requesting agent uses. Synonyms are missing. The trigger is too narrow or too broad.

Tooling Registry#

The tooling registry is a centralized database of available tools. Agents query the registry by name, category, or capability. This is the most traditional discovery surface and the one most analogous to a package manager.

Failure modes: The tool is not registered. The registration is stale or points to a removed version. The registry does not index the tool’s capabilities, only its name. The registry is not shared across teams or organizations.

Semantic Swarm Search#

Semantic swarm search is a decentralized discovery method where agents broadcast capability queries to other agents in the swarm. If another agent has the tool, it responds with a reference. This surface is designed to catch tools that fall through the cracks of centralized registries.

Failure modes: The swarm is not connected. The query embedding does not match the tool’s embedding. The agent that owns the tool is offline or not participating in the swarm. The swarm has no mechanism for propagating queries across organizational boundaries.

Registry Semantic Search#

Registry semantic search combines the centralized registry with semantic matching. Instead of searching by exact name, agents search by meaning — the registry returns tools whose capability descriptions semantically match the query.

Failure modes: The tool’s description is too vague or too specific. The embedding model used by the registry does not align with the requesting agent’s embedding model. The description uses different terminology than the query. The registry’s semantic index is stale.

The Ecosystem Response: Registries, Package Managers, and Discovery Layers#

The market has responded to the AI agent discovery problem with a wave of registries, package managers, and discovery layers. Each takes a different approach to solving the same fundamental challenge: making AI tools findable.

MCPfinder — The Agent-Facing Discovery Layer#

MCPfinder is an open-source MCP server that discovers and installs other MCP servers. It aggregates 27,432 servers across three major registries: the Official MCP Registry, Glama, and Smithery. What makes MCPfinder distinctive is its AI-native interface — it is itself an MCP server, so agents discover tools programmatically without human intervention.

MCPfinder provides trust signals for each server it indexes: a confidence score, source count across registries, warning flags for potential issues, and an install complexity rating. It also generates client-specific install configurations for Claude Desktop, Cursor, Claude Code, Cline, and Windsurf, reducing the friction of moving from discovery to installation.

Enact — Package Manager for AI Tools#

Enact positions itself as a package manager for AI agent tools, analogous to npm for JavaScript or pip for Python. Its focus is on curation and verification of tool quality. Rather than indexing every available server, Enact applies quality gates to ensure that listed tools meet minimum standards for documentation, metadata completeness, and functionality.

The package manager approach addresses the discovery problem at its root: by enforcing metadata standards at the point of publication, Enact ensures that every tool in its registry is discoverable by default. The trade-off is a smaller registry with higher quality per entry.

Vet — Security-First Registry#

Vet (getvet.ai) takes a security-first approach to tool discovery. It indexes over 88,000 MCP servers and AI tools, making it one of the largest registries in the ecosystem. Vet’s primary question is “Is this MCP server safe to install?” — it provides security verification, vulnerability scanning, and trust ratings for each indexed tool.

Vet addresses a related but distinct problem: even if a tool is discoverable, how does an agent know it can trust it? In a world where agents autonomously install tools from community sources, security verification becomes a prerequisite for discovery. A tool that is findable but unsafe is arguably worse than a tool that is invisible.

AgentLookup — Agent-to-Agent Discovery#

AgentLookup takes a fundamentally different approach. Instead of a tool-to-agent discovery model, it enables agent-to-agent discovery. Agents register themselves in a public registry, and other agents can find them by capability. This shifts the discovery problem from “what tools exist” to “what agents exist and what can they do.”

AgentLookup’s decentralized model is designed for scenarios where tools are tightly coupled to specific agent implementations. Rather than discovering a tool and figuring out which agent can run it, you discover the agent and inherit its toolset. This approach is particularly relevant for organizations that deploy specialized agents with curated toolchains.

The Scale Problem: From 5 to 500 Invisible Capabilities#

The AI agent discovery problem is not static. As organizations scale their agent deployments, the problem scales with them — and the relationship is not linear.

At 10 tools with a 53% invisibility rate, roughly 5 tools are invisible. This is annoying but manageable. A human operator can manually audit the toolchain and fix the metadata. At 100 tools, 50 are invisible. Manual audit is still possible but time-consuming. At 1,000 tools, 500 are invisible. Manual audit is no longer feasible. The organization has a strategic crisis on its hands.

The IX Coach scaling analysis projects that at 10,000 tools — a realistic number for a large enterprise within 12-18 months — 5,300 capabilities would be undiscoverable. At that scale, the effective capability of the system is less than half of its installed capability. Organizations are paying for tools they cannot use.

The compounding effect makes this worse. Each invisible tool that is duplicated by another agent creates two invisible tools where one existed before. Each duplicated tool that is itself invisible adds to the discovery burden. The system’s discoverability degrades over time, not improves.

Open Questions and Unsolved Challenges#

Despite the emerging ecosystem of registries and discovery layers, several fundamental challenges remain unsolved.

Trigger Phrase Design Is Still Art, Not Science#

The most critical input to trigger matching — the trigger phrase — has no established design methodology. We do not know what keywords agents will use when searching for a tool. We do not know whether a single trigger phrase is sufficient or whether a tool needs a dozen synonyms. We do not know how trigger phrases should evolve as agent language models change.

The IX Coach audit found that custom-built skills were 100% discoverable, but this was in a controlled environment where the development agents and discovery agents used the same language model. In the wild, different agents may use different models with different semantic embeddings, making trigger phrase design even more uncertain.

Cross-Organizational Discovery Is Unsolved#

No shared discovery layer exists across organizational boundaries. Company A’s agents cannot discover tools built by Company B’s agents, even when both companies would benefit from sharing capabilities. The existing registries (MCPfinder, Enact, Vet) are public registries for open-source tools, not private discovery layers for enterprise tool sharing.

Organizational boundary discovery requires solving authentication, authorization, and trust problems that go beyond metadata configuration. An organization needs to control which tools are visible to which partners, under what terms, and with what usage restrictions. No current solution addresses this comprehensively.

We Can’t Measure the Cost of Undiscoverable Tools#

Organizations have no standard metric for the cost of invisible capabilities. How much engineering time is wasted on rebuilding tools that already exist? How many tasks fail because the right tool could not be found? How much slower is an agent that takes a suboptimal path because it could not discover the optimal tool?

Without a cost metric, organizations cannot justify the investment in discovery infrastructure. The problem remains invisible — in every sense of the word.

Semantic Search Creates False Confidence#

Semantic search is the most sophisticated discovery surface, but it may be the most dangerous. When an agent performs a semantic search and gets a result, it assumes the tool is relevant. But semantic matching is probabilistic, not deterministic. A tool that partially matches a query may be returned while a perfectly matching tool with different terminology is not.

The IX Coach audit found that semantic search created false confidence in the discovery system. Operators assumed that semantic matching would catch tools that fell through the cracks of other surfaces. In practice, semantic search had its own failure modes and could not compensate for missing metadata on other surfaces.

Building Discovery-First: Making Discoverability a First-Class Property#

The solution to the AI agent discovery problem is not a single tool or registry. It is a shift in how organizations think about tool development. Discoverability must become a first-class property of every tool, verified at build time and audited continuously.

A discovery-first approach includes:

  1. Mandatory metadata at creation. Every tool must include trigger metadata, capability descriptions, and semantic tags before it is registered. This should be enforced by the development pipeline, not left to individual agent discretion.

  2. Automated discoverability testing. Every tool should pass an automated discoverability audit before it is deployed. The audit should test all five discovery surfaces and report any failures. A tool that fails discoverability should not be deployed.

  3. Continuous discovery monitoring. Discoverability is not a one-time property. As discovery systems evolve, as new surfaces are added, and as agent language models change, a tool’s discoverability can degrade. Continuous monitoring ensures that tools remain findable over time.

  4. Zero-touch observability for toolchains. The discovery system itself should be observable. Organizations should be able to measure discovery success rates, identify invisible tools, and track the effective capability of their agent systems over time.

  5. Cross-registry standards. The ecosystem needs shared standards for tool metadata, trigger configuration, and discovery protocols. Without standards, each registry becomes a silo, and the discovery problem simply moves from the tool level to the registry level.

Conclusion — The Effective Capability of a System Is What Agents Can Find, Not What Exists#

The AI agent discovery problem is one of the most underappreciated challenges in the multi-agent systems landscape. A 53% invisibility rate means that the majority of tools in a typical system are functionally useless — not because they are broken, but because they cannot be found.

The fix is absurdly small: 3-5 lines of YAML trigger metadata per skill. But the organizational change required to enforce that fix is significant. It requires treating discoverability as a first-class property of every tool, building automated discovery testing into the development pipeline, and continuously monitoring discovery health over time.

As AI agents become prolific tool builders — and they will, because every agent session is an opportunity to create a new capability — the discovery problem will only grow. Organizations that address it now, while the tool count is still manageable, will have a strategic advantage. Organizations that ignore it will find themselves with thousands of tools and no way to use them.

The effective capability of an AI agent system is not what exists. It is what agents can find. Until the discovery problem is solved, the majority of your tools might as well not exist.
