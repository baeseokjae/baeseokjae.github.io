What Is Twigg and Why Does It Matter?#

Twigg is an open-source version control system and software forge written entirely from scratch in Go that brings big-tech development workflows — trunk-based development, stacked commits, hierarchical code ownership, and integrated CI/CD — to teams of any size. Unlike Git, which evolved organically over two decades, Twigg was designed from the ground up for modern development practices, offering a self-hostable or cloud-hosted alternative that challenges Git’s near-monopoly in version control. With AGPL-3.0 licensing and a production-ready codebase already used by its creators and three partner companies, Twigg represents a bold rethinking of what version control should look like in 2026.

What Makes Twigg Different from Git?#

Twigg is not a Git wrapper or a Git-compatible frontend. It is a completely new version control system written from scratch in Go. This fundamental architectural decision shapes every aspect of the tool. Where Git was designed as a content-addressable filesystem with version control as a secondary concern, Twigg was designed with modern development workflows as the primary requirement.

The most significant philosophical difference is Twigg’s default workflow. Git defaults to long-running feature branches and merge commits, requiring teams to adopt additional practices and tooling to achieve trunk-based development. Twigg makes trunk-based development the default, not an afterthought. Every feature of the system — from its commit model to its code review interface — is optimized for small, frequent commits merged directly to the mainline.

Stacked commits are another area where Twigg diverges sharply from Git. While Git supports stacked branches through tools like git rebase and interactive rebase, the workflow is manual, error-prone, and poorly supported by most Git hosting platforms. Twigg treats stacked commits as a first-class concept, making it natural to break large changes into a series of small, reviewable patches that build on each other.

How Does Twigg’s Architecture Work?#

Twigg is composed of three main components that work together to provide a complete development platform:

twigg-web: The Software Forge#

Twigg-web is the web server and software forge component. It provides the web interface for code browsing, pull request management, code review, repository administration, and user management. Unlike GitHub or GitLab, which bolt these features onto a Git backend, twigg-web is deeply integrated with Twigg’s native version control engine. This tight integration enables features that are difficult or impossible to achieve with Git-based forges, such as real-time awareness of stacked commit dependencies and automatic rebase of dependent changes.

twigg-track: The CI/CD Server#

Twigg-track is the built-in continuous integration and continuous deployment server. Rather than requiring a separate CI/CD tool like Jenkins, GitHub Actions, or GitLab CI, Twigg includes CI/CD as a native component. This means the version control system has first-class knowledge of build and deployment status, enabling features like automatic blocking of merges when dependent changes fail CI, and intelligent test selection based on the actual changes in a commit stack.

tw CLI: The Command-Line Tool#

The tw command-line tool is the primary interface for developers interacting with Twigg on a daily basis. It handles cloning, committing, pushing, pulling, reviewing, and managing stacked commits. The CLI is designed to be intuitive for developers coming from Git while introducing new concepts gradually. Commands follow a logical structure that mirrors common development workflows rather than Git’s sometimes cryptic command set.

VS Code Extension#

Twigg also offers a VS Code extension that provides in-editor code review, stacked commit management, and real-time CI status. This brings the full Twigg experience directly into the developer’s editor, reducing context switching and making stacked commit workflows visually manageable.

What Are the System Requirements for Self-Hosting Twigg?#

Twigg servers currently run exclusively on Linux. The full requirements for self-hosting include Go, Node.js, Docker, and LXD for complete CI/CD functionality. This is a significant consideration for teams that operate on Windows or macOS servers, or for organizations that prefer minimal infrastructure dependencies.

The self-hosting requirements reflect Twigg’s design as a modern, container-aware system. Docker and LXD are used to provide isolated build environments for CI/CD pipelines, ensuring that builds are reproducible and secure. While this adds to the initial setup complexity, it provides a robust foundation for production deployments.

For teams that prefer not to manage their own infrastructure, Twigg offers a hosted instance at twigg.vc, providing the same functionality without the operational overhead.

Twigg vs Git#

Git benefits from two decades of development, an enormous ecosystem, universal adoption, and deep integration with every development tool in existence. Twigg cannot match Git’s ecosystem maturity. However, Git’s age is also its weakness. Git’s data model, designed in 2005, does not natively support modern workflows like stacked commits or trunk-based development. Teams that want these workflows must layer complex tooling on top of Git. Twigg provides them out of the box.

Twigg vs Jujutsu (jj)#

Jujutsu, written in Rust, has gained significant popularity as a modern Git alternative that maintains full Git compatibility. Jujutsu’s key advantage is that it works as a drop-in replacement for Git — it uses the same underlying Git repository format, meaning teams can adopt jj without changing their hosting platform. Twigg takes a more radical approach, requiring its own server infrastructure but offering a complete platform (forge + CI/CD) in return.

Twigg vs Meta’s Sapling#

Sapling (formerly EdenSCM) was built by Meta to handle their massive monorepo and is battle-tested at extraordinary scale. It supports stacked diffs and interactive rebase workflows. However, Sapling was primarily designed for Meta-scale needs and may be overkill for smaller teams. Twigg targets a broader audience, from small startups to mid-size organizations that want big-tech workflows without big-tech complexity.

Twigg vs Diversion#

Diversion (YC S22) received 280 points on Hacker News, indicating strong interest in non-Git VCS solutions. Diversion takes a cloud-native approach, meaning it cannot be self-hosted. Twigg’s self-hostable model appeals to organizations that need control over their data, compliance requirements, or air-gapped environments. Diversion’s cloud-native architecture may offer a smoother onboarding experience, while Twigg requires more setup but provides more control.

How Do You Get Started with Twigg?#

Getting started with Twigg depends on whether you want to use the hosted instance or self-host.

Using the Hosted Instance#

The simplest way to try Twigg is through the hosted instance at twigg.vc. This provides immediate access to all Twigg features without any infrastructure setup. The hosted instance is ideal for evaluation, small teams, and individual developers who want to experience the Twigg workflow before committing to self-hosting.

Self-Hosting Twigg#

For teams that need to self-host, the process involves setting up a Linux server with Go, Node.js, Docker, and LXD installed. The Twigg repository on GitHub provides detailed setup instructions. The AGPL-3.0 license means that if you modify Twigg and deploy it as a network service, you must release your modified source code — an important consideration for organizations with proprietary extensions.

The Git Mirror Feature#

One of Twigg’s most practical features is Git Mirror, which provides automatic backup and a migration path back to Git. This reduces the risk of adopting Twigg: if a team decides Twigg is not right for them, they can migrate their entire repository history back to Git without data loss. The Git Mirror also serves as a safety net during the transition period, allowing teams to maintain a Git-based backup while exploring Twigg’s workflows.

Is Twigg Production-Ready?#

According to the Twigg README, the system has been used in production for more than a year by the Twigg team and three partner companies. This suggests a level of stability beyond a typical early-stage open-source project. However, with only 61 GitHub stars and 1 fork as of July 2026, the community around Twigg is extremely small.

The Show HN post on July 24, 2026, received 17 points and 7 comments on Hacker News. Community response was mixed — some developers expressed genuine enthusiasm for the project’s ambition, while others raised concerns about potential sockpuppet accounts inflating the project’s early traction. This skepticism is understandable for any new version control system claiming to replace Git.

For teams considering Twigg, the production readiness assessment depends heavily on their risk tolerance. The core technology appears solid, and the team has been using it internally for over a year. However, the small community means limited third-party testing, fewer community-contributed bug fixes, and less available expertise when problems arise.

What Are the Pros and Cons of Twigg?#

Pros#

  • Purpose-built for modern workflows: Trunk-based development and stacked commits are first-class features, not afterthoughts
  • All-in-one platform: Version control, code forge, and CI/CD in a single integrated system
  • Self-hostable: Full control over data and infrastructure, suitable for compliance requirements
  • Written in Go: A single compiled binary, easy deployment, strong performance characteristics
  • Git Mirror: Safety net for migration and backup, reducing adoption risk
  • AGPL-3.0 licensed: Strong copyleft ensures the project remains open source
  • Not a Git wrapper: Clean architecture without legacy design compromises

Cons#

  • Extremely small community: 61 GitHub stars and minimal community engagement as of July 2026
  • Linux-only server: No support for Windows or macOS server deployments
  • Complex self-hosting requirements: Requires Go, Node.js, Docker, and LXD
  • No Git compatibility: Cannot use Git-based tools, hosting platforms, or workflows directly
  • Early-stage maturity: Limited third-party testing, documentation, and community support
  • AGPL concerns: The strong copyleft license may be problematic for some organizations
  • Skepticism from the developer community: Mixed reception on Hacker News raises questions about adoption trajectory

Who Should Use Twigg?#

Twigg is best suited for teams that are frustrated with Git’s workflow limitations and are willing to invest in a new tool for a better developer experience. Ideal candidates include:

  • Small to mid-size engineering teams that want big-tech development workflows without big-tech infrastructure
  • Teams practicing trunk-based development or wanting to adopt it
  • Organizations that need self-hosted infrastructure for compliance, security, or air-gapped environments
  • Developer tool enthusiasts who enjoy experimenting with new technologies
  • Teams using AI-assisted coding where atomic commits and stacked changes are particularly valuable

Twigg is less suitable for:

  • Large enterprises with established Git-based toolchains and workflows
  • Teams that rely on GitHub, GitLab, or Bitbucket for project management and code review
  • Organizations uncomfortable with AGPL licensing
  • Teams without Linux server infrastructure
  • Projects that need maximum ecosystem compatibility

Frequently Asked Questions#

Is Twigg compatible with Git?#

No, Twigg is not Git-compatible. It uses its own data model and protocol. However, Twigg includes a Git Mirror feature that provides automatic backup to a Git repository and enables migration back to Git if needed. This means you can maintain a Git-based safety net while using Twigg for daily development.

Can I use Twigg with GitHub or GitLab?#

No, Twigg cannot be used with GitHub or GitLab because it is not Git-compatible. Twigg includes its own software forge (twigg-web) and CI/CD server (twigg-track), providing an all-in-one platform that replaces the need for separate hosting and CI/CD services.

What programming language is Twigg written in?#

Twigg is written entirely in Go. The entire system — the version control engine, the web forge, the CI/CD server, and the command-line tool — was built from scratch in Go. This is a deliberate architectural choice that provides strong performance, easy deployment as a single binary, and excellent concurrency support.

How does Twigg handle stacked commits?#

Twigg treats stacked commits as a first-class concept. Unlike Git, where stacked branches require manual management with rebase operations, Twigg natively understands the dependency relationships between commits in a stack. The web interface and CLI both provide tools for visualizing, reviewing, and managing stacked changes, and the CI/CD server automatically understands which builds need to run based on the stack structure.

Is Twigg free to use?#

Yes, Twigg is open-source software licensed under AGPL-3.0. You can use it, modify it, and deploy it for free. The AGPL-3.0 license requires that if you modify Twigg and deploy it as a network service, you must make your modified source code available to users. The hosted instance at twigg.vc is also available for use, though the pricing model for the hosted service has not been detailed publicly.
