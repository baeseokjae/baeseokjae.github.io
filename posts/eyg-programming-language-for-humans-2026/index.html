EYG Programming Language for Humans: A Fresh Take on Language Design

EYG (Eat Your Greens) is a statically typed functional language for makers — non-professional developers who build home-cooked software without fighting deployment complexity.

EYG (Eat Your Greens) is a statically typed functional programming language created by Peter Saxton that targets “makers” — technically minded people who build home-cooked software but are not professional developers. It separates the act of describing logic from the complexity of working with computers, handling deployment, runtime management, and side effects through a sound structural type system that requires no type annotations. EYG promises predictability, usefulness, and confidence for the growing population of citizen developers.

What Is EYG? — The “Eat Your Greens” Philosophy#

EYG, short for “Eat Your Greens,” was created by Peter Saxton during a 10-week visa wait period for a job in Sweden. The name reflects a core philosophy: delayed gratification in language design. Just as eating your vegetables provides long-term health benefits at the cost of short-term pleasure, EYG imposes constraints now — structural typing, effect management, sandboxed execution — to deliver guarantees later: programs that never crash, dependencies that never break, and side effects that are always predictable.

The language is built on three core promises, as stated on its official website at eyg.run:

  • Predictable: Deterministic execution with immutable, hashed dependencies. The same program always produces the same result.
  • Useful: Programs run anywhere with managed effects. EYG abstracts away deployment and runtime concerns so makers focus on logic.
  • Confident: A sound structural type system guarantees programs never crash at runtime, without requiring a single type annotation from the programmer.

EYG is not trying to replace JavaScript, Python, or Rust. It is targeting a different audience entirely: the millions of technically-minded professionals — accountants, biologists, operations managers, data analysts — who write scripts and build tools as a means to an end, not as their primary job.

The Problem EYG Solves — Why End User Programming Disappoints#

Most programming languages were designed by professional developers for professional developers. Python, the most popular “beginner-friendly” language, still requires understanding of virtual environments, pip, dependency resolution, deployment, and error handling. JavaScript demands knowledge of Node.js, npm, bundlers, and a constantly shifting ecosystem. Even “simple” scripting languages force makers to become amateur DevOps engineers before they can ship anything useful.

The result is a massive gap: millions of people who could benefit from writing software simply do not, because the overhead of becoming a “real developer” is too high. This is the problem EYG was designed to solve.

Peter Saxton articulated this clearly in his announcement post: “EYG is a programming language for humans — for people who want to describe logic and have it run somewhere without becoming experts in how computers work.” The language abstracts away what Saxton calls “category 2” problems — everything related to deployment, runtime, dependencies, and infrastructure — so makers can focus entirely on “category 1” problems: describing what they want the program to do.

Humans vs Developers — Two Categories of Programming Work#

EYG draws a sharp distinction between two fundamentally different kinds of programming work:

CategoryWhat It InvolvesWho Does ItEYG’s Approach
Category 1: Describing LogicWriting the actual business rules, transformations, and workflowsMakers, domain experts, end usersEYG’s primary focus — clean functional syntax with structural typing
Category 2: Working with ComputersDeployment, dependency management, runtime configuration, error handling, infrastructureProfessional developers, DevOpsFully abstracted away by EYG’s runtime and effect system

This separation is the key insight behind EYG. Most languages force makers to master both categories before they can ship anything. EYG eliminates category 2 entirely from the maker’s concern. The language handles deployment, dependency resolution, sandboxing, and runtime management automatically.

In many ways, EYG is aiming to be what Excel is for spreadsheet users — a tool where domain experts can express logic without needing to understand the underlying computing infrastructure. Excel users do not worry about memory management, process scheduling, or file I/O. EYG makers should not have to worry about dependency graphs, deployment pipelines, or runtime errors.

Core Features — Sound Type Inference, Hashed Dependencies, and Effect Typing#

How Does EYG’s Type System Work Without Annotations?#

EYG uses structural row typing — a proven mathematical foundation for type checking that infers types automatically from how values are used. Unlike nominal typing (used by Java, TypeScript, Gleam), where types are checked by explicit name or declaration, structural typing checks compatibility based on shape. If two values have the same structure, they are the same type, regardless of what they are called.

This means EYG programmers never write type annotations. The compiler infers everything. Yet the type system is sound — if a program compiles, it will never crash at runtime due to a type error. This is a dramatic improvement over Python (dynamically typed, runtime errors common) and TypeScript (unsound by design, type escapes are possible).

What Are Hashed Dependencies and Why Do They Matter?#

EYG identifies dependencies by the hash of the module’s contents, not by a version number or package name. This is a radical departure from every mainstream package manager. When you depend on a module in EYG, the dependency is pinned to the exact content hash of that module. If the module changes, the hash changes, and the dependency is explicitly broken — no more “works on my machine” or “left-pad” style dependency hell.

This approach provides several guarantees:

  • Immutability: A dependency can never change under your feet. The hash is the identity.
  • Determinism: Every build with the same hashes produces the same result, forever.
  • Security: Hash verification prevents supply chain attacks. You know exactly what code you are running.
  • No version conflicts: Two modules depending on different versions of the same library is not a problem — they are different hashes, treated as different dependencies.

How Does Effect Typing Make Programs Safer?#

EYG captures side effects in its type system. Every function that performs I/O, network access, file operations, or any other side effect declares those effects in its type. The EYG runtime then enforces that programs only perform effects they have explicitly declared.

This is not new in programming language theory — Haskell has had this for decades — but EYG makes it practical for non-professional developers. Effects in EYG are expressed at a business-relevant level of abstraction. Instead of “HTTP GET request,” an effect might be “authenticate with OAuth” or “query customer database.” The runtime exposes focused effect sets, and programs declare their required effects statically before execution.

The result is sandboxed by default: every EYG program runs in a restricted environment where its capabilities are known and limited before it executes. This is ideal for the maker use case, where programs are often shared, run on other people’s machines, or deployed to cloud runtimes automatically.

EYG vs Gleam — Structural vs Nominal Typing#

EYG is frequently compared to Gleam, and for good reason. Peter Saxton was a Gleam contributor before creating EYG, and both languages are statically typed functional languages targeting approachable programming. However, they diverge on a fundamental design axis: structural vs nominal typing.

The structural vs nominal distinction is more than academic. For a maker who does not want to think about types at all, EYG’s approach is superior — types are inferred and invisible until they catch an error. Gleam requires explicit type annotations on function signatures, which is fine for professional developers but adds friction for makers.

Saxton has been explicit about this divergence. In his Func Prog Sweden talk (October 2024), he explained that EYG’s structural typing was a deliberate choice to eliminate the “ceremony” of type annotations while maintaining soundness. Gleam’s nominal typing, by contrast, prioritizes clarity and explicitness for team-scale codebases.

Use Cases — Glue Problems, Dashboards, and Automations#

EYG is not designed for building large-scale web applications, operating systems, or game engines. It is designed for the kinds of software that makers build every day:

  • Glue problems: Connecting APIs, transforming data between formats, automating repetitive tasks across services.
  • Personal dashboards: Pulling data from multiple sources (spreadsheets, databases, APIs) and presenting it in a unified view.
  • Automations: Scheduled tasks, file processing, email filtering, notification systems.
  • Data transformation: Cleaning, joining, and reshaping datasets without writing complex pandas or SQL pipelines.
  • Home-cooked software: The term popularized by Robin Sloan and Maggie Appleton — small, personal tools built for one person or a small team, not for millions of users.

These are precisely the kinds of problems that Python and JavaScript handle poorly for non-professionals. A maker who wants to build a personal dashboard today must learn: Python syntax, pip, virtual environments, a web framework (Flask or FastAPI), HTML/CSS, deployment (Heroku, Vercel, or a VPS), and ongoing maintenance. With EYG, they describe the logic, declare the effects (HTTP, database, scheduling), and the runtime handles the rest.

The Hacker News Reception — Praise, Skepticism, and Debate#

EYG reached 80 points and 62 comments on Hacker News on July 28, 2026, generating a lively debate about the language’s philosophy and positioning.

The praise centered on several themes:

  • The structural editor was widely appreciated. EYG’s editor prevents creating syntactically invalid code, which several commenters noted would be a significant quality-of-life improvement for beginners.
  • The taxonomy of “category 1 vs category 2” programming work resonated with many readers who had experienced the frustration of helping non-developer colleagues set up Python environments.
  • The hashed dependency system was recognized as genuinely innovative, with several commenters noting that it solves a real problem that even mature ecosystems (npm, pip, RubyGems) have not addressed.

The skepticism was equally pointed:

  • Several commenters questioned whether there was room for a new programming language in the LLM era. “If AI can generate code in any language, why learn a new one?” was a recurring theme.
  • Others pointed out that Python already serves the maker audience reasonably well. “What friction does EYG actually remove that Python doesn’t already handle?” one commenter asked.
  • Comparisons to Gherkin and Cucumber were raised — domain-specific languages that promised to let non-developers write code but ultimately failed to gain traction outside of testing.

The debate highlighted a genuine tension: EYG’s value proposition is strongest for people who do not currently write software at all, not for people who already use Python or JavaScript. The question is whether those people will discover EYG before they discover Python.

EYG in the LLM Era — Is There Still Room for New Languages?#

The Hacker News discussion raised an existential question for any new programming language in 2026: when AI can generate code in any existing language, why would anyone learn a new one?

There are several arguments for why EYG remains relevant:

1. LLMs amplify the wrong complexity. An AI that generates Python code still produces code that requires Python tooling, environment setup, dependency management, and deployment. The maker still needs to become a Python developer to run the generated code. EYG eliminates that entire category of work.

2. EYG’s structural editor is AI-complementary. A structural editor that prevents syntax errors is even more valuable when working with AI-generated code, which is notorious for subtle bugs and hallucinated APIs. EYG’s type system catches these before they reach runtime.

3. The maker audience is growing, not shrinking. As more professionals in non-software fields adopt computational thinking, the demand for tools that lower the barrier to entry increases. EYG targets this growing population directly.

4. Determinism matters for AI-generated code. EYG’s hashed dependencies and deterministic execution mean that AI-generated EYG code is reproducible and verifiable. This is harder to guarantee with Python or JavaScript, where dependency resolution is non-deterministic.

The most compelling argument, however, is that EYG is not competing with LLMs — it is competing with the complexity of existing toolchains. An LLM that generates EYG code is more useful than an LLM that generates Python code, because the EYG code actually runs without the user needing to become a DevOps engineer.

Getting Started with EYG#

EYG is designed for instant gratification. The one-line install command is:

curl -fsSL https://eyg.run/install | bash

After installation, the official website at eyg.run provides documentation, guides, a roadmap, and news. The language has a growing ecosystem with package sharing via unique handles, and the structural editor is available as part of the standard toolchain.

For makers who want to explore EYG, the recommended path is:

  1. Install EYG using the one-line command above
  2. Read the official guides at eyg.run for language basics
  3. Try the structural editor to experience syntax-error-free programming
  4. Build a small automation — connect two APIs, transform some data, or build a personal dashboard
  5. Share your package via EYG’s package sharing system

Verdict — Who Should Try EYG?#

EYG is not for everyone. Professional developers building large-scale applications will find Gleam, Rust, or TypeScript more suitable for their needs. But for the growing population of makers — accountants automating reports, biologists analyzing lab data, operations managers building dashboards, hobbyists creating home-cooked software — EYG represents a genuine leap forward.

The language’s core insight — that most programming complexity comes from “working with computers” rather than “describing logic” — is correct, and EYG’s design systematically eliminates that complexity. The sound structural type system, hashed dependencies, effect typing, and sandboxed execution are not just academic niceties; they are practical features that make software development accessible to people who do not want to become developers.

The biggest risk for EYG is adoption. A new programming language needs libraries, community, tutorials, and real-world success stories to thrive. EYG has the design. Whether it gains the momentum to reach its target audience remains to be seen. But for makers who are tired of fighting Python environments and npm dependency trees, EYG is worth a serious look.

Frequently Asked Questions#

What does EYG stand for?#

EYG stands for “Eat Your Greens,” reflecting the language’s philosophy of accepting constraints now (structural typing, effect management, sandboxed execution) for guarantees later (no runtime crashes, deterministic dependencies, predictable side effects).

How is EYG different from Python for beginners?#

Python requires understanding virtual environments, pip, dependency management, and deployment before shipping anything useful. EYG abstracts all of that away — makers describe logic, and the runtime handles deployment, dependencies, and infrastructure automatically. EYG also provides a sound type system that catches errors at compile time, while Python’s dynamic typing allows runtime crashes.

Does EYG require type annotations?#

No. EYG uses structural row typing with full type inference. The compiler infers all types automatically from how values are used. Programmers never write type annotations, yet the type system is sound — if the program compiles, it will not crash at runtime due to a type error.

What are hashed dependencies in EYG?#

Hashed dependencies identify modules by the cryptographic hash of their contents rather than by version numbers or package names. This means dependencies are immutable, builds are deterministic, supply chain attacks are prevented, and version conflicts are impossible. If a module changes, its hash changes, and the dependency is explicitly broken rather than silently updated.

Can I use EYG for web development?#

EYG is designed for glue problems, automations, personal dashboards, and data transformation — not for building large-scale web applications. However, EYG programs can perform HTTP requests, interact with databases, and run scheduled tasks, making them suitable for backend automation and API integration. The runtime handles deployment automatically, so EYG programs can run as cloud services without manual infrastructure setup.
