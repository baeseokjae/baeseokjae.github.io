How to Build and Self-Host a Code Review Agent: Complete Guide

Learn how to build and self-host a code review agent using Ollama, Gitea, or GitLab. Complete guide with Docker Compose setup, cost analysis, and open-source tools.

A self-host code review agent is an AI-powered system that automatically reviews pull requests and merge requests on your own infrastructure, using local or private-cloud LLMs instead of third-party SaaS services. You build it by combining an open-source LLM (like CodeLlama or DeepSeek Coder), a webhook handler that listens for PR events, and a version control system integration (Gitea, GitLab, or GitHub) that posts review comments back to the pull request — all running in Docker containers on your own servers with no data leaving your network.

Why Self-Host a Code Review Agent?#

The shift toward AI-assisted development has been dramatic. By 2026, 84% of developers regularly use AI coding tools, and AI-assisted development accounts for roughly 40% of all committed code. With 82 million pushes and 43 million merged pull requests happening every month, human review capacity has become the critical bottleneck. Self-hosting a code review agent addresses three fundamental concerns: privacy, cost, and control.

Privacy and Compliance#

When you use SaaS code review tools like CodeRabbit or Greptile, your proprietary source code is sent to external servers for analysis. For companies operating under SOC 2, HIPAA, FedRAMP, or GDPR requirements, this is often a non-starter. A self-host code review agent keeps every line of code on your own infrastructure. The LLM runs locally via Ollama or vLLM, the webhook handler processes diffs on your server, and no data ever crosses your network boundary. This is especially critical for fintech, healthcare, defense, and enterprise SaaS companies where source code is the crown jewel.

Upsun’s custom GitLab agent, for example, processed approximately 1,000 merge requests at roughly $0.50 per review — a fraction of what SaaS tools would charge for equivalent volume.

Full Control and Custom Integration#

SaaS code review tools operate as black boxes. You cannot customize the review criteria, integrate with internal issue trackers like Linear or Jira, or add project-specific rules. A self-host code review agent gives you complete control over the prompt, the model, the review standards, and the integration points. You can make it aware of your codebase conventions, enforce internal style guides, and even connect it to your deployment pipeline for pre-merge validation.

Architecture Overview#

Before diving into implementation, it helps to understand the core architecture of a self-hosted code review agent.

Core Components: LLM, Webhook Handler, VCS Integration#

Every self-host code review agent consists of three main components:

  1. LLM Server — Runs the language model that performs the actual code review. Options include Ollama (easiest for local models), vLLM (best for GPU-optimized serving), or llama.cpp (for CPU-only deployments).

  2. Webhook Handler — A lightweight service (Flask, FastAPI, or Node.js) that listens for pull request events from your version control system, fetches the diff, constructs a review prompt, calls the LLM, and posts the results.

  3. VCS Integration — The connection to your version control platform. Gitea, GitLab, and GitHub all support webhooks that fire on PR/MR events, and all three have APIs for posting review comments.

Data Flow: PR Event → Review → Comment#

The data flow follows a simple pipeline:

  1. A developer opens or updates a pull request
  2. Your VCS platform sends a webhook payload to your review bot
  3. The bot fetches the PR diff via the VCS API
  4. The bot constructs a structured prompt with the diff, coding standards, and review instructions
  5. The prompt is sent to the local LLM (Ollama/vLLM)
  6. The LLM returns review comments, suggestions, and potential issues
  7. The bot posts the review as inline comments or a summary on the PR
  8. The entire process completes in 30-90 seconds depending on model and diff size

Recommended Models: CodeLlama, DeepSeek Coder, Qwen Coder#

Three model families stand out for code review:

  • CodeLlama (Meta) — The original specialized code model. CodeLlama 13B offers the best balance of quality and resource usage. It understands multiple programming languages and catches logic errors, security vulnerabilities, and style violations effectively.

  • DeepSeek Coder (DeepSeek) — Trained on a massive corpus of code and natural language. The 6.7B model punches above its weight, rivaling larger models in code understanding. The 33B version approaches GPT-4 quality for code review tasks.

  • Qwen2.5 Coder (Alibaba) — The newest entrant, with strong performance on code generation and understanding. The 7B model is excellent for CPU deployments, and the 32B version competes with the best open-source code models.

All three support 4-bit and 8-bit quantization, which reduces memory requirements by 50-75% with minimal quality loss.

Option 1: Ollama + Gitea (Full Self-Hosted Stack)#

This is the most accessible path to a self-host code review agent. Gitea is a lightweight, self-hosted Git service that runs in under 100 MB of RAM, and Ollama makes running local LLMs trivial.

Docker Compose Setup#

Create a docker-compose.yml file:

version: "3.8"
services:
  gitea:
    image: gitea/gitea:latest
    ports:
      - "3000:3000"
      - "22:22"
    volumes:
      - ./gitea-data:/data
    environment:
      - USER_UID=1000
      - USER_GID=1000

  ollama:
    image: ollama/ollama:latest
    ports:
      - "11434:11434"
    volumes:
      - ./ollama-models:/root/.ollama
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]

  review-bot:
    build: ./review-bot
    ports:
      - "5000:5000"
    environment:
      - OLLAMA_URL=http://ollama:11434
      - GITEA_URL=http://gitea:3000
      - GITEA_TOKEN=your_gitea_token
      - MODEL=codellama:13b
    depends_on:
      - gitea
      - ollama

Pull the model before running:

docker compose run ollama ollama pull codellama:13b
docker compose up -d

Building the Review Bot (Flask/Python)#

The review bot is a simple Flask application that handles webhooks and performs reviews. Here is a minimal implementation:

from flask import Flask, request, jsonify
import requests
import json
import os

app = Flask(__name__)

OLLAMA_URL = os.getenv("OLLAMA_URL", "http://ollama:11434")
GITEA_URL = os.getenv("GITEA_URL", "http://gitea:3000")
GITEA_TOKEN = os.getenv("GITEA_TOKEN")
MODEL = os.getenv("MODEL", "codellama:13b")

@app.route("/webhook", methods=["POST"])
def webhook():
    data = request.json
    if data.get("action") not in ("opened", "synchronize"):
        return jsonify({"status": "ignored"}), 200

    pr = data.get("pull_request", {})
    repo = data.get("repository", {})
    repo_full = repo.get("full_name", "")
    pr_number = pr.get("number")
    head_sha = pr.get("head", {}).get("sha", "")

    # Fetch the diff
    diff_url = f"{GITEA_URL}/api/v1/repos/{repo_full}/pulls/{pr_number}.diff"
    headers = {"Authorization": f"token {GITEA_TOKEN}"}
    diff_resp = requests.get(diff_url, headers=headers)
    diff = diff_resp.text

    # Construct review prompt
    prompt = f"""You are an expert code reviewer. Review the following diff and provide:
1. Potential bugs or logic errors
2. Security vulnerabilities
3. Performance issues
4. Code style improvements
5. Best practice suggestions

Diff:
{diff[:8000]}

Provide your review as a structured list of issues with severity levels."""

    # Call Ollama
    ollama_resp = requests.post(
        f"{OLLAMA_URL}/api/generate",
        json={"model": MODEL, "prompt": prompt, "stream": False}
    )
    review = ollama_resp.json().get("response", "")

    # Post review as PR comment
    comment_url = f"{GITEA_URL}/api/v1/repos/{repo_full}/pulls/{pr_number}/comments"
    comment_data = {"body": review}
    requests.post(comment_url, headers=headers, json=comment_data)

    return jsonify({"status": "reviewed"}), 200

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)

Webhook Configuration#

In Gitea, navigate to your repository → Settings → Webhooks → Add Webhook. Set the target URL to http://your-server:5000/webhook, select “Pull Request” events, and save. Every new PR or update will now trigger an automatic review.

Option 2: Ollama + GitLab (Enterprise Self-Hosted)#

For organizations already running GitLab, the integration is similar but offers more advanced capabilities.

GitLab Webhook Integration#

GitLab’s webhook system is more granular than Gitea’s. You can filter for specific merge request events and even set up push-based triggers for incremental reviews. The webhook payload includes the full MR metadata, diff statistics, and labels, which your bot can use to prioritize reviews.

Context-Aware Review with Codebase Search#

One advantage of GitLab integration is the ability to perform context-aware reviews. Instead of reviewing a diff in isolation, your bot can:

  1. Clone the repository or use the GitLab API to fetch related files
  2. Search for similar patterns in the existing codebase
  3. Check if the PR introduces patterns that conflict with established conventions
  4. Reference related issues and discussions

Upsun’s custom agent took this further by integrating with Linear for issue tracking and performing web searches for dependency vulnerability information. This level of context awareness catches issues that a simple diff review would miss — such as inconsistent API usage across modules or architectural drift.

Option 3: GPU Cloud Deployment with vLLM#

For teams that need high throughput or want to run larger models (33B+ parameters), GPU cloud deployment with vLLM is the best approach.

Model Serving with vLLM#

vLLM is a high-performance inference engine that achieves 2-4x higher throughput than Ollama for GPU deployments. Deploy it on a GPU cloud instance:

# Install vLLM
pip install vllm

# Start the server with DeepSeek Coder 33B
python -m vllm.entrypoints.openai.api_server \
    --model deepseek-ai/deepseek-coder-33b-instruct \
    --tensor-parallel-size 1 \
    --gpu-memory-utilization 0.9 \
    --port 8000

Your review bot then uses the OpenAI-compatible API:

import openai
client = openai.OpenAI(base_url="http://localhost:8000/v1", api_key="none")

response = client.chat.completions.create(
    model="deepseek-ai/deepseek-coder-33b-instruct",
    messages=[{"role": "user", "content": review_prompt}]
)

Scaling for Multiple Repositories#

With vLLM, a single GPU can handle reviews for dozens of repositories simultaneously. The key is to implement a queue system that batches review requests and processes them without overwhelming the model. Using a message queue like Redis or RabbitMQ between your webhook handler and the review worker allows you to scale horizontally — add more GPU instances and route requests to the least-loaded server.

Building the Review Bot Step by Step#

Regardless of which platform you choose, the review bot follows the same core logic.

Fetching PR Diffs#

Every VCS platform provides a way to fetch the diff of a pull request. The diff is the raw input to your review agent. For large PRs, you may want to truncate or chunk the diff to fit within the LLM’s context window. A good rule of thumb is to limit the diff to 8,000 tokens for 7B models and up to 16,000 tokens for 33B+ models.

Constructing the Review Prompt#

The prompt is the most important part of your self-host code review agent. A well-structured prompt produces useful, actionable reviews. Here is a proven template:

You are reviewing a pull request for a {language} project.

Review Guidelines:
- Check for logic errors and edge cases
- Identify security vulnerabilities (SQL injection, XSS, auth bypass)
- Flag performance issues (N+1 queries, unnecessary allocations)
- Suggest idiomatic improvements
- Verify error handling is complete

Project Conventions:
- Use async/await for I/O operations
- All public functions must have type hints
- Error messages must be user-facing and localized

Diff:
{diff}

Provide your review as a markdown list with severity: [CRITICAL], [WARNING], [SUGGESTION]

Calling the LLM#

The call to the LLM is straightforward with Ollama’s API or vLLM’s OpenAI-compatible endpoint. Set temperature to 0.1-0.3 for consistent, deterministic reviews. Higher temperatures produce more creative but less reliable feedback.

Posting Review Comments via API#

Each VCS platform has its own API for posting review comments:

  • Gitea: POST /api/v1/repos/{owner}/{repo}/pulls/{index}/comments
  • GitLab: POST /api/v4/projects/{id}/merge_requests/{iid}/notes
  • GitHub: POST /repos/{owner}/{repo}/pulls/{number}/comments

For inline comments (comments on specific lines of code), you need to parse the diff line numbers and map them to the PR’s file positions. This is more complex but provides a much better developer experience than a summary comment.

Advanced Features#

Once you have a basic self-host code review agent running, you can extend it with advanced capabilities.

Context-Aware Reviews (Codebase Search)#

A simple diff review misses architectural issues. By integrating codebase search, your agent can:

  • Check if new code follows existing patterns
  • Detect duplicate implementations
  • Verify that API changes are consistent across all callers
  • Flag when a PR introduces a dependency that conflicts with project standards

Tools like ripgrep, CodeQL, or a simple vector embedding search over your codebase can provide this context.

Integration with Issue Trackers (Linear, Jira)#

Connect your review agent to your issue tracker so it can:

  • Reference related tickets in review comments
  • Check if the PR addresses all requirements in the linked issue
  • Automatically update ticket status when a PR is reviewed
  • Flag PRs that lack proper issue references

Custom Review Standards Per Project#

Different projects have different standards. Store per-project review rules in a configuration file or database:

# review-rules.yaml
project: backend-api
language: python
rules:
  - "All database queries must use parameterized statements"
  - "No print() statements — use logging"
  - "Every endpoint must have OpenAPI documentation"
  - "Test coverage must be >= 80% for new code"

The review bot loads these rules and includes them in the prompt, ensuring reviews are tailored to each project’s specific requirements.

Inline Code Comments vs Summary Reviews#

There are two approaches to delivering review feedback:

  • Summary reviews — A single comment on the PR with all findings. Simple to implement and works well for small PRs.
  • Inline comments — Comments on specific lines of code. More useful for developers but requires parsing the diff to map line numbers. Most teams prefer inline comments for actionable feedback and summary comments for general observations.

Open-Source Tools and Frameworks#

You do not have to build everything from scratch. Several open-source projects provide ready-made foundations for a self-host code review agent.

Codesteward — Agentic Code Review with Graph Intelligence#

Codesteward is an open-source agentic code review tool that uses graph-based code analysis. It builds a dependency graph of your codebase and uses it to understand the impact of changes across modules. This allows it to catch issues that a simple diff review would miss, such as breaking changes in shared interfaces or cascading effects of API modifications.

SuperscriptSystems/codereview-agent#

This open-source project provides a complete code review agent with support for GitHub, GitLab, and Gitea. It includes a web dashboard for reviewing review history, configurable review rules, and support for multiple LLM backends including Ollama, OpenAI, and Anthropic. It is a good starting point if you want a production-ready system with minimal customization.

Wolli Agent Framework#

Wolli is an npm-based agent framework that makes it easy to build code review agents. It provides built-in tools for Git operations, file system access, and LLM integration. The framework handles the boilerplate of PR detection, diff fetching, and comment posting, letting you focus on the review logic. It can be set up in under 30 minutes and supports both polling and webhook-based PR detection.

Cost Analysis and Optimization#

Running a self-host code review agent involves ongoing infrastructure costs. Here is how to optimize them.

GPU Cloud Spot Pricing#

GPU cloud providers offer significant discounts for spot (preemptible) instances. An H100 SXM5 at $1.49/hour spot pricing costs approximately $1,154/month — compared to $3.50+/hour on-demand. For code review workloads, which are asynchronous and can tolerate brief interruptions, spot instances are ideal. Configure your review queue to retry failed reviews when a spot instance is preempted.

Model Quantization for Lower Resource Usage#

Quantization reduces model size and speeds up inference with minimal quality loss:

QuantizationModel SizeQuality LossSpeed Gain
FP16 (none)100%None1x
INT8 (8-bit)50%Negligible1.5-2x
INT4 (4-bit)25%Minimal2-3x
GGUF Q4_K_M30%Minimal2-3x

For code review, INT4 quantization works well. The structured nature of code review means the model does not need the precision required for creative tasks. A quantized 13B model runs comfortably on 8 GB of RAM.

Caching and Deduplication Strategies#

Avoid re-reviewing the same diff. Cache review results keyed by commit SHA. If a developer pushes the same code to a different branch or reopens a PR, the cached review can be returned instantly. This is especially valuable for large monorepos where the same files may be reviewed across multiple PRs.

Security Considerations#

Running a self-host code review agent introduces security considerations that you must address.

Network Isolation#

Run your review bot and LLM on an isolated network segment. The webhook handler should be the only service exposed to the VCS platform. The LLM server should not be directly accessible from outside your network. Use Docker networks to isolate services:

networks:
  review-net:
    internal: true
  webhook-net:
    external: true

Token and Secret Management#

Your review bot needs API tokens for the VCS platform and potentially for the LLM server. Store these in environment variables or a secrets manager — never in the codebase. Use Docker secrets or HashiCorp Vault for production deployments. Rotate tokens regularly and audit token usage.

Audit Logging#

Log every review request, including the PR identifier, the model used, the review duration, and any errors. This audit trail is essential for compliance and for debugging review quality issues. Store logs in a centralized logging system with appropriate retention policies.

Conclusion and Next Steps#

Building a self-host code review agent is a practical, cost-effective alternative to SaaS code review tools. With open-source models like CodeLlama, DeepSeek Coder, and Qwen2.5 Coder, and platforms like Ollama and vLLM, you can have a working system in an afternoon. The key benefits — data privacy, cost control, and full customization — make it compelling for any organization that takes code quality seriously.

Start with the Ollama + Gitea option for the simplest path, then graduate to GitLab integration and GPU cloud deployment as your needs grow. The open-source ecosystem around code review agents is maturing rapidly, and the tools available today are production-ready for teams of any size.

Frequently Asked Questions#

What is a self-host code review agent? A self-host code review agent is an AI system that automatically reviews pull requests on your own infrastructure using local LLMs. It listens for PR events via webhooks, fetches the diff, sends it to a locally running model for analysis, and posts review comments back to the PR — all without sending your code to external services.

How much does it cost to self-host a code review agent? For a small team, the cost is essentially the server hardware you already have — a 7B parameter model runs on CPU with 8 GB RAM. For larger teams, a GPU cloud instance costs approximately $1,154/month (H100 spot pricing), which covers unlimited repositories and reviews for 50+ engineers — comparable to CodeRabbit Pro at $1,200/month for the same team size.

Which LLM is best for code review? CodeLlama 13B offers the best balance of quality and resource usage for most teams. DeepSeek Coder 6.7B punches above its weight for CPU deployments. For maximum quality, DeepSeek Coder 33B or Qwen2.5 Coder 32B approach GPT-4 level performance but require a GPU.

Can I run a code review agent without a GPU? Yes. Models with 7B parameters or less run on CPU with acceptable performance for small teams (10-30 PRs per day). Reviews take 1-2 minutes. Quantized models (GGUF format) reduce memory requirements further. For higher throughput, add a single GPU.

How does self-hosted code review compare to CodeRabbit? Self-hosted solutions offer complete data privacy, unlimited repositories, custom review rules, and any open-source model you choose. CodeRabbit provides a polished SaaS experience with no infrastructure management. At 50+ engineers, the costs are comparable, but self-hosting gives you full control over your code and review pipeline.
