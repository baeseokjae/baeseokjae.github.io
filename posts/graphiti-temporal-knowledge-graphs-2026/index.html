Graphiti is an open-source temporal knowledge graph framework by Zep that gives AI agents persistent, time-aware memory. Unlike static retrieval-augmented generation (RAG) systems that treat all information as equally current, Graphiti tracks when facts are valid, automatically invalidates outdated information, and enables agents to reason across time. With 29,000 GitHub stars, Apache-2.0 licensing, and benchmark scores of 94.8% on the DMR evaluation, it has become the leading open-source solution for agent memory infrastructure.

What Is Graphiti? An Open-Source Temporal Context Graph Framework#

Graphiti is a Python-based, open-source framework designed specifically for building temporal knowledge graphs that serve as long-term memory for AI agents. Developed and maintained by Zep, Graphiti addresses a fundamental gap in the AI agent ecosystem: the inability of most systems to remember what changed and when.

At its core, Graphiti represents information as a graph of entities and relationships, where every fact carries a temporal validity window. When an agent learns something new, Graphiti adds it to the graph. When a fact becomes outdated — for example, a person changes jobs or a company relocates — Graphiti automatically invalidates the old fact and records the new one, preserving the full history.

The framework supports four graph database backends: Neo4j, FalkorDB, Amazon Neptune, and Kuzu. It integrates with major LLM providers including OpenAI, Anthropic, Gemini, and Groq, and offers a REST API built on FastAPI for easy deployment. Graphiti also ships with an MCP (Model Context Protocol) server, enabling direct integration with Claude, Cursor, and other MCP-compatible AI tools.

Why Temporal Knowledge Graphs Matter for AI Agents#

Traditional RAG systems retrieve information from a static vector store. They work well for answering questions about fixed knowledge — documentation, reference materials, or historical facts. But they fail when information changes over time. A RAG system cannot distinguish between “the CEO of Acme Corp is Jane Doe” (current) and “the CEO of Acme Corp was John Smith” (outdated). Both statements exist as vectors in the embedding space, and the system has no mechanism to prefer one over the other.

This is a critical limitation for AI agents that operate in dynamic environments. Enterprise AI assistants need to track changing project statuses, evolving customer relationships, shifting organizational structures, and time-sensitive compliance data. Without temporal awareness, agents either hallucinate outdated information or require expensive full-context-window approaches that do not scale.

Graphiti solves this with three core capabilities:

  • Temporal fact management: Every fact has a validity window with a start and end date. Queries automatically filter for facts that were true at the relevant time.
  • Automatic fact invalidation: When new information contradicts existing facts, Graphiti marks the old facts as expired and adds the new ones, maintaining a complete audit trail.
  • Cross-session reasoning: Agents can synthesize information from multiple conversations, understanding how facts evolved over time.

The result is an agent memory system that behaves more like human memory — it knows not just what you told it, but when you told it, and whether that information is still relevant.

Key Features Deep Dive#

Temporal Fact Management#

Every piece of information in Graphiti is stored as a triple — subject, relationship, object — with temporal metadata. A fact like “Acme Corp acquired StartupX” is stored with a valid_at timestamp. If Acme later divests StartupX, the original fact is marked as expired and the new fact is recorded. Queries can target specific time windows or ask “what was true at the time of the last conversation.”

This temporal layer is what separates Graphiti from every static knowledge graph solution. It enables agents to answer questions like “What did the customer say about pricing in our last three meetings?” or “Has the project timeline changed since last week?” — queries that are impossible for traditional RAG systems.

Episodes and Provenance#

Graphiti organizes information into episodes — discrete units of interaction or observation. Each episode captures a complete snapshot of what the agent learned during a specific session or event. Every fact in the graph is linked back to the episode where it was first recorded, providing full provenance.

This provenance chain is invaluable for debugging and auditability. When an agent makes a decision based on a fact, developers can trace that fact back to its source episode, understand the context in which it was learned, and verify its accuracy. In regulated industries like finance and healthcare, this audit trail is not just useful — it is often a compliance requirement.

Prescribed and Learned Ontology#

Graphiti supports two modes of ontology management. In prescribed ontology mode, developers define the entity types and relationship schemas upfront, ensuring strict consistency. In learned ontology mode, Graphiti uses LLMs to dynamically discover entity types and relationships from unstructured data, adapting the graph schema as new information arrives.

This dual-mode approach is powerful because it accommodates both structured enterprise environments where schemas must be controlled and exploratory AI applications where the data landscape is unknown at design time. Many production deployments use a hybrid approach: a prescribed core ontology for critical entities with learned extensions for ad-hoc information.

Incremental Graph Construction#

Rather than rebuilding the entire graph on each update, Graphiti performs incremental graph construction. When new information arrives, the system identifies which parts of the graph are affected, updates only those nodes and edges, and propagates changes through connected relationships. This approach keeps update latency low and enables real-time ingestion of streaming data.

The incremental construction algorithm uses LLM calls to extract entities and relationships from new text, then merges them into the existing graph structure. The system handles entity resolution — recognizing that “Acme Corp” and “Acme Corporation” refer to the same entity — and relationship deduplication automatically.

Hybrid Retrieval: Semantic + BM25 + Graph Traversal#

Graphiti’s retrieval pipeline combines three complementary approaches:

  1. Semantic search: Embedding-based similarity search over entity descriptions and fact text, capturing semantic meaning.
  2. BM25 keyword search: Traditional term-frequency-based retrieval for exact matches and technical terminology.
  3. Graph traversal: Following relationships through the graph to discover connected facts that may not be semantically similar but are contextually relevant.

This hybrid approach consistently outperforms any single retrieval method. The graph traversal component is particularly powerful for agent memory because it enables serendipitous discovery — finding relevant information through relationship chains rather than keyword or semantic similarity alone. Search results return in under 100 milliseconds, with the primary latency contribution coming from embedding API calls.

The most common question developers ask is how Graphiti compares to Microsoft’s GraphRAG. While both use graph structures to enhance LLM retrieval, they serve fundamentally different purposes.

The key takeaway: Graphiti and GraphRAG are complementary, not competitive. GraphRAG excels at extracting insights from large static document collections — think legal document review, academic literature analysis, or enterprise knowledge base mining. Graphiti excels at maintaining up-to-date, temporally aware memory for interactive AI agents — think customer support bots that remember past interactions, personal assistants that track changing preferences, or enterprise agents that monitor evolving project statuses.

If your use case involves information that changes over time and requires an agent to remember what happened when, Graphiti is the right choice. If you need to analyze a large, static corpus and generate structured insights, GraphRAG is the better fit.

Benchmarks and Performance#

Graphiti’s performance has been rigorously evaluated in Zep’s peer-reviewed paper, “A Temporal Knowledge Graph Architecture for Agent Memory” (arXiv:2501.13956). The results demonstrate state-of-the-art performance across multiple benchmarks.

DMR Benchmark: 94.8% Accuracy#

The Dialog Memory Reasoning (DMR) benchmark evaluates how well agent memory systems can recall and reason about information from past conversations. Graphiti achieves 94.8% accuracy, outperforming MemGPT (Letta AI) at 93.4%. This 1.4 percentage point improvement represents a meaningful reduction in memory-related errors for production AI agents.

LongMemEval: Up to 18.5% Improvement#

LongMemEval tests an agent’s ability to perform complex temporal reasoning and synthesize information across multiple sessions. Graphiti demonstrates up to 18.5% accuracy improvement over baseline approaches on enterprise-specific tasks. This benchmark is particularly relevant for real-world deployments because it simulates the cross-session reasoning that enterprise AI assistants must perform daily.

Response Latency: 90% Reduction#

Compared to full-context-window baselines — where the entire conversation history is fed into the LLM prompt — Graphiti achieves a 90% reduction in response latency. Instead of processing thousands of tokens of history for every query, Graphiti retrieves only the relevant facts from the knowledge graph, dramatically reducing both cost and response time.

Search Performance: Sub-100ms#

Graphiti’s hybrid retrieval pipeline returns search results in under 100 milliseconds. The primary latency contributor is the embedding API call for semantic search; the graph traversal and BM25 components add negligible overhead. This makes Graphiti suitable for real-time agent interactions where users expect sub-second responses.

Getting Started with Graphiti#

Installation#

Graphiti is available via pip and works with Python 3.10 or later:

pip install graphiti-core

Supported Graph Backends#

Graphiti supports four graph database backends, giving you flexibility based on your infrastructure and scale requirements:

  • Neo4j: The most popular graph database, ideal for production deployments with rich querying needs
  • FalkorDB: High-performance graph database optimized for low-latency operations
  • Amazon Neptune: Fully managed graph database service on AWS, suitable for enterprise cloud deployments
  • Kuzu: Embedded graph database for development and small-scale deployments

Quickstart Example#

The fastest way to get started is with Docker Compose using Neo4j:

# Clone the repository
git clone https://github.com/getzep/graphiti.git
cd graphiti

# Start with Docker Compose
docker compose up -d

# Install Python dependencies
pip install graphiti-core

Once running, you can create a Graphiti client and start adding facts:

from graphiti import Graphiti

client = Graphiti(
    uri="bolt://localhost:7687",
    user="neo4j",
    password="password"
)

# Add a fact with temporal context
client.add_fact(
    subject="Acme Corp",
    relationship="acquired",
    obj="StartupX",
    valid_at="2026-01-15"
)

# Query current facts
results = client.query("What companies did Acme Corp acquire?")

MCP Server Integration#

One of Graphiti’s most powerful features is its MCP (Model Context Protocol) server. The MCP server acts as a bridge between AI agents and the temporal knowledge graph, enabling persistent memory across sessions.

How It Works#

The MCP server exposes Graphiti’s capabilities as a set of tools that MCP-compatible clients can call. When an AI agent like Claude or Cursor needs to remember information from a previous interaction, it queries the MCP server instead of relying on its limited context window.

The server provides tools for:

  • Adding facts: Storing new information with temporal context
  • Querying facts: Retrieving relevant information based on current context
  • Updating facts: Invalidating outdated information and recording changes
  • Searching across episodes: Finding information from specific time periods or conversations

Supported Clients#

Graphiti’s MCP server works with any MCP-compatible client, including:

  • Claude Desktop: Claude can maintain persistent memory across conversations, remembering user preferences, project details, and ongoing tasks
  • Cursor: The AI-powered code editor can remember codebase context, coding conventions, and project history across sessions
  • Custom MCP clients: Any application implementing the MCP protocol can leverage Graphiti for persistent memory

This integration transforms AI agents from stateless query responders into systems that build and maintain context over time, much like a human collaborator who remembers the history of a project.

Production Deployment#

Docker Compose Setup#

For production deployments, Graphiti provides a Docker Compose configuration that includes the Graphiti service, your chosen graph database, and supporting infrastructure:

version: '3.8'
services:
  graphiti:
    image: zep/graphiti:latest
    ports:
      - "8080:8080"
    environment:
      - GRAPH_DATABASE_URL=bolt://neo4j:7687
      - LLM_PROVIDER=openai
      - OPENAI_API_KEY=${OPENAI_API_KEY}
    depends_on:
      - neo4j

  neo4j:
    image: neo4j:5
    environment:
      - NEO4J_AUTH=neo4j/password
    volumes:
      - neo4j_data:/data

volumes:
  neo4j_data:

REST API#

Graphiti’s FastAPI-based REST API provides endpoints for all core operations:

  • POST /facts — Add a new fact with temporal metadata
  • GET /facts/{id} — Retrieve a specific fact with its history
  • POST /search — Hybrid search across the knowledge graph
  • POST /episodes — Create a new episode
  • GET /episodes/{id} — Retrieve episode details with provenance

Scalability Considerations#

Graphiti is designed for horizontal scalability. The graph database backends handle data distribution, while the Graphiti service layer is stateless and can be scaled independently. For high-throughput deployments, consider:

  • Using Amazon Neptune or a clustered Neo4j deployment for the graph backend
  • Scaling the Graphiti REST API behind a load balancer
  • Caching frequent queries at the application layer
  • Monitoring embedding API latency, which is typically the bottleneck

The Future of Agent Memory#

Graphiti represents a fundamental shift in how AI agents handle memory. The trajectory is clear: agents are moving from stateless, session-bound interactions to persistent, context-aware systems that build understanding over time.

Several trends point to Graphiti’s growing importance:

  • Multi-agent systems: As organizations deploy fleets of AI agents, shared temporal knowledge graphs will enable agents to coordinate, share context, and avoid duplicating work
  • Regulatory compliance: Industries subject to data retention and audit requirements will need temporal fact management to demonstrate what an agent knew and when
  • Personal AI assistants: Consumer-facing AI assistants require persistent memory to be genuinely useful — remembering user preferences, past conversations, and evolving needs
  • Enterprise knowledge management: Organizations are recognizing that static knowledge bases are insufficient for dynamic business environments

Graphiti’s open-source foundation, strong benchmark performance, and growing ecosystem position it as the leading infrastructure layer for this transition. As LLMs continue to improve, the bottleneck for agent capabilities will increasingly be memory and context management — precisely the problem Graphiti was built to solve.

Frequently Asked Questions#

What makes Graphiti different from a regular vector database?#

Vector databases store embeddings and retrieve semantically similar content, but they have no concept of time or fact validity. Graphiti stores structured facts with temporal metadata, enabling queries like “what was true at this point in time” and automatically invalidating outdated information. Vector databases are a component of Graphiti’s hybrid retrieval pipeline, not a replacement for it.

Can I use Graphiti without Neo4j?#

Yes. Graphiti supports four graph database backends: Neo4j, FalkorDB, Amazon Neptune, and Kuzu. Kuzu is an embedded graph database that requires no separate server, making it ideal for development and testing. FalkorDB offers lower latency for high-throughput scenarios, and Amazon Neptune provides a fully managed cloud experience.

Does Graphiti work with any LLM provider?#

Graphiti integrates with OpenAI, Anthropic (Claude), Google Gemini, and Groq for entity extraction, relationship discovery, and query understanding. The framework’s LLM abstraction layer makes it straightforward to add custom providers. The graph operations themselves — storage, retrieval, traversal — are LLM-agnostic and run entirely on the graph database backend.

How does Graphiti handle fact conflicts?#

When new information contradicts existing facts, Graphiti does not overwrite the old data. Instead, it marks the existing fact as expired by setting its validity end date, then adds the new fact with a fresh validity window starting from the current time. This preserves the complete history and enables temporal queries that can ask “what did we believe at any point in time.”

Is Graphiti suitable for production use?#

Yes. Graphiti powers Zep’s production agent memory infrastructure and has been deployed in enterprise environments since 2024. It offers Docker Compose deployment, a FastAPI REST API, support for production-grade graph databases like Neo4j and Amazon Neptune, and horizontal scalability. The Apache-2.0 license allows unrestricted commercial use, and the active community provides ongoing support and development.
