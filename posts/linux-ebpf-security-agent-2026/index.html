Introduction — Why eBPF for Runtime Security?#

Traditional Linux security agents rely on kernel modules, auditd, or userspace polling — each with significant trade-offs. Kernel modules can crash the kernel and require maintenance across kernel versions. Auditd generates massive log volumes and imposes high CPU overhead. Userspace polling misses events between sampling intervals. The extended Berkeley Packet Filter (eBPF) solves all three problems by providing a safe, programmable, and high-performance sandbox within the Linux kernel. An eBPF-based security agent can inspect every system call, monitor file access, track process execution, and enforce network policy — all with deterministic overhead under one microsecond per event and without loading a single kernel module. This guide walks through the complete architecture of a Linux eBPF security agent, from kernel-level program design to production deployment.

Understanding eBPF Architecture for Security#

eBPF Program Types Relevant to Security (kprobe, tracepoint, LSM, XDP)#

eBPF offers several program types, each suited to different security monitoring surfaces:

For a comprehensive security agent, you will typically attach programs to multiple hook points simultaneously. The LSM program type, added in kernel 5.7, is particularly powerful — it allows eBPF to enforce mandatory access control policies that cannot be bypassed by userspace processes, even by root.

The eBPF Verifier and Safety Guarantees#

Every eBPF program passes through a strict verifier before it is loaded into the kernel. The verifier performs a static analysis that guarantees:

  • Termination: The program contains no infinite loops (or bounded loops with a verified upper bound since kernel 5.3).
  • Memory safety: All memory accesses are bounds-checked. The verifier tracks register states across every possible execution path.
  • No kernel crashes: The program cannot dereference arbitrary kernel memory or call unsafe kernel functions.
  • Limited instruction count: Programs are capped at 1 million instructions (raised from 4096 in kernel 5.2).

These guarantees mean that a bug in your eBPF security agent will cause the program to be rejected by the verifier or safely unloaded — it will never panic the kernel. This is the fundamental advantage over kernel modules, where a single null pointer dereference can take down the entire system.

Maps, Ring Buffers, and Event Delivery#

eBPF programs run in kernel context and cannot write to files, make network calls, or allocate memory dynamically. Instead, they communicate with userspace through data structures called BPF maps:

  • Hash maps: Key-value stores for tracking state (e.g., process whitelists, connection tracking tables).
  • Per-CPU arrays: Lock-free counters for performance metrics.
  • Ring buffers (BPF ringbuf): The recommended mechanism for streaming security events to userspace. Introduced in kernel 5.8, ringbuf is per-CPU and reservation-based, offering better performance and ordering guarantees than the older perf buffer.
  • Perf event arrays (BPF perfbuf): Legacy event delivery mechanism, still widely used but being replaced by ringbuf.

A typical security agent pipeline works as follows: an eBPF program attached to a tracepoint or kprobe captures an event, enriches it with context (PID, UID, command name), writes it into a ring buffer, and a lightweight userspace daemon reads the buffer, enriches the event with container metadata, and forwards it to a processing pipeline.

Core Security Monitoring Capabilities with eBPF#

System Call Monitoring and Anomaly Detection#

Syscall monitoring is the foundation of runtime security. By attaching tracepoints to sys_enter_* and sys_exit_* hooks, an eBPF agent can observe every system call made by every process on the system. The key syscalls to monitor for security include:

  • execve/execveat: Process execution — detect unauthorized binaries, reverse shells, and container escapes.
  • openat/creat: File access — monitor sensitive file reads and writes.
  • connect/bind/sendto: Network connections — detect beaconing to command-and-control servers.
  • ptrace: Debugging operations — detect process injection attempts.
  • mount/umount: Filesystem operations — detect container escape via host mount.
  • setuid/setgid/capset: Privilege escalation attempts.

The eBPF program captures the syscall arguments, the calling process PID, and the UID, then emits this data to a ring buffer. The userspace agent applies rules — for example, alerting when a container process calls mount or when a non-root process calls ptrace on a process in a different container.

File Integrity Monitoring at Kernel Level#

Traditional file integrity monitoring (FIM) tools like AIDE or Tripwire scan files on a schedule, creating windows where changes go undetected. eBPF-based FIM is event-driven: every openat, write, rename, and unlink syscall is captured in real time.

A practical eBPF FIM program monitors security_file_open LSM hook or the sys_enter_openat tracepoint, checks the file path against a monitored path list (stored in a BPF hash map), and emits an event when a protected file is accessed. The userspace agent can then compute a hash of the modified file and compare it against a known-good baseline.

This approach detects ransomware encryption in real time — before the encryption completes. SentinelOne reports detecting and stopping ransomware in under one second using eBPF-based file monitoring (eBPF Foundation 2026 Report).

Process Execution and Tree Tracking#

Tracking process ancestry is critical for detecting supply chain attacks and lateral movement. An eBPF agent can attach to sys_enter_execve and capture the full process lineage: parent PID, child PID, executable path, command-line arguments, and environment variables.

By maintaining a process tree in a BPF hash map, the agent can answer questions like:

  • Did a web server spawn a shell? (Common webshell attack pattern)
  • Did a container process execute a binary that was not part of the original image?
  • Is there an unexpected parent-child relationship (e.g., a network daemon spawning a compiler)?

The eBPF Foundation 2026 report notes that GitHub uses eBPF to block circular dependency deploy scripts — a process execution monitoring pattern that prevents build pipeline abuse.

Network Security with XDP and Socket Filters#

XDP (eXpress Data Path) attaches eBPF programs to the earliest point in the network stack — the network driver’s receive queue. This allows packet inspection and filtering at line rate, before any kernel networking overhead. Security use cases include:

  • DDoS mitigation: Cloudflare mitigates DDoS attacks peaking above 7 Tbps using eBPF-based XDP programs (eBPF Foundation 2026 Report).
  • Container network isolation: Cilium uses XDP and tc (traffic control) eBPF programs to enforce Kubernetes network policies without iptables.
  • DNS monitoring: Socket filter programs can inspect DNS queries per container, detecting data exfiltration via DNS tunneling.

Building a Custom eBPF Security Agent#

Architecture Overview — Collection, Aggregation, Enforcement#

A production eBPF security agent follows a three-layer architecture:

┌─────────────────────────────────────────────────────┐
│  Layer 3: Enforcement & Response                     │
│  (LSM policies, process termination, network blocks) │
├─────────────────────────────────────────────────────┤
│  Layer 2: Aggregation & Detection                    │
│  (Rule engine, anomaly detection, alert correlation) │
├─────────────────────────────────────────────────────┤
│  Layer 1: Collection                                 │
│  (eBPF programs on kprobes, tracepoints, XDP, LSM)   │
└─────────────────────────────────────────────────────┘

Layer 1 (Collection) runs in kernel context. eBPF programs attached to security-relevant hooks capture raw events and emit them to ring buffers. This layer must be minimal — the verifier limits complexity, and every instruction adds overhead.

Layer 2 (Aggregation) runs in userspace. A daemon reads events from ring buffers, enriches them with container metadata (from the container runtime socket or Kubernetes API), applies detection rules, and correlates events across time windows.

Layer 3 (Enforcement) can be either kernel-side (via BPF LSM programs that deny operations) or userspace-side (via process termination, network block rules, or SIEM alerts).

Writing eBPF Programs with libbpf and CO-RE#

The modern approach to writing eBPF programs uses libbpf with CO-RE (Compile Once, Run Everywhere). CO-RE allows you to compile a single eBPF binary that runs across different kernel versions without modification. Here is a minimal example of an eBPF program that monitors openat syscalls:

// openat_monitor.bpf.c
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>

char LICENSE[] SEC("license") = "GPL";

struct event {
    u32 pid;
    u32 uid;
    char comm[16];
    char filename[256];
};

struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 256 * 1024);
} events SEC(".maps");

SEC("tracepoint/syscalls/sys_enter_openat")
int trace_openat(struct trace_event_raw_sys_enter *ctx)
{
    struct event *e;
    e = bpf_ringbuf_reserve(&events, sizeof(*e), 0);
    if (!e)
        return 0;

    e->pid = bpf_get_current_pid_tgid() >> 32;
    e->uid = bpf_get_current_uid_gid() & 0xFFFFFFFF;
    bpf_get_current_comm(&e->comm, sizeof(e->comm));

    const char *filename = (const char *)ctx->args[1];
    bpf_probe_read_user_str(e->filename, sizeof(e->filename), filename);

    bpf_ringbuf_submit(e, 0);
    return 0;
}

This program reserves space in a ring buffer, captures the PID, UID, process name, and filename, then submits the event. The vmlinux.h header (generated by bpftool btf dump file /sys/kernel/btf/vmlinux format c) provides type definitions for the running kernel, enabling CO-RE.

Userspace Agent Design in Go/Python#

The userspace agent loads the eBPF program, reads events from the ring buffer, and applies security rules. Go is the most common choice for production agents due to its static binaries, strong concurrency model, and the cilium/ebpf library. Python with bcc is better suited for prototyping.

A Go userspace agent skeleton:

package main

import (
    "encoding/binary"
    "fmt"
    "os"
    "os/signal"

    "github.com/cilium/ebpf"
    "github.com/cilium/ebpf/link"
    "github.com/cilium/ebpf/ringbuf"
    "github.com/cilium/ebpf/rlimit"
)

func main() {
    // Allow the current process to lock memory for eBPF maps
    rlimit.RemoveMemlock()

    // Load the compiled eBPF object
    objs := openatMonitorObjects{}
    if err := loadOpenatMonitorObjects(&objs, nil); err != nil {
        panic(err)
    }
    defer objs.Close()

    // Attach to the tracepoint
    tp, err := link.Tracepoint("syscalls", "sys_enter_openat", objs.TraceOpenat, nil)
    if err != nil {
        panic(err)
    }
    defer tp.Close()

    // Open the ring buffer reader
    rd, err := ringbuf.NewReader(objs.Events)
    if err != nil {
        panic(err)
    }
    defer rd.Close()

    // Read events in a goroutine
    go func() {
        for {
            record, err := rd.Read()
            if err != nil {
                return
            }
            var e openatEvent
            if err := binary.Read(bytes.NewReader(record.RawSample), binary.LittleEndian, &e); err != nil {
                continue
            }
            fmt.Printf("PID=%d UID=%d COMM=%s FILE=%s\n",
                e.Pid, e.Uid, string(e.Comm[:]), string(e.Filename[:]))
        }
    }()

    // Wait for interrupt
    sig := make(chan os.Signal, 1)
    signal.Notify(sig, os.Interrupt)
    <-sig
}

Event Processing, Enrichment, and Alerting Pipeline#

Raw eBPF events contain kernel-level data (PID, UID, syscall arguments). The userspace agent enriches these with higher-level context:

  1. Container metadata: Map PID to container ID via /proc/<pid>/cgroup, then query the container runtime or Kubernetes API for image name, namespace, pod name, and labels.
  2. Process ancestry: Walk /proc/<pid>/status to build the full process tree.
  3. File path resolution: Resolve the monitored file path to determine if it falls under a protected directory.
  4. Reputation checks: Hash the executable and check against a known-good or known-bad database.

The enriched event is then evaluated against a rule engine. Rules can be simple (e.g., “alert if any process in the web namespace calls execve on /bin/bash”) or complex (e.g., “alert if a process opens more than 100 files in 10 seconds — possible ransomware behavior”).

Existing eBPF Security Tools and When to Use Them#

Falco — Runtime Threat Detection#

Falco, originally developed by Sysdig and now a CNCF graduated project, is the most widely deployed eBPF-based runtime security tool. It uses a driver (kernel module, eBPF probe, or modern eBPF) to capture syscall events and applies a rich rule engine with hundreds of built-in rules.

CNCF statusGraduatedSandboxSandbox

When to use Falco: You need a mature, battle-tested runtime security solution with extensive built-in rules and SIEM integration. Falco is the best choice for teams that want to start with runtime security without writing custom eBPF programs.

Tetragon — Kernel-Level Enforcement#

Tetragon, part of the Cilium ecosystem, is unique among eBPF security tools because it can actively block operations using BPF LSM programs. While Falco only alerts, Tetragon can prevent a malicious syscall from completing.

When to use Tetragon: You need active enforcement (blocking, not just alerting) and are already running Cilium in your Kubernetes cluster. Tetragon’s LSM-based enforcement is the closest you can get to a kernel-level security agent without loading kernel modules.

Tracee — Tracing and Security Monitoring#

Tracee, developed by Aqua Security, focuses on deep event visibility. It uses CO-RE eBPF programs to capture a comprehensive set of events — syscalls, kernel function calls, and network events — and exports them in a structured format.

When to use Tracee: You need deep forensic visibility for incident response or compliance auditing. Tracee’s event coverage is broader than Falco’s, making it suitable for post-incident analysis.

Cilium — Network Security and Observability#

Cilium has become the default CNI for many Kubernetes clusters (eBPF Foundation 2026 Report). While primarily a networking and observability tool, Cilium’s network policies are enforced at the kernel level via eBPF, providing security isolation between pods without iptables overhead.

When to use Cilium: You need Kubernetes network policy enforcement with eBPF performance. Cilium is the de facto standard for eBPF-based container networking and is recommended for any new Kubernetes cluster.

Production Deployment Patterns#

DaemonSet vs Sidecar Deployment Models#

AspectDaemonSetSidecar

IsolationAgent runs outside container boundariesAgent runs in the same pod

For most production deployments, a DaemonSet is the right choice. It provides node-wide coverage with lower resource overhead. Sidecar deployment is reserved for high-security environments where each workload must have its own dedicated security agent.

Performance Tuning and Overhead Management#

eBPF security agents are remarkably efficient, but poor configuration can still cause performance issues. Key tuning parameters:

  1. Ring buffer size: Start with 256 KB per CPU and monitor drop counts. Increase if events are being dropped.
  2. Sampling rate: For high-frequency syscalls like read and write, consider sampling 1 in N events rather than capturing every call.
  3. Filter early: Apply filters in the eBPF program itself (e.g., only monitor specific PIDs or file paths) to avoid flooding the ring buffer with irrelevant events.
  4. Per-CPU data structures: Use per-CPU maps for counters to avoid lock contention.

Real-world overhead numbers are compelling. Datadog cut CPU usage by 35% after switching to an eBPF-based connection tracker (eBPF Foundation 2026 Report). DoorDash saw 40% less memory usage and 98% fewer restarts after migrating to eBPF monitoring. Companies report up to 90% CPU reduction compared with legacy agents (martinuke0 eBPF Tracing Guide).

Integration with SIEM and Alerting Systems#

eBPF security events are most valuable when integrated into a broader security operations pipeline. Common integration patterns:

  • Fluentd/Fluent Bit: Ship eBPF events to Elasticsearch, Splunk, or Loki.
  • Kafka/Pulsar: Buffer events for downstream processing by stream processors (Flink, Spark).
  • Prometheus/Alertmanager: Export metrics (event counts, drop rates, alert counts) for monitoring and alerting.
  • Webhook/Slack/PagerDuty: Direct alerting for critical security events.

LinkedIn reduced Kafka log volume by 70% using an eBPF observability agent that filters and aggregates events before writing to the message bus (eBPF Foundation 2026 Report).

Challenges and Limitations#

Kernel Version Requirements and Feature Gaps#

eBPF’s capabilities are tightly coupled to kernel version. Key features and their minimum kernel versions:

FeatureMinimum KernelNotes
Basic eBPF (kprobes, tracepoints)3.18Limited to 4096 instructions
Bounded loops5.3Required for complex programs
BPF ring buffer5.8Recommended for event delivery
BPF LSM5.7Required for enforcement
CO-RE (BTF support)5.2Required for portable programs

BPF sk_lookup5.9For socket-level security

If your production environment includes kernels older than 5.2, you will need to distribute per-kernel eBPF binaries or use BCC’s on-the-fly compilation approach, which requires LLVM/clang on each node.

Verifier Constraints and Debugging eBPF Programs#

The eBPF verifier is strict by design, but this creates practical challenges:

  • Complexity limits: Programs with deep branching or large loops may be rejected. You may need to split logic across multiple eBPF programs.
  • No floating point: eBPF programs cannot use floating-point arithmetic.
  • Limited stack: The stack is capped at 512 bytes. Complex data structures must be stored in maps.
  • Debugging difficulty: Failed verifier logs are cryptic. Tools like bpftool prog tracelog and bpf_printk() are essential for debugging.

The recommended debugging workflow is: prototype with Python/bcc for rapid iteration, then port to C/libbpf for production.

Security of the eBPF System Itself#

eBPF is a powerful kernel mechanism, and its security depends on proper configuration:

  • Root-only by default: Loading eBPF programs requires CAP_BPF or root. In container environments, the security agent must run with elevated privileges.
  • Unprivileged eBPF: Some eBPF program types (socket filters, cgroup skb) can be loaded by unprivileged users. If not needed, disable with kernel.unprivileged_bpf_disabled=1.
  • BPF LSM risks: A misconfigured LSM program can lock legitimate users out of the system. Always test LSM policies in enforcement-only mode before enabling blocking.

Future of eBPF Security Agents#

The eBPF ecosystem is evolving rapidly. Several developments will shape the next generation of security agents:

  1. eBPF on Windows: Microsoft is porting eBPF to Windows, enabling cross-platform security agents with a unified programming model.
  2. Rust-based eBPF: The aya crate allows writing eBPF programs in Rust, bringing memory safety guarantees to the eBPF program itself.
  3. eBPF in the kernel mainline: More eBPF program types are being added to the mainline kernel, reducing the need for out-of-tree patches.
  4. AI-assisted detection: Combining eBPF event streams with machine learning models for anomaly detection, running in the userspace agent layer.
  5. Standardized security profiles: The eBPF Foundation is working on standardized security profiles that can be shared across tools, similar to seccomp profiles.

The eBPF Foundation, backed by Google, Meta, Microsoft, and Netflix as a Linux Foundation project, ensures that eBPF will remain a core Linux technology with long-term support and investment.

Conclusion and Getting Started Checklist#

Building a Linux eBPF security agent is a practical way to achieve kernel-level runtime security without the risks of kernel modules. The architecture is proven at scale — Netflix, Cloudflare, DoorDash, LinkedIn, and GitHub all run eBPF security agents in production with measurable performance improvements over legacy approaches.

Getting started checklist:

  • Verify kernel support: bpftool feature probe on your target systems
  • Choose your approach: build custom (this guide) or deploy Falco/Tetragon/Tracee
  • Set up the development environment: libbpf, clang, bpftool, Go or Python
  • Write your first eBPF program: start with syscall monitoring (openat or execve)
  • Implement the userspace agent: ring buffer reader, event enrichment, rule engine
  • Deploy as a DaemonSet on Kubernetes or as a systemd service on bare metal
  • Tune performance: monitor drop counts, adjust ring buffer sizes, add early filters
  • Integrate with your SIEM: ship events to Elasticsearch, Splunk, or Kafka
  • Test with attack simulations: use tools like stratus-red-team or atomic-red-team

The barrier to entry has never been lower. With CO-RE, libbpf, and the cilium/ebpf Go library, you can build a production-quality eBPF security agent in a matter of weeks — not months.

FAQ#

Q: What is a Linux eBPF security agent? A: A Linux eBPF security agent is a runtime security tool that uses eBPF (extended Berkeley Packet Filter) programs to monitor system calls, file access, process execution, and network traffic directly within the Linux kernel. It provides real-time threat detection with deterministic overhead under one microsecond per event, without loading kernel modules.

Q: How does eBPF compare to traditional Linux security modules like AppArmor or SELinux? A: eBPF complements rather than replaces AppArmor and SELinux. While MAC systems enforce static policies defined in profiles, eBPF enables dynamic, programmable security logic that can adapt to runtime conditions. BPF LSM (since kernel 5.7) allows eBPF programs to attach to LSM hooks, combining the safety of eBPF with the enforcement points of traditional LSM frameworks.

Q: Can eBPF security agents block malicious operations or only detect them? A: Both. Detection-only agents (Falco, Tracee) alert on suspicious activity. Enforcement-capable agents (Tetragon, custom BPF LSM programs) can actively block operations by returning an error code from the eBPF program, preventing the syscall from completing. Blocking requires kernel 5.7+ and BPF LSM support.

Q: What is the performance impact of running an eBPF security agent in production? A: The performance impact is minimal when properly configured. eBPF programs have deterministic overhead of under 1 microsecond per event in kernel context. Companies report 35-90% CPU reduction compared with legacy monitoring agents. Datadog cut CPU usage by 35%, DoorDash reduced memory by 40%, and Seznam.cz cut CPU usage by 72x after migrating to eBPF-based solutions.

Q: What kernel version do I need to run an eBPF security agent? A: Basic syscall monitoring works on kernel 3.18+. For CO-RE (portable eBPF binaries), you need kernel 5.2+. For BPF LSM enforcement, you need kernel 5.7+. For the recommended ring buffer event delivery, kernel 5.8+. Most modern enterprise Linux distributions (Ubuntu 22.04+, RHEL 9+, Debian 12+) ship with kernels that support all eBPF features needed for a security agent.
