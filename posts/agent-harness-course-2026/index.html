What is an Agent Harness?#

An agent harness is the middleware layer that sits between a large language model (LLM) and your application logic. It handles tool discovery, model communication, conversation history, and the execution loop that makes autonomous agents possible. Instead of calling an LLM directly with a single prompt, a harness manages the full ask-generate-execute cycle — the LLM decides which tools to call, the harness executes them, and the results feed back into the next model turn. This separation of concerns is what turns a stateless API call into a reasoning agent that can browse the web, run code, query databases, and take actions on your behalf.

The concept has exploded in popularity. As of mid-2026, the OpenAI Agents SDK has surpassed 28,000 GitHub stars, and the broader ecosystem of agent harness projects — from Codex and Qwen Code to OpenHands and Hermes Agent — sees more than two new releases per day across major open-source projects. A 2026 survey paper titled “Code as Agent Harness” frames code itself as the operational substrate for agent reasoning, acting, environment modeling, and execution-based verification. Understanding how a harness works from the inside out is no longer optional for AI engineers — it is foundational.

The 4 Essential Components of Every Agent Harness#

Every agent harness, regardless of complexity or provider, shares four core components. Whether you are building a simple CLI agent in 150 lines or a production-grade multi-agent orchestrator, these four pieces must exist in some form.

Tool Registry — Discovering and Describing Available Capabilities#

The tool registry is the agent’s catalog of what it can do. Each tool is a function wrapped with a schema that the LLM can understand — typically a JSON schema describing the tool’s name, description, and parameters. When the LLM decides it needs to perform an action, it selects a tool from this registry and provides the arguments.

A well-designed tool registry supports:

  • Dynamic discovery: Tools can be registered at startup or discovered at runtime via a service registry (as demonstrated by the go-micro approach in the “Build Your Own AI Agent CLI” series).
  • Rich descriptions: Each tool includes a human-readable description that helps the LLM decide when to use it. The quality of these descriptions directly impacts the agent’s ability to choose the right tool.
  • Type-safe parameters: JSON Schema or Pydantic models define exactly what arguments each tool expects, enabling validation before execution.
  • Error contracts: Tools declare what errors they might return, allowing the harness to handle failures gracefully.

LLM Interface — Connecting to Any Provider#

The LLM interface abstracts away the differences between model providers. A good harness supports OpenAI, Anthropic, Google Gemini, and local models through a unified API. This provider-agnostic design is critical because:

  • Different models excel at different tasks (Claude for coding, GPT-4o for reasoning, Gemini for multimodal).
  • Cost optimization requires routing simple tasks to cheaper models.
  • Resilience demands fallback chains when a provider is down.
  • Local models are essential for air-gapped or privacy-sensitive environments.

The interface typically handles: authentication, request formatting, response parsing, streaming, token counting, and error retry logic. The OpenAI Agents SDK, for example, supports 100+ LLMs through its LiteLLM integration while maintaining a single agent interface.

Conversation Memory — Managing Context Windows and History#

Conversation memory is what gives an agent continuity across multiple turns. Without it, every LLM call is a fresh start — the agent cannot remember what it did two steps ago, what the user asked five minutes ago, or what results it already computed.

Memory management involves several challenges:

  • Context window limits: Even the largest models (Claude 4 with 200K tokens, Gemini 2.5 Pro with 2M tokens) have finite context. The harness must decide what to keep, what to summarize, and what to drop.
  • Token budgeting: Each turn consumes tokens from the context window. The harness needs to track usage and implement strategies like sliding windows, summarization, or retrieval-augmented memory.
  • Structured history: Raw message dumps waste tokens. A good harness stores structured turns — user message, assistant response, tool calls, tool results — and formats them efficiently for the model.

Execution Loop — The Core Ask-Generate-Execute Cycle#

The execution loop is the heartbeat of the agent harness. It follows a simple but powerful pattern:

  1. Ask: Present the current state (system prompt + conversation history + tool schemas) to the LLM.
  2. Generate: The LLM responds — either with a final answer or with one or more tool call requests.
  3. Execute: The harness runs the requested tools, captures results, and appends them to the conversation history.
  4. Repeat: Go back to step 1 with the updated state.

This loop continues until the LLM produces a final answer, reaches a maximum iteration limit, or hits a safety guardrail. The elegance of this design is its simplicity — the entire complexity of autonomous agent behavior emerges from this single loop.

Building Your First Agent Harness — Step-by-Step Implementation in Python#

Let’s build a working agent harness from scratch. We will implement all four components in under 200 lines of Python, then extend it with advanced features.

Setting Up the Project Structure#

Create a new directory and a single Python file:

agent-harness/

│   ├── __init__.py
│   ├── web_search.py

├── requirements.txt    # Dependencies
└── example.py          # Usage example

Dependencies are minimal: openai (or anthropic), pydantic for schema validation, and httpx for async HTTP calls.

Implementing the Tool Registry#

from pydantic import BaseModel
from typing import Callable, Dict, Any, List, Optional
import json


class ToolParameter(BaseModel):
    name: str
    type: str
    description: str
    required: bool = True


class Tool(BaseModel):
    name: str
    description: str
    parameters: List[ToolParameter]
    function: Callable

    def to_openai_tool(self) -> Dict[str, Any]:
        """Convert to OpenAI-compatible tool schema."""
        properties = {}
        required_params = []
        for p in self.parameters:
            properties[p.name] = {
                "type": p.type,
                "description": p.description,
            }
            if p.required:
                required_params.append(p.name)
        return {
            "type": "function",
            "function": {
                "name": self.name,
                "description": self.description,
                "parameters": {
                    "type": "object",
                    "properties": properties,
                    "required": required_params,
                },
            },
        }


class ToolRegistry:
    def __init__(self):
        self._tools: Dict[str, Tool] = {}

    def register(self, tool: Tool):
        self._tools[tool.name] = tool

    def get(self, name: str) -> Optional[Tool]:
        return self._tools.get(name)

    def list_schemas(self) -> List[Dict[str, Any]]:
        return [t.to_openai_tool() for t in self._tools.values()]

    def execute(self, name: str, arguments: Dict[str, Any]) -> str:
        tool = self.get(name)
        if not tool:
            return f"Error: Tool '{name}' not found"
        try:
            result = tool.function(**arguments)
            return str(result)
        except Exception as e:
            return f"Error executing {name}: {str(e)}"

This registry is the backbone of the harness. Tools are registered with their name, description, parameter schema, and the actual Python function. The to_openai_tool() method converts each tool into the format that OpenAI and compatible APIs expect, making integration seamless.

Creating the LLM Client Abstraction#

from openai import OpenAI
from typing import List, Dict, Any, Optional


class LLMClient:
    def __init__(
        self,
        model: str = "gpt-4o",
        api_key: Optional[str] = None,
        base_url: Optional[str] = None,
    ):
        self.model = model
        self.client = OpenAI(api_key=api_key, base_url=base_url)

    def chat(
        self,
        messages: List[Dict[str, str]],
        tools: Optional[List[Dict[str, Any]]] = None,
        temperature: float = 0.7,
        max_tokens: int = 4096,
    ) -> Dict[str, Any]:
        kwargs = {
            "model": self.model,
            "messages": messages,
            "temperature": temperature,
            "max_tokens": max_tokens,
        }
        if tools:
            kwargs["tools"] = tools
            kwargs["tool_choice"] = "auto"

        response = self.client.chat.completions.create(**kwargs)
        return response.choices[0].message

This abstraction lets you swap providers by changing the base_url and model parameters. For Anthropic, you would create a similar wrapper using the Anthropic SDK. For local models running through Ollama or vLLM, point base_url to http://localhost:11434/v1.

Building the Conversation Manager#

from typing import List, Dict, Any


class ConversationManager:
    def __init__(self, system_prompt: str, max_history: int = 20):
        self.messages: List[Dict[str, Any]] = [
            {"role": "system", "content": system_prompt}
        ]
        self.max_history = max_history

    def add_user_message(self, content: str):
        self.messages.append({"role": "user", "content": content})
        self._trim()

    def add_assistant_message(self, content: Optional[str], tool_calls: Optional[List] = None):
        msg = {"role": "assistant"}
        if content:
            msg["content"] = content
        if tool_calls:
            msg["tool_calls"] = tool_calls
        self.messages.append(msg)
        self._trim()

    def add_tool_result(self, tool_call_id: str, name: str, result: str):
        self.messages.append({
            "role": "tool",
            "tool_call_id": tool_call_id,
            "name": name,
            "content": result,
        })
        self._trim()

    def get_messages(self) -> List[Dict[str, Any]]:
        return self.messages

    def _trim(self):
        """Keep system message + last N turns."""
        if len(self.messages) > self.max_history + 1:
            system = self.messages[0]
            self.messages = [system] + self.messages[-(self.max_history):]

The conversation manager maintains the message history, handles the system prompt, and implements a sliding window to stay within context limits. The _trim method drops the oldest messages while preserving the system prompt, ensuring the agent never exceeds its budget.

Wiring the Main Execution Loop#

class AgentHarness:
    def __init__(
        self,
        llm: LLMClient,
        registry: ToolRegistry,
        conversation: ConversationManager,
        max_iterations: int = 10,
    ):
        self.llm = llm
        self.registry = registry
        self.conversation = conversation
        self.max_iterations = max_iterations

    def run(self, user_input: str) -> str:
        self.conversation.add_user_message(user_input)
        iteration = 0

        while iteration < self.max_iterations:
            iteration += 1
            messages = self.conversation.get_messages()
            tools = self.registry.list_schemas()

            response = self.llm.chat(messages, tools=tools)

            if not response.tool_calls:
                # LLM produced a final answer
                self.conversation.add_assistant_message(
                    content=response.content
                )
                return response.content

            # Process each tool call
            self.conversation.add_assistant_message(
                content=response.content,
                tool_calls=[
                    {
                        "id": tc.id,
                        "type": "function",
                        "function": {
                            "name": tc.function.name,
                            "arguments": tc.function.arguments,
                        },
                    }
                    for tc in response.tool_calls
                ],
            )

            for tc in response.tool_calls:
                import json
                args = json.loads(tc.function.arguments)
                result = self.registry.execute(tc.function.name, args)
                self.conversation.add_tool_result(tc.id, tc.function.name, result)

        return "Agent reached maximum iterations without producing a final answer."

This is the core loop. The harness sends the conversation state plus tool schemas to the LLM. If the LLM returns tool calls, the harness executes them and feeds the results back. If the LLM returns a text response, the harness returns it to the user. The max_iterations guard prevents infinite loops.

Adding Advanced Features#

Once the basic loop works, you can extend the harness with production-grade capabilities.

Multi-Turn Conversations and Context Management#

Real-world agents need to maintain state across multiple user interactions. Implement session persistence by serializing the conversation history to a database or file. Use summarization techniques — when the context window fills, ask a secondary LLM to summarize older turns, then replace them with the summary. This is how production systems like Hermes Agent handle long-running sessions without losing critical context.

Tool Execution with Error Handling#

Tools can fail for many reasons: network timeouts, invalid inputs, rate limits, or unexpected data. A robust harness wraps each tool execution in try-catch blocks, returns structured error messages to the LLM, and implements retry logic with exponential backoff. The LLM can then decide whether to retry, try a different tool, or inform the user of the failure.

Streaming Responses#

For a better user experience, stream the LLM’s response token by token. Instead of waiting for the full response, yield each chunk as it arrives. When the LLM decides to call a tool, the stream pauses, the tool executes, and the result feeds back into a new stream. This is how tools like Claude Code and Codex provide real-time feedback during long-running tasks.

Structured Output Parsing#

Many agent tasks require structured output — JSON, YAML, or specific data formats. Use the LLM’s structured output mode (OpenAI’s response_format, Anthropic’s tool use with structured tools) to guarantee valid output. The harness can then validate the output against a Pydantic schema before passing it to downstream systems.

From Single Agent to Multi-Agent Orchestration#

A single agent harness is powerful, but many real-world problems require multiple agents working together.

Agent Handoffs and Delegation Patterns#

In a multi-agent system, one agent can hand off a task to another agent that specializes in a different domain. The handoff is itself a tool — the agent calls a “delegate to writer agent” tool, and the harness routes the task to the appropriate sub-agent. This pattern is used by OpenAI Agents SDK (handoffs), LangGraph (conditional edges), and Hermes Agent (delegate_task tool).

Building a Meta-Harness for Multiple Agent Types#

A meta-harness orchestrates different agent types — CLI agents, browser agents, code agents, voice agents — under a single coordination layer. Projects like Omnigent (7,500+ GitHub stars) demonstrate this pattern, supporting Claude Code, Codex, Cursor, Hermes, and custom agents through a unified interface. The meta-harness handles routing, state sharing, and result aggregation across heterogeneous agents.

Policy and Governance Layers#

Production agent systems need guardrails. A policy layer sits between the LLM and tool execution, enforcing rules like:

  • Approval gates: Require human approval before destructive actions (file deletion, database writes, financial transactions).
  • Spend caps: Limit API costs per session, per user, or per day.
  • Tool restrictions: Block certain tools in specific contexts (no web access for sensitive data).
  • Audit logging: Record every tool call, LLM response, and decision for compliance.

Testing and Evaluating Your Agent Harness#

Building the harness is only half the work. You need to verify it behaves correctly.

Synthetic Scenario Generation#

Tools like Gambit generate synthetic test scenarios that exercise your agent’s capabilities. Instead of manually writing test cases, you describe the capabilities you want to test, and the scenario generator produces diverse inputs that probe edge cases, error conditions, and complex multi-step workflows.

Behavior Grading and Regression Testing#

Each test scenario produces a trace of the agent’s behavior — which tools it called, in what order, what arguments it used, and what final answer it produced. A grading system compares this trace against expected behavior, flagging regressions when a code change causes the agent to take a different (worse) path. This is the agent equivalent of unit testing.

Trace Capture and Debugging#

Every turn of the execution loop should be captured as a trace: the messages sent to the LLM, the tool calls made, the results returned, and the timing of each step. These traces are invaluable for debugging. When an agent makes a surprising decision, the trace shows exactly what information it had at that moment. The OpenAI Agents SDK includes built-in tracing, and you can implement your own by wrapping the execution loop with a trace recorder.

Decision Framework for Build-vs-Buy#

Build your own harness when:

  • You need deep understanding of how agents work (learning goal).
  • Your use case is simple (one model, a few tools, single user).
  • You have unique requirements that existing frameworks don’t support.
  • You want zero external dependencies and full control over the codebase.

Use an existing framework when:

  • You need production-grade reliability, tracing, and error handling out of the box.
  • Your team needs to move fast and cannot afford to build infrastructure.
  • You need multi-agent orchestration with handoffs, governance, and monitoring.
  • You want community support, documentation, and proven patterns.

The middle ground is to start with a custom harness for learning, then migrate to a framework for production. Many teams build a thin custom layer on top of the OpenAI Agents SDK or LangGraph, getting the best of both worlds.

Conclusion — The Future of Agent Harnesses#

The agent harness is becoming the operating system of AI applications. Just as every web application needs an HTTP server, every AI application will need an agent harness. The trend is clear: from 150-line prototypes to 28K-star SDKs, from single-agent loops to multi-agent meta-harnesses with policy engines and governance layers.

The “Code as Agent Harness” paradigm suggests that code itself — with its ability to reason, act, model environments, and verify execution — is the ultimate harness. As models grow more capable, the harness’s role shifts from compensating for model limitations to enabling model capabilities. The best time to understand this architecture was yesterday. The second best time is now.

Build your own harness. Break it. Fix it. Extend it. Then decide whether to keep it or adopt a framework. Either way, you will understand agents at a level that no tutorial can teach without hands-on code.

FAQ#

What is the difference between an agent harness and an agent framework?#

An agent harness is the minimal runtime that manages the LLM-tool-execution loop. An agent framework is a higher-level abstraction that includes harness functionality plus additional features like multi-agent orchestration, memory systems, evaluation tools, and built-in integrations. The harness is the core; the framework is the full ecosystem.

How many lines of code does a basic agent harness need?#

A functional agent harness with tool registry, LLM client, conversation memory, and execution loop can be implemented in approximately 150-200 lines of Python. The go-micro team demonstrated a working CLI agent in 150 lines, and the implementation in this tutorial is under 200 lines.

Can I use a local LLM with a custom agent harness?#

Yes. The LLM client abstraction in a well-designed harness supports any OpenAI-compatible API. Local models running through Ollama, vLLM, or llama.cpp expose an OpenAI-compatible endpoint, so you can point your harness at http://localhost:11434/v1 with a model like Llama 3 or Qwen 2.5.

What is a meta-harness in multi-agent systems?#

A meta-harness is an orchestrator that manages multiple heterogeneous agents under a single coordination layer. It handles routing tasks to the right agent, sharing state between agents, aggregating results, and enforcing cross-agent policies. Omnigent is a prominent example of a meta-harness architecture.

How do I test an agent harness for reliability?#

Test your harness using synthetic scenario generation (tools like Gambit), behavior grading that compares actual vs. expected tool-call sequences, regression testing that catches behavior changes after code modifications, and trace capture that records every LLM call and tool execution for debugging. This four-layer testing approach mirrors unit, integration, and system testing in traditional software.
