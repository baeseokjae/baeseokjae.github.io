What is CubeSandbox?#

CubeSandbox is an open-source, hardware-isolated sandbox runtime purpose-built for AI agents. Developed by Tencent Cloud and released under the Apache 2.0 license in April 2026, it provides a secure execution environment for LLM-generated code, agent tool calls, and reinforcement learning training workloads. Built on RustVMM and KVM, each sandbox instance boots a dedicated Guest OS kernel in under 60 milliseconds with less than 5 MB of memory overhead, offering hardware-level isolation that container-based approaches cannot match. CubeSandbox is fully compatible with the E2B SDK, meaning developers can switch from E2B to CubeSandbox by changing a single environment variable with zero code modifications.

Why AI Agents Need a New Kind of Sandbox#

AI agents today execute code, run shell commands, browse the web, and interact with APIs on behalf of users. Every one of these actions is a potential attack surface. When an LLM generates and executes code, that code may contain unintended side effects — file system access, network calls, or resource exhaustion. Traditional sandboxing approaches like Docker containers share a host kernel, making them vulnerable to container escape exploits. CubeSandbox addresses this by providing a dedicated microVM per sandbox instance, ensuring that even if an agent’s code is compromised, the host system and other sandboxes remain completely isolated.

The Security Problem with LLM-Generated Code#

LLM-generated code is inherently unpredictable. Models can hallucinate API calls, generate infinite loops, or produce code that attempts to access restricted resources. In production agent systems, this code runs autonomously — often without human review for every execution. A single malicious or buggy code execution in a shared environment can compromise an entire agent fleet. CubeSandbox’s hardware-level isolation means each agent execution gets its own dedicated kernel, its own virtualized hardware, and its own network stack. If an agent’s code crashes or attempts an exploit, it affects only that single sandbox instance.

Architecture Deep Dive#

CubeSandbox’s architecture is divided into a control plane and a data plane, with several specialized components handling networking, security, and state management.

Control Plane: CubeAPI, CubeMaster, and WebUI#

The control plane manages sandbox lifecycle, scheduling, and user interactions. CubeAPI is the RESTful API layer that accepts sandbox creation, execution, and management requests. CubeMaster is the central scheduler that assigns sandbox instances to available nodes, manages capacity, and handles failover. The WebUI Dashboard provides a graphical interface for monitoring active sandboxes, viewing logs, managing templates, and configuring egress rules. This three-tier control plane architecture mirrors Kubernetes’ design philosophy, making CubeSandbox familiar to DevOps teams already comfortable with cluster management.

Data Plane: Cubelet, CubeHypervisor, and CubeShim#

On each host node, the data plane components handle the actual sandbox lifecycle. Cubelet is the node agent that communicates with CubeMaster, similar to kubelet in Kubernetes. CubeHypervisor manages the RustVMM-based microVM instances, handling boot, pause, resume, and teardown. CubeShim provides the OCI-compatible interface that allows CubeSandbox to work with standard container tooling and images. This design means CubeSandbox can use OCI container images as templates, converting them into bootable microVM snapshots.

Network: CubeVS eBPF Virtual Switch#

CubeSandbox’s networking layer is built on CubeVS, an eBPF-based virtual switch that provides kernel-level network isolation. CubeVS uses three distinct eBPF programs to enforce network policies: one for ingress filtering, one for egress control, and one for inter-sandbox isolation. This approach achieves near-native network performance while maintaining strict isolation between sandboxes. Egress control rules can be configured per sandbox or per template, allowing administrators to whitelist specific domains or IP ranges that an agent is allowed to contact.

Security: CubeEgress, Credential Vault, and Audit#

Security is a first-class concern in CubeSandbox. CubeEgress enforces outbound network policies at the hypervisor level, preventing agents from exfiltrating data to unauthorized destinations. The Credential Vault stores API keys, tokens, and secrets outside the sandbox — secrets never enter the sandbox’s environment variables, filesystem, or process space. Instead, the vault injects credentials directly into authorized API calls at the proxy level. The Audit Trail system records every action within a sandbox session, including which model was called, what code was executed, and the token usage, providing end-to-end accountability for enterprise compliance requirements.

State Management: CubeCoW Snapshot/Clone/Rollback#

CubeSandbox uses CubeCoW, a copy-on-write layer built on XFS reflink (FICLONE), to manage sandbox state. Snapshots, clones, and rollbacks all complete in hundreds of milliseconds. This enables powerful workflows: an agent can snapshot its state before a risky operation, clone a sandbox to parallelize testing, or roll back to a known good state after a failure. For RL training workloads, this means thousands of agent environments can be cloned from a single base snapshot in seconds, dramatically reducing the overhead of environment setup.

Key Features and Performance#

Sub-60ms Cold Start — How Template Snapshots Work#

CubeSandbox achieves its remarkable cold start performance through a three-phase template lifecycle: Init → Boot & Snapshot → Deploy. First, a base template is created from an OCI image. The template is booted once, and a clean snapshot of the booted microVM state is saved. When a new sandbox is requested, CubeSandbox clones this pre-booted snapshot rather than booting from scratch. The result is a fully serviceable sandbox in under 60 milliseconds. Under 50 concurrent creations, CubeSandbox averages 67 ms with a P95 of 90 ms and a P99 of 137 ms. These numbers were measured on Tencent Cloud’s bare-metal lab infrastructure and represent production-grade performance.

Auto-Pause/Resume for Zero Idle Cost#

CubeSandbox automatically pauses sandbox instances when they are idle and resumes them in hundreds of milliseconds when activity resumes. This auto-pause/resume feature eliminates the cost of running idle sandboxes, which is particularly important for agent workloads that may have long pauses between tool calls. A single node can support over 2,000 sandbox instances simultaneously, and the auto-pause mechanism ensures that memory is only consumed by actively running sandboxes.

E2B SDK Compatibility — Drop-in Migration#

One of CubeSandbox’s most strategic features is its compatibility with the E2B SDK. Developers using E2B’s Code Interpreter SDK can switch to CubeSandbox by changing a single environment variable — no code changes required. This compatibility extends to the sandbox API, file operations, and execution semantics. For teams already invested in the E2B ecosystem, this means they can migrate to CubeSandbox’s hardware-level isolation without rewriting their agent code. It also means CubeSandbox immediately benefits from the entire E2B developer tooling ecosystem.

Template System and Volume Framework#

CubeSandbox’s template system allows teams to define reusable sandbox environments from OCI container images. Templates can include pre-installed packages, environment configurations, and network policies. The Volume Framework, introduced in v0.6, allows persistent data volumes to be attached to sandbox instances, enabling stateful agent workloads. Template aliases provide a convenient naming mechanism for managing multiple template versions.

Deployment Options#

CubeSandbox supports four deployment modes, ranging from single-node development setups to production Kubernetes clusters.

Single-Node Bare-Metal Setup#

For development and testing, CubeSandbox can be deployed on a single bare-metal or virtual machine. The setup requires KVM support and a Linux kernel with eBPF capabilities. This mode is ideal for evaluating CubeSandbox, running local agent tests, or small-scale deployments.

Multi-Node Cluster Deployment#

For production workloads, CubeSandbox supports multi-node cluster deployments with CubeMaster coordinating sandbox scheduling across nodes. The cluster mode provides horizontal scaling, high availability, and load balancing. Nodes can be added or removed without disrupting running sandboxes.

Kubernetes Deployment via Helm#

CubeSandbox v0.6 introduced native Kubernetes deployment via a Helm chart. This allows teams to deploy CubeSandbox on existing Kubernetes clusters, treating sandbox instances as custom resources managed by the Kubernetes control plane. The Helm chart handles CubeAPI, CubeMaster, Cubelet, and supporting services, integrating with existing Kubernetes networking and storage infrastructure.

Terraform on Tencent Cloud#

For teams deploying on Tencent Cloud, CubeSandbox provides a Terraform provider that automates the provisioning of the underlying infrastructure — bare-metal instances, networking, and storage. This is the recommended deployment path for production workloads on Tencent Cloud, as it ensures optimal performance by using Tencent’s optimized hardware and network configurations.

Real-World Use Cases#

MiniMax RL Training at 10K+ Concurrency#

MiniMax, a leading AI company, uses CubeSandbox’s Agent Runtime for reinforcement learning training at massive scale. According to Tencent Cloud, MiniMax runs RL training workloads with over 10,000 concurrent sandbox instances and million-level throughput, achieving a “zero-incident” security record. For RL training, each training step requires thousands of parallel environment executions, and CubeSandbox’s sub-60ms cold start and snapshot/clone capabilities make it feasible to create and destroy environments at this scale without becoming a training bottleneck.

SWE-bench and Coding Agent Evaluation#

CubeSandbox is well-suited for running coding agent benchmarks like SWE-bench, where each test case requires an isolated environment with specific dependencies, file structures, and network configurations. The template system allows each benchmark to define its environment as a template, and the snapshot/rollback feature ensures clean state between test runs. The E2B SDK compatibility means existing SWE-bench runners built on E2B can switch to CubeSandbox with minimal changes.

Enterprise Agent Hosting with Governance#

For enterprises deploying AI agents in production, CubeSandbox provides the governance tooling that security teams require. The credential vault ensures that API keys never leak into agent environments. The egress control prevents data exfiltration. The audit trail provides a complete record of every action taken by every agent. Tencent Cloud positions CubeSandbox as an “Agent Runtime” control plane that separates agent state from compute, allowing enterprises to manage agent fleets with the same rigor they apply to their production infrastructure.

CubeSandbox’s open-source nature and self-hosting capabilities give it a significant advantage for enterprises that need to run agent workloads on their own infrastructure. E2B’s advantage lies in its mature ecosystem, broader SDK language support, and managed cloud service.

vs OpenSandbox, Microsandbox, and Daytona#

OpenSandbox and Microsandbox are smaller open-source projects that provide container-based sandboxing for AI agents. They lack the hardware-level isolation that CubeSandbox provides, making them suitable for development and testing but potentially insufficient for production security requirements. Daytona is a more established open-source project focused on development environments rather than agent execution, with a different target use case.

vs Firecracker, Kata Containers, and gVisor#

Firecracker is the microVM technology that powers AWS Lambda and Fargate. It provides similar hardware-level isolation but lacks the agent-specific features that CubeSandbox offers — credential vault, egress control, audit trails, and E2B SDK compatibility. Kata Containers provides hardware-virtualized containers but has a heavier footprint and slower startup times. gVisor is a user-space kernel that provides a security layer for containers but does not offer true hardware isolation. CubeSandbox’s combination of agent-specific features, sub-60ms startup, and hardware isolation makes it the most complete solution for AI agent workloads.

The Bigger Picture — Agent Infrastructure in 2026#

CubeSandbox represents a broader trend in AI infrastructure: the emergence of specialized execution environments for AI agents. Just as Kubernetes became the standard control plane for containerized applications, CubeSandbox and similar projects are vying to become the standard control plane for agentic workloads. The key requirements — hardware isolation, fast startup, state management, and governance — are fundamentally different from both traditional container orchestration and serverless computing.

Tencent Cloud’s decision to open-source CubeSandbox under Apache 2.0 is a strategic move to set de facto standards for agent infrastructure. By making the technology freely available and compatible with the existing E2B ecosystem, Tencent is positioning itself at the center of the agent infrastructure market. The company’s focus on governance tooling — credential management, audit trails, egress control — reflects the enterprise demand for secure, auditable agent deployments.

The open-source strategy also accelerates adoption. With 10,774 GitHub stars and 979 forks in just three months, CubeSandbox has attracted significant community interest. The monthly release cadence (v0.4 in May, v0.5 in June, v0.6 in July 2026) demonstrates active development and rapid feature iteration.

Conclusion and Recommendations#

CubeSandbox is a compelling solution for teams that need secure, fast, and scalable sandbox environments for AI agents. Its hardware-level isolation, sub-60ms cold starts, and comprehensive security features make it suitable for production agent workloads, particularly in enterprise environments where security and governance are paramount.

For teams currently using E2B, CubeSandbox offers a migration path that requires minimal code changes, making it worth evaluating as an open-source alternative. For teams building new agent infrastructure, CubeSandbox’s combination of features — credential vault, egress control, audit trails, template system, and multiple deployment options — provides a complete solution that would otherwise require integrating multiple separate tools.

The main caveat is CubeSandbox’s relative youth. The project is only three months old, and while development is active, the ecosystem, documentation, and community support are still maturing. Teams should evaluate CubeSandbox against their specific requirements, particularly around performance, and verify that the benchmarks align with their own infrastructure.

For RL training workloads, enterprise agent hosting, and any scenario requiring hardware-level isolation at scale, CubeSandbox is worth serious consideration. It represents a significant step forward in agent infrastructure and signals the direction the industry is heading.

FAQ#

What is CubeSandbox and how does it work?#

CubeSandbox is an open-source microVM runtime from Tencent Cloud designed specifically for AI agent execution. It uses RustVMM and KVM to create hardware-isolated sandbox environments that boot in under 60 milliseconds. Each sandbox runs its own dedicated Guest OS kernel, providing stronger isolation than containers while maintaining the startup speed and low memory footprint that agent workloads require.

How does CubeSandbox compare to Docker for AI agent sandboxing?#

Docker containers share the host kernel and provide OS-level isolation through namespaces and cgroups, which is vulnerable to container escape exploits. CubeSandbox provides hardware-level isolation with a dedicated kernel per sandbox, making it significantly more secure. While Docker starts instantly, CubeSandbox’s sub-60ms boot time is close enough for most agent workloads, and the security benefits of hardware isolation outweigh the marginal startup time difference.

Is CubeSandbox compatible with E2B’s SDK?#

Yes, CubeSandbox is fully compatible with the E2B Code Interpreter SDK. Developers can switch from E2B to CubeSandbox by changing a single environment variable with zero code modifications. This compatibility extends to the sandbox API, file operations, and execution semantics, making migration straightforward for teams already using E2B.

Can CubeSandbox be deployed on Kubernetes?#

Yes, CubeSandbox v0.6 introduced native Kubernetes deployment via a Helm chart. The Helm chart handles CubeAPI, CubeMaster, Cubelet, and supporting services, integrating with existing Kubernetes networking and storage infrastructure. CubeSandbox also supports single-node bare-metal deployment, multi-node cluster deployment, and Terraform-based deployment on Tencent Cloud.

What are the hardware requirements for running CubeSandbox?#

CubeSandbox requires a Linux host with KVM support and a kernel that supports eBPF. A single node can support over 2,000 sandbox instances. For production deployments, Tencent Cloud recommends bare-metal instances with KVM virtualization extensions. ARM64 is fully supported across compilation, build, and deployment. The memory overhead per sandbox is less than 5 MB, making it efficient even on resource-constrained hosts.
