What Is Agentry? A Framework That Treats AI Agents as React Components#

Agentry is an open-source TypeScript framework that reimagines AI agents as React components. Instead of writing imperative agent logic with chained API calls and manual state management, you define agents declaratively using JSX — the same syntax React developers use for UI components. An agent becomes a tree of <Agent>, <System>, <Tools>, and <Message> elements rendered by a custom React reconciler. Created as a Thanksgiving 2025 weekend project by Colin Dsouza, Agentry is at version 0.1.0 with 8 GitHub stars and roughly 20 monthly npm downloads. Despite its early stage, the framework introduces a genuinely novel paradigm: using React’s component model not just to render UI, but to define the agent itself.

Core Architecture — How React’s Component Model Maps to Agent Execution#

At the heart of Agentry is the react-reconciler package (v0.33), the same low-level library that powers React DOM and React Native. Agentry implements a custom host config that maps React’s reconciliation cycle — mount, update, unmount — to agent lifecycle events. When you write <Agent> in JSX, the reconciler creates a host instance that manages an LLM conversation loop. When a <Tool> mounts, the reconciler registers a function call handler. When it unmounts, the tool is removed from the agent’s available tool set.

This architecture means every React concept you already know — props, state, effects, context, conditional rendering — maps directly to agent behavior. The component tree becomes the agent execution tree. State changes trigger re-renders that update the agent’s system prompt, tool list, or message history. The framework uses Zustand for internal state management and eventemitter3 for event handling during execution.

Key Features Deep Dive#

Declarative Agent Definition with JSX#

Agentry’s most distinctive feature is its JSX-based agent definition. Here is what a basic agent looks like:

import { Agent, System, Tools, Tool, Message } from "agentry";

function MyAgent() {
  return (
    <Agent provider="openai" model="gpt-4o">
      <System>
        You are a helpful assistant with access to tools.
      </System>
      <Tools>
        <Tool name="search" parameters={searchSchema}>
          Perform web searches
        </Tool>
        <Tool name="calculator" parameters={calcSchema}>
          Perform mathematical calculations
        </Tool>
      </Tools>
    </Agent>
  );
}

This declarative approach eliminates boilerplate. The <System> component sets the system prompt. <Tools> wraps tool definitions. Each <Tool> declares a name, Zod schema for parameters, and a description. The framework handles serialization, function calling, and response parsing automatically.

Dynamic Tools via React State#

Because agents are React components, you can use useState to add or remove tools dynamically based on conversation context. This is a significant departure from static tool definitions in frameworks like LangChain or the Vercel AI SDK:

function AdaptiveAgent() {
  const [hasFileAccess, setHasFileAccess] = useState(false);

  return (
    <Agent provider="openai" model="gpt-4o">
      <System>You are a file management assistant.</System>
      <Tools>
        <Tool name="read_file" parameters={readFileSchema}>
          Read file contents
        </Tool>
        {hasFileAccess && (
          <Tool name="delete_file" parameters={deleteFileSchema}>
            Delete files from disk
          </Tool>
        )}
      </Tools>
    </Agent>
  );
}

When hasFileAccess becomes true, the delete_file tool mounts and becomes available to the LLM on the next turn. When it becomes false, the tool unmounts and the agent can no longer call it. This pattern enables fine-grained, context-aware tool access control without any imperative tool registration logic.

Subagents and Composition with AgentTool#

Agentry supports hierarchical agent composition through the <AgentTool> component. You can nest agents inside other agents, with type-safe parameter passing via Zod schemas:

function ResearchAgent() {
  return (
    <Agent provider="openai" model="gpt-4o">
      <System>Coordinate research across specialists.</System>
      <Tools>
        <AgentTool
          name="web_researcher"
          agent={<WebSearchAgent />}
          parameters={z.object({ query: z.string() })}
        />
        <AgentTool
          name="data_analyst"
          agent={<DataAnalysisAgent />}
          parameters={z.object({ dataset: z.string() })}
        />
      </Tools>
    </Agent>
  );
}

The parent agent calls subagents as tools. Each subagent runs its own conversation loop with its own system prompt, tools, and model configuration. The parent receives the subagent’s final output as the tool result. This mirrors the manager-employee pattern common in production agent deployments.

Conditional Rendering with Condition#

Agentry includes a <Condition> component that evaluates natural language conditions against conversation history to change agent behavior:

function CustomerSupportAgent() {
  return (
    <Agent provider="openai" model="gpt-4o">
      <System>You are a customer support agent.</System>
      <Condition when="the user is frustrated or angry">
        <System>Escalate to a human supervisor and apologize.</System>
        <Tool name="escalate" parameters={escalateSchema}>
          Escalate to human support
        </Tool>
      </Condition>
      <Condition when="the user asks about pricing">
        <System>Provide pricing information from our current plans.</System>
        <Tool name="lookup_pricing" parameters={pricingSchema}>
          Look up current pricing
        </Tool>
      </Condition>
    </Agent>
  );
}

The <Condition when="natural language description"> component evaluates the condition against the conversation history using an LLM call. When the condition is met, the children mount and become active. When it is not, they unmount. This enables natural language routing — a more flexible alternative to rigid if/else logic in agent code.

Programmatic Agent Spawning#

Beyond declarative composition, Agentry provides context.runAgent() for programmatic agent spawning from within tool handlers. This enables parallel execution patterns:

async function researchTask({ queries }, context) {
  const results = await Promise.all(
    queries.map((q) =>
      context.runAgent(
        <WebSearchAgent query={q} />,
        { provider: "openai", model: "gpt-4o-mini" }
      )
    )
  );
  return synthesize(results);
}

This pattern is powerful for parallelizable workloads — analyzing multiple documents, searching across sources, or running independent validation checks simultaneously. Each spawned agent runs in its own execution context with its own conversation state.

Cross-Provider Subagents#

Agentry supports mixing different LLM providers in the same agent tree. An OpenAI parent agent can spawn Anthropic subagents and vice versa:

function HybridAgent() {
  return (
    <Agent provider="openai" model="gpt-4o">
      <System>Coordinate research across providers.</System>
      <Tools>
        <AgentTool
          name="claude_analyst"
          agent={
            <Agent provider="anthropic" model="claude-sonnet-4">
              <System>Analyze data with deep reasoning.</System>
            </Agent>
          }
          parameters={z.object({ data: z.string() })}
        />
      </Tools>
    </Agent>
  );
}

This cross-provider capability is rare among agent frameworks. Most frameworks lock you into a single provider. Agentry’s provider-agnostic reconciler means each subagent can use the model best suited to its task — GPT-4o for tool use, Claude for reasoning, a smaller model for classification — all within a single declarative tree.

Streaming and WebSocket Mode#

Agentry supports both batch mode (run to completion and return the final result) and interactive mode (streaming responses with an ongoing conversation handle). For OpenAI, it offers WebSocket mode that reduces latency in multi-tool loops by maintaining a persistent connection. The framework also includes compaction controls for long conversations — you can configure when and how aggressively to summarize older messages to stay within context limits. Anthropic’s prompt caching is supported out of the box.

Tambo — Agents That Render React Components#

Tambo (11,157 stars) takes the opposite approach from Agentry. Instead of agents being React components, Tambo gives agents the ability to render React components. An agent decides which UI component to show based on conversation context, and Tambo handles the state management between the user, the agent, and the rendered component. Tambo has processed over half a million messages on its hosted service and reached v1.0 in February 2026. It is significantly more mature than Agentry and has an active community.

Vercel AI SDK — The Industry Standard#

The Vercel AI SDK (25,910 stars) is the dominant toolkit for building AI-powered applications in the TypeScript ecosystem. Created by the team behind Next.js, it supports generative UI — agents that dynamically render React components — alongside streaming, tool calling, and multi-model support. It is framework-agnostic (React, Svelte, Vue, Next.js) and production-tested at scale. For most teams, the Vercel AI SDK is the safe, proven choice.

Agent Prism and Gaia UI — Visualization and UI Libraries#

Agent Prism (376 stars) by Evil Martians focuses on observability — visualizing AI agent traces using OpenTelemetry for distributed tracing of LLM calls. Gaia UI (212 stars) provides beautifully designed React components for building agent interfaces. Neither competes directly with Agentry; they solve different problems in the agent development stack.

Practical Evaluation — Installation, Setup, and First Impressions#

Agentry requires React 19 and Zod 4 as peer dependencies, plus either the Anthropic or OpenAI SDK depending on your provider. Installation is straightforward:

npm install agentry

The framework ships as a single small package with minimal dependencies: react-reconciler, zustand, eventemitter3, and scheduler. The API surface is compact — you can learn the core concepts in under 30 minutes if you already know React and TypeScript.

However, documentation is sparse. The README on GitHub provides examples but no API reference, no migration guide, and no troubleshooting section. There are no tests visible in the repository, no CI/CD pipeline, and no contribution guidelines. For a framework at v0.1.0, this is expected but worth noting.

Use Cases and When to Use Agentry#

Agentry’s declarative, component-based approach shines in specific scenarios:

  • Complex agent hierarchies — When you need manager agents that delegate to specialist subagents with different models and tools
  • Dynamic tool access control — When tool availability depends on context, authentication state, or user role
  • Multi-provider agent systems — When different subtasks benefit from different LLM providers
  • Experimental and research projects — When you want to explore novel agent composition patterns
  • React-centric teams — When your team already thinks in components and wants to apply that mental model to agents

For production applications serving real users, Tambo or the Vercel AI SDK are safer choices today. Agentry is best suited for exploration, prototyping, and understanding what declarative agent composition looks like in practice.

Limitations and Maturity Concerns#

Agentry’s biggest limitation is its maturity. With 8 GitHub stars, 20 monthly npm downloads, and no visible test suite, the framework is effectively an experimental prototype. Key concerns include:

  • No production deployments — No evidence of the framework running in production
  • Single maintainer — Colin Dsouza is the sole contributor; bus factor of 1
  • No test coverage — No tests visible in the repository
  • No documentation beyond README — No API docs, no examples directory, no guides
  • React 19 requirement — Teams on React 18 cannot adopt Agentry without upgrading
  • Zod 4 requirement — Zod 4 is still in early adoption; many projects use Zod 3
  • No error handling guidance — How does the framework handle provider failures, rate limits, or malformed tool calls?
  • No streaming reliability guarantees — WebSocket reconnection, backpressure, and error recovery are undocumented

Verdict — Is Agentry Worth Adopting?#

Agentry is one of the most interesting experimental agent frameworks in the TypeScript ecosystem. Its core insight — that React’s component model maps naturally to agent composition — is genuinely novel and could influence how future agent frameworks are designed. The ability to define agents with JSX, manage tools with useState, compose subagents declaratively, and mix providers in a single tree is powerful.

However, Agentry is not production-ready. At v0.1.0 with 8 stars and no test coverage, it is a proof of concept — a glimpse of what declarative agent composition could look like, not a tool for building production systems. For teams building agent-powered applications today, the Vercel AI SDK or Tambo are the right choices. For teams curious about where agent frameworks are heading, Agentry is worth watching — and perhaps contributing to.

Frequently Asked Questions#

What is Agentry and how does it work?#

Agentry is a TypeScript framework that lets you define AI agents as React components using JSX syntax. It uses React’s reconciler to render agent execution trees, mapping React’s component lifecycle to agent lifecycle events. Agents are composed declaratively with components like <Agent>, <System>, <Tools>, and <Message>.

How is Agentry different from the Vercel AI SDK?#

The Vercel AI SDK provides tools for building AI-powered applications with generative UI — agents that can render React components. Agentry takes the opposite approach: the agent itself is a React component. Agentry also supports JSX-based agent definitions, dynamic tool mounting via React state, and cross-provider subagents as first-class features.

Does Agentry support multiple LLM providers?#

Yes. Agentry supports both OpenAI and Anthropic providers through a single declarative API. It also supports cross-provider subagents — an OpenAI parent agent can spawn Anthropic subagents and vice versa. Each subagent in the tree can use a different provider and model.

Is Agentry ready for production use?#

No. Agentry is at version 0.1.0 with 8 GitHub stars, approximately 20 monthly npm downloads, no visible test suite, and a single maintainer. It is best suited for experimentation, prototyping, and research. For production applications, consider the Vercel AI SDK or Tambo.

What are the prerequisites for using Agentry?#

Agentry requires React 19 and Zod 4 as peer dependencies, plus either the Anthropic SDK or OpenAI SDK depending on your chosen provider. The framework itself has minimal dependencies: react-reconciler, zustand, eventemitter3, and scheduler.
