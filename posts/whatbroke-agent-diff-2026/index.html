The Problem — Your Agent Can Fail Silently While Talking Perfectly#

AI agents are notoriously non-deterministic. Even at temperature 0 with a fixed random seed, small local models produce different tool call sequences between runs. This means your agent can output a perfectly coherent paragraph while silently calling the wrong tool, passing malformed arguments, or skipping a critical step entirely. The worst part? A human reading the final reply will never notice. The agent sounds confident, the text looks right, but the underlying behavior has broken. This is the “vibe check” trap — and it is the single most dangerous failure mode in production AI agent deployments today.

What Is Behavioral Diffing?#

Behavioral diffing is the practice of comparing two AI agent runs at the level of tool calls, argument values, execution order, latency, and cost — rather than comparing the natural language outputs. Instead of asking “does the reply sound right?”, behavioral diffing asks “did the agent call the same tools in the same order with the same arguments?”

This distinction matters because agent behavior is what produces real-world outcomes. A customer support agent that calls refund_order instead of escalate_ticket has failed regardless of how polite its closing message sounds. A code-generation agent that calls write_file with the wrong path has introduced a bug regardless of how well it explains the change. Behavioral diffing catches these failures at the tool-call level, before they reach production.

The approach draws from a well-established software engineering practice: snapshot testing. Just as frontend developers snapshot-render UI components to catch visual regressions, AI engineers can snapshot-record agent behavior to catch behavioral regressions. The key difference is that agent behavior is probabilistic, so a single snapshot is rarely enough — you need multiple samples to distinguish real regressions from normal agent flakiness.

WhatBroke — The Tool That Catches Silent Agent Regressions#

WhatBroke is an open-source CLI tool (TypeScript, MIT license) purpose-built for diffing AI agent behavior between two runs. Created by arthi-arumugam-git and released on July 22, 2026, it has quickly become one of the most practical tools in the emerging agent-testing ecosystem. The npm package whatbroke-cli (v0.5.0) ships with zero runtime dependencies — only picocolors for terminal output — making it trivially easy to install in any CI pipeline.

At its core, WhatBroke answers three questions:

  1. What changed? — Which tool calls appeared, disappeared, or changed between runs?
  2. Is it real? — Multi-sample diffing separates genuine regressions from pre-existing agent flakiness.
  3. Should I care? — Breaking, changed, and info classifications help you triage what matters.

How It Works: Record → Change → Diff#

The workflow is a straightforward three-step pipeline:

Step 1: Record a baseline. Run your agent scenarios with WhatBroke’s proxy recorder active. The recorder intercepts all LLM API calls via OPENAI_BASE_URL or ANTHROPIC_BASE_URL and saves the full trace — tool calls, arguments, responses, timing, and cost.

Step 2: Make your change. Swap the model, update the prompt, change the tool definitions, or modify the agent code.

Step 3: Diff against the baseline. Run the same scenarios again and let WhatBroke align the two runs by ID, align tool calls within each run, and produce a structured diff report. The output classifies every difference as:

  • Breaking — A tool call was removed, a required argument changed, or a critical step was skipped.
  • Changed — Arguments shifted, new tool calls appeared, or execution order changed.
  • Info — Timing, cost, or token count differences that don’t affect correctness.

Multi-Sample Diffing: Separating Signal from Agent Flakiness#

This is WhatBroke’s killer feature. A single run of a non-deterministic agent is meaningless — the agent might call search_knowledge_base before get_user_profile in one run and the reverse in another, both producing the correct final answer. If you diff single runs, you’ll see a “change” that was actually just normal variance.

WhatBroke solves this by running each scenario multiple times per version. In the published case studies, the tool uses 3 runs per version (9 run pairs total: 3 baseline × 3 changed). This turns anecdotes into rates: instead of “the tool call changed,” you get “in 6 out of 9 run pairs, the agent sent the tool’s own JSON schema as arguments instead of actual data.” A 6/9 rate is actionable; a single-run observation is noise.

The multi-sample approach also prevents a common anti-pattern: blaming pre-existing flakiness on your change. If the baseline already shows 2/3 runs diverging on a particular tool call, a 3/3 divergence after your change is not a regression — it’s the same flakiness. WhatBroke’s diff report surfaces this distinction automatically.

The Proxy Recorder: Zero-Code Trace Capture#

WhatBroke’s proxy recorder is the most elegant part of the tool. It requires zero code changes to your agent. You simply set an environment variable:

export OPENAI_BASE_URL=http://localhost:3000/proxy
# or
export ANTHROPIC_BASE_URL=http://localhost:3000/proxy

Then run your agent as normal. The proxy intercepts every API call, records the full request and response, and forwards it to the real provider. No SDK integration, no monkey-patching, no code changes. This works with any agent framework — LangChain, CrewAI, AutoGPT, custom implementations — because it operates at the HTTP transport layer.

For programmatic use, WhatBroke also provides SDKs for Node.js and Python (pip install whatbroke-recorder), giving you finer control over what gets recorded and when.

CI Integration: Fail the Build on Breaking Changes#

WhatBroke is designed from the ground up for CI/CD pipelines. The --fail-on flag accepts a severity level:

npx whatbroke-cli diff baseline.jsonl current.jsonl --fail-on breaking

This exits with a non-zero code if any breaking changes are detected, which means your CI system naturally treats it as a build failure. You can also use --fail-on changed for stricter enforcement or --fail-on never for informational-only mode.

The tool outputs machine-readable JSON for downstream processing and human-readable terminal output with color-coded severity levels. This makes it equally useful for local development (quick feedback) and automated pipelines (structured data).

Importing Existing Traces from Langfuse, LangSmith, OpenTelemetry#

WhatBroke doesn’t require you to use its proxy recorder. If you already have traces in Langfuse, LangSmith, or OpenTelemetry format, you can import them directly:

npx whatbroke-cli import langfuse --project my-agent --from 2026-07-01 --to 2026-07-26
npx whatbroke-cli diff baseline.jsonl current.jsonl

This is critical for teams that already invest in observability. You don’t need to choose between observability and testing — WhatBroke sits on top of your existing trace infrastructure and adds the diffing layer that observability tools lack.

Real-World Case Studies from WhatBroke#

The WhatBroke repository includes several published case studies that demonstrate exactly what the tool catches and why it matters. These are not synthetic examples — they are real regressions discovered during the tool’s own development and dogfooding.

The 3x Smaller Model Swap — JSON Schema as Arguments#

A team swapped from llama3.2:3b to llama3.2:1b — a 3x reduction in model size — expecting faster, cheaper inference with acceptable quality loss. WhatBroke’s diff revealed something alarming: in 6 out of 9 run pairs, the smaller model sent the tool’s own JSON schema as arguments instead of actual data.

The agent was calling search_database with the literal text of the tool’s parameter schema — field names, types, descriptions — instead of the actual search query. The final reply to the user was still coherent because the model generated plausible-sounding text about what it “would have” searched. A human reading the output would never catch this. The tool call was silently broken.

The team reverted the swap and chose a different optimization strategy. Without WhatBroke, this regression would have shipped to production.

The LiteLLM Proxy That Silently Dropped All Tool Calls#

In what may be the most cautionary tale in the case studies, a team migrated to LiteLLM’s streaming proxy with the ollama/ route. Every request returned HTTP 200. The agent appeared to work. WhatBroke’s diff told a different story: in all 4 scenarios, at 9 out of 9 run pairs, the proxy dropped every single tool call.

The streaming proxy was consuming the tool call tokens as text tokens, never delivering them to the agent. The agent received empty tool call arrays, proceeded as if no tools were needed, and generated a text-only response. The user saw a perfectly reasonable answer — just one that never actually executed any tools. The agent had been silently converted from a tool-using agent into a chatbot.

This case study is particularly important because it demonstrates that infrastructure changes — not just model swaps — can silently break agent behavior. A proxy upgrade, a routing change, or a new streaming implementation can all introduce regressions that no amount of manual testing will catch.

Same-Size Vendor Swap Changed More Than the Downgrade#

Perhaps the most surprising finding: swapping from llama3.2:3b to qwen2.5:3b — same model size, different vendor — introduced more behavioral changes than the 3x model downgrade. The vendor swap changed tool call ordering, argument formatting, and even which tools were called in several scenarios.

This finding upends a common assumption: that same-size models from different vendors are roughly interchangeable. They are not. Each model family has its own output distribution, its own tendency to format arguments differently, and its own “preferred” tool call patterns. A vendor swap requires the same testing rigor as a model upgrade or downgrade.

WhatBroke is the best choice when you need to answer “what changed?” quickly and reliably. It excels at catching silent regressions in tool call behavior, especially during model swaps, prompt changes, and infrastructure updates.

EvalView (124 GitHub stars, Apache-2.0, Python) is WhatBroke’s closest competitor. AgentRR and AgentReplay are debugging tools for understanding individual runs, not regression testing across versions. Use them when you need to understand why a specific run failed, not when you need to catch regressions across deployments.

The Diff-First Workflow: See What Changed, Then Judge It#

The most effective workflow combines behavioral diffing with evaluation:

  1. Diff first — Run WhatBroke to see exactly what changed between two versions.
  2. Triage — Classify each change as breaking, acceptable, or expected.
  3. Eval selectively — Run your evaluation suite only on the scenarios that actually changed.
  4. Ship with confidence — You know exactly what changed and whether it matters.

This is far more efficient than running a full eval suite on every change. Most changes don’t affect most scenarios. Why spend compute and time evaluating scenarios that didn’t change? Diff first, eval second.

The Model Swap Checklist — 20 Minutes to Production Confidence#

Based on WhatBroke’s case studies and the broader agent testing ecosystem, here is a reproducible checklist for any model change:

  1. Record baseline (5 minutes). Run each critical scenario 3 times with your current model. Save the traces.
  2. Swap the model (1 minute). Update the model identifier in your agent configuration.
  3. Record the new runs (5 minutes). Run the same scenarios 3 times with the new model.
  4. Diff the results (2 minutes). Run npx whatbroke-cli diff baseline.jsonl current.jsonl --fail-on breaking.
  5. Inspect breaking changes (5 minutes). For each breaking change, decide: is this a regression or an acceptable behavior shift?
  6. Run targeted evals (2 minutes). Evaluate only the scenarios that changed.
  7. Ship or revert. If no unacceptable regressions, deploy. Otherwise, revert and investigate.

Total: 20 minutes. This is the minimum viable process for any model change in production. Skipping it means you are shipping blind.

The Future of Agent Reliability Testing#

The agent testing ecosystem is evolving rapidly. Several trends are worth watching:

Standardized trace formats. As tools like WhatBroke, EvalView, and Langfuse converge on common trace schemas, the ability to mix and match tools will improve. OpenTelemetry is the most likely standard, but agent-specific extensions are still being defined.

Automated regression detection. Future versions of WhatBroke and similar tools will likely learn your agent’s “normal” behavior patterns and flag anomalies without requiring explicit baseline recording. This shifts from snapshot testing to anomaly detection.

Behavioral contracts. WhatBroke already supports basic behavior contracts for guardrails. Expect this to evolve into a full contract-testing paradigm where agents declare their expected behavior and tools verify compliance at runtime.

Multi-agent diffing. As multi-agent systems become more common, diffing tools will need to handle inter-agent communication patterns, delegation decisions, and coordination failures — not just individual agent tool calls.

Integration with fine-tuning pipelines. When you fine-tune a model for agentic tasks, behavioral diffing should be part of the evaluation pipeline. Did the fine-tune improve tool call accuracy or introduce new failure modes?

Conclusion — Stop Vibing, Start Diffing#

The era of deploying AI agents based on “it looks good to me” is over. Agents are non-deterministic, infrastructure is fragile, and silent failures are the norm — not the exception. WhatBroke provides a practical, open-source answer to the question every AI engineer should be asking: “What actually changed?”

With zero-code recording, multi-sample diffing, CI integration, and real-world case studies that demonstrate exactly what can go wrong, WhatBroke is the tool that turns agent testing from a vibe check into an engineering discipline. Install it, record a baseline, make your next change, and see for yourself what your agent is really doing.

FAQ#

Q1: What is WhatBroke and what problem does it solve? WhatBroke is an open-source CLI tool that diffs AI agent behavior between two runs. It solves the problem of silent regressions — changes in tool calls, arguments, costs, and execution order that human review misses because the agent’s text output still looks correct.

Q2: How does WhatBroke differ from LangSmith or Langfuse? LangSmith and Langfuse are observability platforms for monitoring and debugging agent runs. WhatBroke is a testing tool that compares two sets of runs and produces structured diff reports. They are complementary: you can import Langfuse or LangSmith traces into WhatBroke for diffing.

Q3: Does WhatBroke require code changes to my agent? No. The proxy recorder works by setting OPENAI_BASE_URL or ANTHROPIC_BASE_URL environment variables — zero code changes. For programmatic use, WhatBroke also provides Node.js and Python SDKs.

Q4: How does multi-sample diffing work? WhatBroke runs each scenario multiple times per version (e.g., 3 baseline runs × 3 changed runs = 9 run pairs). This turns single observations into rates — “6/9 runs showed this change” — and distinguishes genuine regressions from pre-existing agent flakiness.

Q5: Can WhatBroke integrate with my CI/CD pipeline? Yes. The --fail-on breaking flag causes WhatBroke to exit with a non-zero code when breaking changes are detected, which naturally fails your CI build. It also supports --fail-on changed for stricter enforcement and outputs machine-readable JSON for downstream processing.
