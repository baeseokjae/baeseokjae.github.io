Gemini API Temperature, Top-P, and Top-K Deprecated 2026 — What Developers Need to Know

Google deprecated temperature, top-p, and top-k in Gemini 3.6 Flash and 3.5 Flash-Lite. Here is what replaces them and how to migrate safely.

Overview — What Changed and Why It Matters#

On July 21, 2026, Google released Gemini 3.6 Flash and Gemini 3.5 Flash-Lite with a sweeping set of API changes that break nearly every existing integration. The most impactful change is the deprecation of three core sampling parameters — temperature, top-p, and top-k — which are now silently accepted and ignored by the API. This means your existing code continues to return HTTP 200 responses, but the parameters you relied on for controlling output randomness, determinism, and creativity no longer have any effect. Google has shifted its design philosophy from developer-controlled sampling to model-autonomous output optimization, arguing that modern reasoning models produce better results when left at their default settings. This guide covers all five breaking changes, explains what replaces each deprecated parameter, and provides a step-by-step migration checklist to help you update your codebase safely.

The Five Breaking Changes in Gemini 3.6 Flash and 3.5 Flash-Lite#

The Gemini 3.x release introduces five distinct API changes that developers must address during migration. They range from silent no-ops to hard HTTP 400 errors, and each requires a different migration strategy.

The silent deprecation of temperature, top-p, and top-k is the most dangerous change because it produces no error. Pipelines that rely on temperature=0 for deterministic output will continue receiving 200 OK responses while losing the determinism guarantee entirely. The four hard-error changes are easier to catch because they fail immediately during testing.

The Silent Danger — Why temperature/top_p/top_k Being Ignored Is Worse Than an Error#

When an API returns an error, you know something is wrong. When it silently ignores your parameters, your application degrades without any signal. This is precisely the situation with temperature, top-p, and top-k in Gemini 3.6 Flash and 3.5 Flash-Lite.

Consider a production pipeline that sets temperature=0 to ensure consistent, deterministic responses for structured data extraction. Before the migration, this pipeline produces identical outputs for identical inputs. After switching to a Gemini 3.x model, the same code runs without errors — but the temperature parameter is ignored, and the model uses its default sampling behavior. Outputs become non-deterministic, and the pipeline produces different results on each call. The developer has no warning, no error log, and no obvious signal that the behavior has changed.

Google’s official documentation states that the company “strongly recommends keeping temperature at default 1.0 for all Gemini 3 models” and warns that “changing temperature below 1.0 may cause unexpected behavior like looping or degraded performance.” In future model generations, supplying these parameters will return an HTTP 400 error, but for now they are silently accepted.

According to the evolink.ai migration guide, “the silent no-op on temperature is the most dangerous change — pipelines relying on temperature=0 for determinism will keep getting 200 OK while losing the guarantee.” This makes thorough testing and code auditing essential before any production migration.

What Replaces Temperature? System Instructions and Structured Outputs#

Google’s replacement for temperature tuning is a combination of system instructions and structured outputs. Instead of lowering temperature to make the model more deterministic, you now guide the model’s behavior through explicit instructions and constrain its output format.

System instructions allow you to set the model’s behavior, tone, and constraints at the start of a conversation. For example, instead of setting temperature=0.2 for a factual Q&A bot, you would include a system instruction like “Provide concise, factual answers based only on the provided context. Do not add speculation or creative elements.”

Structured outputs (via response_schema or function calling) constrain the model to produce output in a specific JSON schema. This is the most reliable way to achieve deterministic, parseable output without temperature control. By defining the exact shape of the response, you eliminate the variability that temperature was meant to control.

The labmemo.com analysis notes that “Google’s design philosophy shift” is to “provide optimal output by default,” and that “the rise of reasoning models reduces the need for developers to fine-tune sampling parameters.” This represents a fundamental change in how Google expects developers to interact with its models — moving from low-level parameter tuning to high-level behavioral guidance.

thinking_budget → thinking_level Migration#

The thinking_budget parameter, which controlled how many tokens the model could use for internal reasoning before generating a response, has been replaced by the thinking_level parameter. The new parameter accepts a string value rather than an integer, making it simpler to configure.

Old ParameterNew Parameter
thinking_budget: 1024thinking_level: “low”
thinking_budget: 4096thinking_level: “medium”
thinking_budget: 16384thinking_level: “high”

The critical migration rule is: do not send both parameters. Sending thinking_budget together with thinking_level returns an HTTP 400 error. You must remove thinking_budget from your requests and replace it with the equivalent thinking_level value.

Google’s Interactions API documentation recommends using the new stateful mode with previous_interaction_id to maintain reasoning context across API calls, which can reduce the need for large thinking budgets in multi-turn conversations.

candidate_count Removal and Output Variety Alternatives#

The candidate_count parameter, which allowed developers to request multiple response candidates from a single API call, is not supported in Gemini 3.x models. Attempting to use it returns an HTTP 400 error.

To generate multiple output options, developers now have two alternatives:

  1. Make multiple API calls with different system instructions or seed values. This is the simplest approach and works with any model version.
  2. Use the Interactions API with stateful mode to explore different reasoning paths. Google recommends the Interactions API over the legacy generateContent API for new development.

The removal of candidate_count aligns with Google’s broader simplification of the API surface. As reasoning models become more capable, the need to sample multiple candidates and pick the best one diminishes — the model’s internal reasoning process handles this optimization.

Function Calling Stricter Requirements (call_id and name)#

Function calling in Gemini 3.x now requires that every FunctionResponse include both call_id and name fields. Previously, these fields were optional in some implementations. Omitting either field now returns an HTTP 400 error.

This change affects any code that constructs FunctionResponse objects manually or uses a client library that does not automatically populate these fields. The call_id must match the ID of the corresponding FunctionCall from the model, and the name must match the function name exactly.

To migrate, audit all function calling code paths and ensure that every FunctionResponse includes both fields. Most SDKs have been updated to handle this automatically, but custom implementations and raw HTTP callers need explicit updates.

Last Turn Role ‘model’ Restriction#

In Gemini 3.x, the last turn in a request must not have the role ‘model’. If the last message in your conversation history has role ‘model’, the API returns an HTTP 400 error.

This change affects applications that maintain conversation state and append the model’s previous response as the last message before sending a new request. The fix is to ensure that the last message in every request has role ‘user’ or role ‘system’ (if supported), and to trim or restructure conversation histories accordingly.

Migration Checklist — Step by Step#

Follow this checklist to migrate your Gemini API integration safely:

  1. Audit all API call sites — Search your codebase for every occurrence of temperature, top_p, top_k, candidate_count, and thinking_budget parameters.
  2. Remove or comment out deprecated parameters — For temperature, top_p, and top_k, remove them from your requests. They are ignored, but removing them makes your code future-proof.
  3. Replace thinking_budget with thinking_level — Map your existing thinking budget values to the equivalent thinking_level string (“low”, “medium”, or “high”).
  4. Update FunctionResponse construction — Ensure every FunctionResponse includes call_id and name fields.
  5. Fix conversation history — Ensure the last message in every request has role ‘user’, not ‘model’.
  6. Replace temperature=0 with structured outputs — For deterministic behavior, implement response_schema or function calling with strict schema validation.
  7. Replace temperature>0 with system instructions — For creative control, use system instructions to guide tone and style.
  8. Update candidate_count calls — Replace single-call candidate generation with multiple API calls or the Interactions API.
  9. Run smoke tests — Test each change in a staging environment before production deployment.
  10. Monitor production behavior — Watch for changes in output quality, determinism, and error rates after migration.

How to Find Every Call Site in Your Codebase#

Finding all deprecated parameter usages is the first and most critical step. Here are practical approaches for different languages:

Python: grep -rn "temperature\|top_p\|top_k\|candidate_count\|thinking_budget" --include="*.py" .

JavaScript/TypeScript: grep -rn "temperature\|topP\|topK\|candidateCount\|thinkingBudget" --include="*.{js,ts,jsx,tsx}" .

For Google AI Python SDK: Search for genai.GenerativeModel instantiation and generate_content or send_message calls. The deprecated parameters may be passed as keyword arguments or in the generation_config dictionary.

For raw HTTP callers: Search for "temperature", "top_p", "top_k", "candidate_count", and "thinking_budget" in your JSON payload construction code.

For the Vertex AI SDK: Search for GenerationConfig objects and predict method calls. The deprecated parameters may be set as attributes on the config object.

Create a tracking spreadsheet or issue list with each call site, its migration status, and any notes about the expected behavior change. This systematic approach prevents missed call sites from causing production issues.

Smoke Test Plan Before Deploying to Production#

Before deploying your migrated code to production, run these smoke tests:

  1. Basic request test — Send a simple request without any deprecated parameters. Verify you receive a 200 OK response with valid content.
  2. thinking_level test — Send a request with thinking_level=“low” and verify the response includes thought content. Repeat for “medium” and “high”.
  3. Structured output test — Send a request with response_schema defined and verify the output matches the schema exactly.
  4. Function calling test — Send a request with a function declaration, respond with a FunctionResponse that includes call_id and name, and verify the model processes it correctly.
  5. Conversation history test — Send a multi-turn conversation where the last message has role ‘user’. Verify it works. Then test with role ‘model’ as the last turn and confirm you get HTTP 400.
  6. Deprecated parameter test — Send a request with temperature=0.5 and verify it is accepted (200 OK) but has no effect on output. Compare outputs with and without the parameter.
  7. Regression test — Compare outputs from your old model and the new model for 10-20 representative inputs. Document any differences in quality, style, or accuracy.
  8. Error handling test — Verify your error handling code correctly processes HTTP 400 responses for invalid parameter combinations.

Run these tests in a staging environment with the same model version you will use in production. The agentpedia.codes guide recommends migrating “behind an evaluation flag rather than changing model string globally,” allowing you to compare old and new behavior side by side.

FAQ — Common Developer Questions#

Q: Will my existing code break immediately if I switch to Gemini 3.6 Flash? A: It depends on which parameters you use. If you only use temperature, top-p, or top-k, your code will continue to work but those parameters will be silently ignored. If you use thinking_budget, candidate_count, FunctionResponse without call_id/name, or have a ‘model’ role as the last turn, you will receive HTTP 400 errors. The silent no-op on temperature is the most dangerous because it causes behavioral degradation without any error signal.

Q: How do I achieve deterministic output without temperature=0? A: Use structured outputs with response_schema or function calling to constrain the model’s output format. Combine this with precise system instructions that specify the exact behavior you expect. For example, a system instruction like “Extract the following fields from the text and return them in the specified JSON format. Do not add any commentary or variation” combined with a response_schema produces highly consistent results.

Q: What is the difference between thinking_budget and thinking_level? A: thinking_budget was an integer that controlled how many tokens the model could use for internal reasoning. thinking_level is a simpler string parameter with three values: “low”, “medium”, and “high”. You must not send both parameters together — doing so returns an HTTP 400 error. Remove thinking_budget and replace it with the equivalent thinking_level value.

Q: Is there any way to still use temperature with Gemini 3.x models? A: No. Temperature, top-p, and top-k are deprecated and silently ignored in Gemini 3.6 Flash and 3.5 Flash-Lite. Google’s official documentation states that the company “strongly recommends keeping temperature at default 1.0 for all Gemini 3 models.” In future model generations, supplying these parameters will return an HTTP 400 error. The recommended alternatives are system instructions for behavioral control and structured outputs for format control.

Q: How much money will I save by migrating to Gemini 3.6 Flash? A: Gemini 3.6 Flash offers a 16% reduction in output token pricing compared to Gemini 3.5 Flash — from $9.00 to $7.50 per million output tokens. Input pricing remains unchanged at $1.50 per million tokens. For applications with high output token consumption, this represents meaningful savings. For example, an application consuming 100 million output tokens per month would save $150 per month by migrating from 3.5 Flash to 3.6 Flash.

Summary — What Developers Must Do Now#

The Gemini 3.x API changes represent a significant shift in how Google expects developers to interact with its language models. The deprecation of temperature, top-p, and top-k marks the end of an era where developers could fine-tune sampling behavior at the parameter level. The new paradigm relies on system instructions, structured outputs, and the model’s built-in reasoning capabilities to produce optimal results.

Here is your action plan:

  1. Audit immediately — Search your entire codebase for all five deprecated parameters. Create a complete inventory of every call site.
  2. Test in isolation — Migrate behind an evaluation flag so you can compare old and new behavior side by side.
  3. Replace, don’t just remove — For temperature-dependent pipelines, implement structured outputs and system instructions as replacements. Do not simply delete the parameter and hope for the best.
  4. Update SDKs — Ensure you are using the latest version of the Google AI Python SDK, Node.js SDK, or Vertex AI SDK, all of which have been updated to handle the new parameter requirements.
  5. Monitor after deployment — Watch for changes in output quality, determinism, and error rates for at least one week after migration.

The Hacker News discussion on this deprecation scored 119 points with 40 comments, reflecting the community’s concern about the silent nature of the temperature deprecation. By following the migration checklist in this guide, you can avoid the silent failure trap and ensure your Gemini API integration continues to work reliably.
