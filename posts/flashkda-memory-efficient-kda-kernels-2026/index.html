What is FlashKDA? — Overview and Motivation#

FlashKDA is MoonshotAI’s high-performance CUDA kernel implementation of Kimi Delta Attention (KDA), a linear attention mechanism designed to eliminate the quadratic complexity bottleneck of standard attention in large language models. Built on NVIDIA CUTLASS and targeting Hopper (SM90+) GPUs, FlashKDA delivers production-grade memory efficiency for both training and inference, reducing KV cache by up to 75% while achieving 15%+ end-to-end speedups over monolithic fused kernels. It powers the Kimi K3 model at 2.8 trillion parameters and integrates seamlessly with the Flash Linear Attention (FLA) ecosystem.

Kimi Delta Attention (KDA) — The Algorithm Behind the Kernel#

Kimi Delta Attention is a refined variant of Gated DeltaNet, a linear attention architecture that replaces the softmax-based attention mechanism with a recurrent state update. Unlike standard multi-head attention (MHA) which stores a growing KV cache of all previous tokens, KDA compresses the context into a fixed-size recurrent state that updates incrementally as each new token is processed.

The core idea is straightforward: instead of computing attention scores between every pair of tokens (O(n²) complexity), KDA maintains a compact hidden state that evolves through a gated delta rule. Each new token contributes an update to this state, and the output is computed by reading from the current state. This reduces the memory footprint from O(n × d) for KV cache to O(d²) for the recurrent state, where d is the head dimension.

KDA introduces a more efficient gating mechanism compared to the original DeltaNet. The gate controls how much of the previous state is retained versus overwritten by new information, giving the model fine-grained control over context retention. This gating is what enables KDA to handle sequences up to 1 million tokens without the memory explosion that plagues standard attention.

Architecture Deep Dive — Chunk Size, Fusion Strategy, and Precision#

Why CHUNK=16 Instead of CHUNK=64#

The chunk size is one of the most consequential design decisions in linear attention kernels. Flash Linear Attention (FLA), the reference implementation, uses CHUNK=64. FlashKDA deliberately chooses CHUNK=16, and this choice has deep technical justification.

A smaller chunk size means fewer tokens are processed together in each intra-chunk step, which reduces the dynamic range of intermediate values. This is critical for numerical stability when working with bf16 precision. At CHUNK=64, the accumulated values can span a wide dynamic range, requiring intra-chunk rescaling tricks to maintain precision. FlashKDA’s CHUNK=16 eliminates the need for these rescaling operations entirely, because the values stay within bf16’s representable range.

The trade-off is parallelism: larger chunks expose more parallelism within each chunk. However, FlashKDA compensates through its two-kernel fusion strategy, which recovers parallelism along different axes. The net result is better numerical stability without sacrificing throughput.

Two-Kernel Pipeline: K1 and K2#

FlashKDA decomposes the attention computation into two specialized kernels, each optimized for a different parallelism axis:

K1 (Token-Parallel): This kernel operates across the token dimension. Each thread block processes one token’s contribution to the recurrent state update. Because tokens are independent in the forward pass of a linear attention layer, K1 achieves near-perfect scaling across the sequence length dimension. It computes the gated delta update for each token and writes the updated state to shared memory.

K2 (Head-Parallel): This kernel operates across the attention head dimension. After K1 has computed the updated states, K2 reads those states and computes the final output for each head. Head parallelism is natural because attention heads are independent by design.

The two-kernel split yields at least 15% end-to-end speedup over a single fused kernel. The reason is that a monolithic kernel must serialize token and head operations, creating a bottleneck where one dimension waits for the other. By splitting, FlashKDA keeps both the SM tensor cores and the memory subsystem fully utilized.

This is a practical lesson in GPU kernel design: splitting computation along natural parallelism axes can outperform monolithic fusion, even though fusion is conventionally seen as the optimization ideal.

Numerical Precision: bf16 State, fp16 Inverse, fp32 FMA#

FlashKDA employs a three-tier precision strategy that balances throughput against numerical accuracy:

  1. Recurrent state stored in bf16: The on-chip recurrent state is maintained in bf16, which provides 8 bits of exponent and 7 bits of mantissa. This is sufficient for the state values, which evolve gradually through gated updates. Storing in bf16 rather than fp32 cuts shared memory usage in half — a critical savings on Hopper GPUs where shared memory is a scarce resource.

  2. 16×16 matrix inversion in fp16: The matrix inversion step required by the delta update rule operates on 16×16 blocks. FlashKDA computes this inversion in fp16 rather than bf16 because the inverse elements are mathematically bounded within the range [-1, 1]. This bounded range means fp16’s limited exponent range is not a problem, and fp16’s higher precision (11 mantissa bits vs bf16’s 7) actually improves inversion accuracy.

  3. FMA accumulation in fp32: All fused multiply-add (FMA) operations that accumulate over the sequence dimension are performed in fp32. This is the standard practice for numerical stability in attention kernels — the accumulator needs the extra precision to avoid error accumulation across thousands of tokens.

The result is a precision-engineering sweet spot: no measurable accuracy loss compared to a full fp32 reference, with 2× shared memory savings and maximum tensor core utilization.

Performance Benchmarks and Speedups#

FlashKDA’s performance numbers are compelling across multiple dimensions:

KV Cache Reduction: KDA reduces KV cache by up to 75% compared to full attention mechanisms. For a 1M-token sequence with 64 attention heads and 128-dimensional head size, standard MHA requires approximately 64 GB of KV cache. KDA’s recurrent state approach brings this down to roughly 16 GB — a difference that determines whether a model fits on a single H100 node.

Token Processing Speed: Kimi Linear, which uses KDA as its core attention mechanism, achieves 6.3× faster time-to-first-token (TTOT) and tokens-per-second (TPOT) compared to Multi-head Latent Attention (MLA) at 1M-token sequences. This is because KDA’s recurrent state eliminates the need to attend over the entire prefix on every generation step.

End-to-End Throughput: The two-kernel split (K1 + K2) delivers at least 15% end-to-end speedup over a single fused kernel implementation. This has been verified on H100 (SM90) GPUs with sequence lengths ranging from 8K to 128K tokens.

RULER Benchmark: At 128K context length, KDA-based models achieve a 3.98× speedup over full attention while maintaining competitive accuracy on the RULER long-context evaluation suite.

Integration with Flash Linear Attention and Kimi-Linear#

FlashKDA is not a standalone project — it is designed as a backend for the Flash Linear Attention (FLA) library, which is the dominant open-source linear attention kernel ecosystem with over 5,479 GitHub stars and 617 forks.

The integration works through FLA’s chunk_kda dispatch mechanism. When a user calls FLA’s chunked KDA operation, the library checks whether FlashKDA is available (i.e., the system has a compatible Hopper GPU and CUDA 12.9+). If so, it dispatches to the FlashKDA CUDA kernel. If not, it falls back to the Triton-based implementation.

Users can explicitly opt out of FlashKDA by setting the environment variable FLA_FLASH_KDA=0, which forces the Triton fallback. This is useful for debugging or for running on Ampere (SM80) GPUs where FlashKDA is not yet supported.

Kimi-Linear, MoonshotAI’s hybrid linear attention architecture, uses KDA as its core attention mechanism. The stack is layered: Kimi-Linear → KDA → FlashKDA (CUDA) or FLA Triton (fallback). This means FlashKDA’s performance benefits flow directly to any model built on Kimi-Linear.

FlashKDA in Production: Powering Kimi K3#

FlashKDA is not a research prototype — it is production-hardened and deployed at scale. The Kimi K3 model, a 2.8 trillion parameter Mixture-of-Experts (MoE) architecture with 104 billion activated parameters per token, uses KDA as its attention mechanism, and FlashKDA as the kernel backend.

Kimi K3 achieves a 2.5× scaling efficiency improvement over Kimi K2 through the combination of KDA, Attention Residuals (AttnRes), and Stable LatentMoE. The model supports a 1-million-token context window, which would be prohibitively expensive with standard attention. FlashKDA’s memory efficiency is what makes this context length feasible on production GPU clusters.

The model activates 16 of 896 experts per token through its Stable LatentMoE mechanism, and KDA’s reduced memory footprint means more GPU memory is available for expert parameters and activations. This is a compounding efficiency gain: memory-efficient attention frees resources for larger model capacity.

Requirements and Limitations#

FlashKDA has specific hardware and software requirements that constrain its deployment:

Hardware: Requires NVIDIA Hopper architecture (SM90+) — specifically H100, H200, or B200 GPUs. Ampere (SM80) and Ada Lovelace (SM89) GPUs are not supported. This is because FlashKDA leverages Hopper-specific features including Tensor Memory Accelerator (TMA), warp-group specialization, and fourth-generation tensor cores.

Software: Requires CUDA 12.9 or later and CUTLASS 3.x. The dependency on CUTLASS means the build system must have the CUTLASS headers available. The project is built as a Python package with CUDA extensions, so a working CUDA toolchain is essential.

Head Dimension Constraint: FlashKDA currently requires K=V=128. This is a limitation of the current implementation — the 16×16 matrix inversion and the shared memory layout are hardcoded for this head dimension. Support for other head dimensions (e.g., 64, 96) is not yet available.

Ecosystem Lock-in: FlashKDA is designed specifically for KDA. It cannot be used for other linear attention variants (e.g., Mamba, Based, or ReLU attention) without significant modification. Users who want a general linear attention kernel library should use FLA Triton.

Conclusion — Why FlashKDA Matters for LLM Inference#

FlashKDA represents a significant step forward in production-grade linear attention kernels. Its CHUNK=16 design, two-kernel fusion strategy, and three-tier precision approach demonstrate that careful engineering at the kernel level can deliver substantial real-world gains.

For LLM practitioners, FlashKDA matters because it makes long-context inference practical. The 75% KV cache reduction and 6.3× faster TPOT at 1M tokens mean that models can handle book-length contexts, multi-turn conversations with full history, and large-document analysis without requiring specialized hardware or exotic quantization schemes.

The fact that FlashKDA powers Kimi K3 — one of the largest open-weight models ever released — validates that these techniques work at scale. It is not a theoretical paper optimization; it is a production kernel running on real GPU clusters.

As the linear attention paradigm continues to mature, FlashKDA sets a new standard for what is possible with CUDA kernel engineering. The open-source ecosystem around KDA — FlashKDA, Kimi-Linear, and FLA integration — provides a complete stack from kernel to model, making these advances accessible to the broader AI community.

FAQ#

What is FlashKDA and how does it differ from standard attention?#

FlashKDA is MoonshotAI’s CUDA kernel implementation of Kimi Delta Attention (KDA), a linear attention mechanism that replaces the quadratic-complexity softmax attention with a recurrent state update. Unlike standard attention which stores a growing KV cache of all previous tokens, KDA compresses context into a fixed-size state, reducing memory from O(n×d) to O(d²).

What hardware do I need to run FlashKDA?#

FlashKDA requires NVIDIA Hopper architecture GPUs (SM90+), specifically H100, H200, or B200. It also requires CUDA 12.9 or later and CUTLASS 3.x. Ampere (A100) and Ada Lovelace (RTX 4090) GPUs are not supported. For those GPUs, the FLA Triton fallback path is available.

How much faster is FlashKDA compared to standard attention kernels?#

FlashKDA delivers a 3.98× speedup on the RULER benchmark at 128K context length compared to full attention. Its two-kernel split (K1 + K2) provides at least 15% end-to-end speedup over a single fused kernel. At 1M-token sequences, Kimi Linear with KDA achieves 6.3× faster TPOT compared to Multi-head Latent Attention (MLA).

Can I use FlashKDA with my existing model or training pipeline?#

FlashKDA integrates as a backend for the Flash Linear Attention (FLA) library. If your model uses FLA’s chunked KDA operation and runs on Hopper GPUs with CUDA 12.9+, FlashKDA is automatically used. You can opt out with the FLA_FLASH_KDA=0 environment variable. Direct integration outside of FLA is not currently supported.

What are the limitations of FlashKDA?#

The main limitations are: (1) Hopper GPU requirement — no Ampere or Ada support; (2) head dimension locked to K=V=128; (3) KDA-specific — cannot be used for other linear attention variants; (4) CUDA 12.9+ requirement which may not be available in all environments. These limitations are expected to ease as the project matures.
