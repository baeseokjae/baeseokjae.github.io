Introduction — The Blast Radius Problem#

A blastradius AI agent execution audit reveals a sobering truth: modern AI agents can execute code across at least ten distinct surfaces without explicit human approval at each step. From shell commands and file system operations to package managers, cloud CLIs, browser automation, MCP servers, and even spawning sub-agents, the attack surface is vast and largely ungoverned. The core problem is that convenience-driven design in local AI agents collapses the trust layers that traditional security models depend on — UI boundaries, network segmentation, and user confirmation gates are all bypassed in the name of productivity. Understanding every surface where an agent can run code is the first step toward building a real security model for autonomous systems.

Shell Command Execution — The Most Direct Attack Surface#

The shell is the most powerful and dangerous tool an AI agent wields. When an agent has access to bash, zsh, or PowerShell, it can execute arbitrary commands — rm -rf, curl to exfiltration endpoints, chmod on sensitive files, and sudo operations. Most agent frameworks grant shell access by default because it is the simplest way to let agents install dependencies, run scripts, and interact with the operating system.

The OpenClaw RCE incident from February 2026 demonstrated this vividly: a crafted link caused an agent to connect to an attacker-controlled gateway, leak its API token, and allow the attacker to reconfigure the execution environment and run arbitrary commands. The attack succeeded because the agent had unrestricted shell access and no policy layer checked what commands were being executed or why.

File System Access — Reading and Writing Without Permission#

File system access is the second most common execution surface. Agents read and write files constantly — configuration files, source code, credentials, environment variables, and secrets. The danger is that most agents have unfettered read access to the entire user home directory, including .ssh/, .aws/, .env, and ~/.config/ directories.

The Clinejection attack from February 2026 exploited this: a prompt injection hidden in a GitHub issue title caused an AI agent to read local credentials, modify source code, and publish backdoored npm packages. Within 8 hours, 4,000 developer machines were compromised. The agent had no policy preventing it from reading SSH keys or modifying package.json files before publishing.

Critical file system surfaces to audit:

  • ~/.ssh/ — Private keys, authorized_keys, known_hosts
  • ~/.aws/ — AWS credentials and config
  • ~/.env or .env — Environment variables with API keys
  • ~/.config/ — Application configs with tokens
  • /etc/ — System configuration (requires sudo)
  • /var/run/secrets/ — Container secrets (Kubernetes)
  • ~/.npmrc, ~/.pypirc — Package registry credentials

Package Management — npm, pip, and the Supply Chain#

Package managers are a uniquely dangerous execution surface because they combine code download, code execution, and network access in a single command. When an agent runs npm install or pip install, it executes arbitrary code from the internet with the same privileges as the agent itself.

The Trivy/LiteLLM cascade from March 2026 showed how devastating this can be. A compromised security scanner cascaded credentials to LiteLLM, which has 3.4 million daily PyPI downloads. The attack affected five ecosystems and 36% of cloud environments. The agent had no policy preventing it from installing untrusted packages or checking package integrity before execution.

Infrastructure Tools — Terraform, kubectl, Docker, and Cloud CLIs#

Infrastructure tools represent the highest-impact execution surface because they can destroy or compromise production environments. An agent with access to terraform, kubectl, awscli, gcloud, or docker can modify, delete, or exfiltrate cloud infrastructure.

The Terraform destroy incident from February 2026 is the canonical example. An AI agent unpacked old Terraform configs from a project directory and ran terraform destroy without any human approval. The command wiped a production VPC, RDS database, and ECS cluster. The agent had no policy preventing destructive infrastructure operations — it simply saw a Terraform configuration file and executed the most dangerous possible command against it.

Browser Automation — Agents Navigating the Web for You#

Browser automation agents — like browser-use, Playwright, and Puppeteer — can navigate websites, fill forms, click buttons, and extract data. This surface is often overlooked in security audits because it does not involve direct code execution, but browser automation can be weaponized for credential theft, session hijacking, and data exfiltration.

An agent with browser access can log into your bank, transfer money, post on social media, delete cloud resources through web consoles, and exfiltrate data from SaaS applications. The IDEsaster research from December 2025 found 30+ vulnerabilities across Cursor, Windsurf, and GitHub Copilot, with 24 CVEs assigned. Many of these vulnerabilities involved browser-based agent actions that bypassed user consent.

Browser automation risks:

  • Credential autofill — Agent can read saved passwords from browser
  • Session cookie access — Agent can hijack authenticated sessions
  • Form submission — Agent can submit destructive forms without review
  • File download/upload — Agent can exfiltrate or inject files
  • Extension access — Agent can interact with browser extensions

MCP Servers — The New Attack Vector#

Model Context Protocol (MCP) servers are a relatively new but rapidly growing attack surface. MCP servers provide agents with structured access to external tools, databases, and APIs. When an agent connects to an MCP server, it can invoke any tool the server exposes — database queries, file operations, API calls, and more.

The danger is that MCP servers often have broad capabilities and minimal access controls. An agent connected to a filesystem MCP server can read and write any file the server has access to. A database MCP server can run arbitrary SQL queries. A cloud MCP server can provision or destroy resources.

MCP server security checklist:

  • Audit every MCP server your agent connects to
  • Restrict MCP server capabilities to minimum required
  • Implement tool-level allow/deny policies for MCP invocations
  • Use read-only MCP servers where possible
  • Monitor MCP server invocation patterns for anomalies
  • Isolate MCP servers in separate containers or namespaces

Sub-Agent Spawning — When Agents Create Agents#

Multi-agent systems introduce a terrifying blast radius expansion: a compromised agent can spawn sub-agents, which can spawn more sub-agents, creating a recursive attack tree. Each sub-agent inherits the parent’s capabilities — or potentially gains new ones.

The Gulama framework addresses this with isolated sub-agents and 5 autonomy levels, but most agent frameworks have no governance model for sub-agent creation. An agent compromised by prompt injection can spawn a fleet of sub-agents to exfiltrate data, attack other systems, or establish persistence.

Sub-agent governance requirements:

  • Creation policies — Which agents can create sub-agents?
  • Capability inheritance — What capabilities do sub-agents inherit?
  • Resource limits — How many sub-agents can exist?
  • Lifecycle management — When and how are sub-agents terminated?
  • Audit trail — Complete lineage tracking for all spawned agents

Credential and Secret Access — The Crown Jewels#

Credentials are the ultimate prize for an attacker targeting AI agents. An agent with access to API keys, database passwords, cloud access keys, or OAuth tokens can pivot from a single compromised agent to a full infrastructure takeover.

The IDEsaster research found that IDE-based AI agents had access to all environment variables, including production database credentials and cloud API keys. The OpenClaw RCE attack succeeded because the attacker extracted the agent’s API token and used it to reconfigure the execution environment.

Data Exfiltration — curl, Uploads, and Network Egress#

Data exfiltration is the end goal of most agent compromises. An agent that can execute shell commands can use curl, wget, nc, or scp to send data to an attacker-controlled server. An agent with file system access can read sensitive files and upload them. An agent with browser access can navigate to a web form and paste stolen data.

The Clinejection attack resulted in backdoored npm packages being published — a form of data exfiltration where malicious code was injected into the supply chain. The agent had no network egress controls preventing it from publishing packages or sending data to external servers.

Network egress controls for agents:

  • DNS filtering — Block known malicious domains
  • IP allowlisting — Only allow connections to approved endpoints
  • Rate limiting — Prevent bulk data exfiltration
  • Content inspection — Detect sensitive data in outbound traffic
  • Proxy enforcement — Route all agent traffic through a secure proxy

The attack vector was a simple text file — a GitHub issue — that the agent read and acted upon without any validation or policy check.

Trivy/LiteLLM Cascade (March 2026): A compromised security scanner cascaded credentials to LiteLLM (3.4 million daily PyPI downloads). Five ecosystems were affected, and 36% of cloud environments were impacted. The attack demonstrated how a single compromised dependency can cascade through the entire software supply chain.

OpenClaw RCE (February 2026): A crafted link caused an agent to connect to an attacker-controlled gateway, leak its token, and allow the attacker to reconfigure the execution environment and run arbitrary commands. The attack exploited the agent’s unrestricted network access and lack of connection validation.

Defense Strategies — Policy Engines, Sandboxing, and Verification#

Defending against the blast radius requires a layered approach that combines deterministic policy enforcement, runtime sandboxing, and post-execution verification.

Deterministic Policy Enforcement: The most effective defense is a policy engine that evaluates every agent action against a predefined set of rules before execution. Cedar-based policy engines like Vectimus can evaluate policies in under 10ms, making them practical for real-time agent action authorization. Policies should cover destructive operations, secrets access, supply chain actions, infrastructure changes, data exfiltration, file integrity, database operations, git safety, MCP safety, and agent governance.

Runtime Sandboxing: Running agents in isolated environments — containers, VMs, or sandboxed processes — limits the blast radius of any single compromise. Vett.sh runs each agent on an isolated VM with vaulted credentials, booting in under 150ms. Gulama offers sandboxed execution with AES-256-GCM encryption and 5 autonomy levels from “ask before everything” to “autopilot.”

Post-Execution Verification: Predicate-Secure uses mathematical state diffing to verify that agent actions did not violate policies after execution. This catches cases where a policy bypass or race condition allowed an unauthorized action. The approach is 100% offline and works with browser-use, LangChain, PydanticAI, OpenClaw, and raw Playwright.

Network Segmentation: Agents should operate on isolated networks with strict egress controls. No agent should have unfettered internet access. DNS filtering, IP allowlisting, and proxy enforcement should be standard.

Vett.sh scans every agent skill for malicious code using 40+ static analysis rules at the AST level. Skills are signed with Sigstore before publishing, and each agent runs on an isolated VM with vaulted credentials. Vett has indexed 8,000+ skills and supports 46 agents.

Predicate-Secure is a 3-line drop-in Python wrapper that adds deterministic pre-execution authorization and post-execution verification. It uses YAML policy files (allow/deny) for OS and browser actions, with mathematical state diffing instead of LLM-as-a-judge. A Rust sidecar (predicate-authorityd) provides sub-millisecond policy evaluations in production.

Gulama is a security-first open-source AI agent with 15+ security mechanisms including AES-256-GCM encryption, sandboxed execution, and prompt injection detection. It offers 5 autonomy levels and supports MCP Server and Client protocols with multi-agent orchestration using isolated sub-agents.

Execwall is a dedicated firewall that blocks command injection attacks targeting AI agent frameworks, specifically designed to stop exploits like CVE-2026-2256 (ModelScope AI agent command injection).

Compliance and Standards — OWASP Agentic Top 10, NIST AI RMF#

The blastradius AI agent execution audit landscape is increasingly shaped by regulatory frameworks and industry standards:

OWASP Agentic Top 10 (2026): The OWASP Agentic Top 10 identifies the most critical security risks for agentic AI systems. Vectimus maps all 11 of its policy packs to all 10 OWASP categories, providing a compliance-ready security posture. The top risks include prompt injection, insecure output handling, excessive agency, and supply chain vulnerabilities.

NIST AI RMF: The NIST AI Risk Management Framework provides a structured approach to identifying, assessing, and managing AI risks. For agentic systems, the RMF’s focus on mapping, measuring, and managing risks is particularly relevant. Organizations deploying AI agents should conduct NIST AI RMF assessments as part of their security program.

SOC 2 for Agentic Systems: SOC 2 compliance for agentic AI systems requires demonstrating that security controls cover agent actions, data access, and system changes. Policy engines that log every agent action provide the audit trail needed for SOC 2 evidence.

EU AI Act: The EU AI Act classifies AI systems by risk level. Agentic systems that can execute code or control infrastructure likely fall into high-risk or limited-risk categories, requiring conformity assessments, human oversight, and transparency obligations.

NIST CSF 2.0: The NIST Cybersecurity Framework 2.0’s govern, identify, protect, detect, respond, and recover functions map naturally to agent security. Policy enforcement covers protect, monitoring covers detect, and incident response plans must account for compromised agents.

Conclusion — Building a Security Model for Autonomous Agents#

A blastradius AI agent execution audit reveals that the attack surface is vast but not unmanageable. The key insight is that local execution is not a security boundary — an agent running on your laptop has the same capabilities as an agent running in the cloud. The difference must come from policy enforcement, sandboxing, and verification.

The tools exist today: Vectimus for policy enforcement, Vett for skill scanning, Predicate-Secure for pre- and post-execution verification, Gulama for security-first agent design, and Execwall for agent-specific firewalls. What has been missing is the organizational commitment to using them.

Every organization deploying AI agents should conduct a blastradius AI agent execution audit covering all ten surfaces: shell, filesystem, package managers, infrastructure tools, browser automation, MCP servers, sub-agents, credentials, network egress, and supply chain. For each surface, implement deterministic policies, runtime isolation, and post-execution verification. Map your controls to OWASP Agentic Top 10, NIST AI RMF, and SOC 2 requirements.

The era of trusting AI agents by default is over. The era of verifying every action through policy is here.

FAQ#

Q: What is a blastradius AI agent execution audit? A: A blastradius AI agent execution audit is a systematic security assessment that identifies every surface where an AI agent can execute code or perform actions without explicit human approval. It covers shell commands, file system operations, package managers, infrastructure tools, browser automation, MCP servers, sub-agent spawning, credential access, network egress, and supply chain interactions.

Q: How did the Clinejection attack work? A: The Clinejection attack (February 2026) used a prompt injection hidden in a GitHub issue title. When an AI agent read the issue, the injected prompt caused the agent to read local credentials, modify source code, and publish backdoored npm packages. Within 8 hours, 4,000 developer machines were compromised. The attack succeeded because the agent had no policy preventing it from reading SSH keys or publishing packages.

Q: What is the difference between deterministic policy enforcement and LLM-as-a-judge? A: Deterministic policy enforcement uses predefined rules (like Cedar policies or YAML allow/deny lists) evaluated in under 10ms to authorize or block agent actions before execution. LLM-as-a-judge uses another AI model to evaluate whether an action is safe, which introduces latency, cost, and the possibility of the judge model itself being compromised or hallucinating incorrect decisions. Deterministic approaches are faster, cheaper, and more reliable for security-critical decisions.

Q: Can AI agents be safely used with infrastructure tools like Terraform and kubectl? A: Yes, but only with strict policy enforcement. Agents should never have unrestricted access to infrastructure tools. Policies should block destructive operations (terraform destroy, kubectl delete), require human approval for any infrastructure changes, use read-only credentials by default, and log every infrastructure action for audit. The Terraform destroy incident of February 2026 demonstrated what happens without these controls.

Q: What compliance frameworks apply to AI agent security? A: The key frameworks are OWASP Agentic Top 10 (specific to agentic AI risks), NIST AI RMF (AI risk management), SOC 2 (security controls and audit trails), NIST CSF 2.0 (cybersecurity framework), ISO 27001 (information security management), and the EU AI Act (regulatory compliance for high-risk AI systems). Policy engines like Vectimus map their controls to all of these frameworks.
