Introduction — Why Authorization Matters More Than Authentication for AI Agents#

Authentication tells you who someone is. Authorization tells you what they are allowed to do. For AI agents that book travel, send emails, deploy code, and spend money on behalf of real humans, authentication alone is dangerously insufficient. The industry is waking up to a hard truth: authorize, don’t authenticate is the new security mantra for AI agent architectures. Without a proper authorization layer, a single compromised agent credential can expose every user’s data in your database. This guide explains how to implement agentic access control using dual-subject authorization, policy-as-code with OPA/Rego, just-in-time credentials, and zero-trust principles to keep user data safe.

The Core Problem: Authentication Is Not Enough#

Authentication answers the question “Who are you?” — it verifies identity through passwords, API keys, OAuth tokens, or certificates. Authorization answers “What are you allowed to do?” — it enforces permissions based on policy. For decades, the security industry has understood that these are separate concerns, yet most AI agent deployments today treat them as the same thing.

Why AI Agents Break the Authentication-Only Model#

Traditional applications authenticate a human user, then authorize that user’s session. The human is the sole subject of every action. AI agents break this model in three fundamental ways:

  1. Agents act autonomously. An agent may execute dozens or hundreds of actions without human intervention. Each action needs independent authorization, not just a one-time authentication handshake.

  2. Agents act on behalf of multiple users. A single agent instance might serve different users with different permission levels. Shared credentials cannot distinguish between them.

  3. Agents compose tools and data. An agent that reads a customer record, then writes to a billing system, then sends an email is performing three actions across three domains — each requiring different authorization decisions.

As OWASP states in its Top 10 Web Application Security Risks, broken authorization is the number one risk in web applications. For AI agents, this risk is magnified because agents execute actions at machine speed with no human judgment in the loop.

The Authorization Gap in Current AI Agent Architectures#

Most current agent deployments rely on a single shared API key or OAuth token that authenticates the agent as a monolithic service. This approach creates a critical authorization gap.

The Shared Credential Problem#

When an agent uses a single credential, there is no way to:

  • Identify which specific agent instance performed an action
  • Encode the scope of delegated authority
  • Revoke access for one agent without breaking all agents
  • Audit actions back to a specific human user or task

The Grantex project, an open-source delegated authorization protocol for AI agents, describes this as “What OAuth 2.0 is to humans, Grantex is to agents.” It gives each agent a verifiable decentralized identifier (DID) and scoped, time-limited, revocable authority. The protocol has been submitted as an IETF draft (draft-mishra-oauth-agent-grants) and provides SDKs in TypeScript, Python, and Go with MCP integration.

The MCP Authorization Gap#

The Model Context Protocol (MCP) focuses on tool interaction and discovery but leaves per-request authorization largely undefined. This means that an agent connected to an MCP server can potentially call any tool the server exposes, with no granularity on which agent can call which tool under which conditions. The Pomerium Agentic Access Gateway addresses this by acting as an identity-aware proxy in front of MCP tools and APIs, enforcing centralized policy at each step.

The Dual-Subject Model: Authorizing Both Agent and Human#

One of the most promising developments in AI agent authorization is the dual-subject model. The AGBAC (AGent Based Access Control) specification, released under Apache 2.0, introduces a fundamental shift: every action requires authorization for both the AI agent AND the human it acts for.

How Dual-Subject Authorization Works#

In the dual-subject model, a single action produces two subjects that must both be authorized:

Action: "Read customer record #4521"
  Subject 1: Agent "support-bot-v3" (agent_id: abc-123)
    → Is this agent authorized to read customer records? YES
  Subject 2: Human "alice@company.com" (user_id: user-789)
    → Is this human authorized to read customer record #4521? YES
  Decision: ALLOW

This model aligns with zero-trust principles — never trust, always verify — applied at the agent level. It also works with existing IAM solutions, making it practical for organizations that already have mature identity and access management infrastructure.

Evolution of Access Control Models#

The progression from traditional models to agent-native authorization is clear:

  • RBAC (Role-Based Access Control): Users have roles, roles have permissions. No agent awareness.
  • PBAC (Policy-Based Access Control): Policies define access rules. Still human-centric.
  • ABAC (Attribute-Based Access Control): Attributes of user, resource, and environment drive decisions. Partial agent support.
  • AGBAC (AGent Based Access Control): Dual-subject authorization where both agent and human attributes are evaluated for every decision.

Policy-as-Code: Using OPA/Rego for Deterministic Agent Authorization#

Policy-as-code with Open Policy Agent (OPA) and its policy language Rego provides a deterministic, auditable, and replayable authorization engine for AI agents. Instead of scattering authorization logic across application code, you centralize it in policy files that can be version-controlled, tested, and reviewed.

Why OPA for AI Agents?#

OPA decouples policy decision-making from policy enforcement. This separation is critical for AI agent architectures because:

  • Deterministic decisions: Given the same inputs, OPA always produces the same output. No LLM hallucination in authorization.
  • Auditable: Every decision can be logged with full context for compliance audits.
  • Replayable: You can replay past decisions against updated policies to understand the impact of policy changes.
  • Language-agnostic: OPA makes authorization decisions via REST API, so any agent framework can use it.

Example OPA Policy for AI Agent Authorization#

package agent.authz

# Allow if agent is authorized for the action AND the human is authorized
default allow = false

allow {
  agent_authorized
  human_authorized
}

agent_authorized {
  input.agent.scope == "read:customers"
  input.agent.trust_level >= 3
}

human_authorized {
  input.human.role == "support_manager"
  input.resource.owner == input.human.team
}

This policy enforces the dual-subject model: both the agent and the human must be authorized for the action to proceed.

Just-in-Time Credentials vs Static API Keys#

Static API keys are the default credential model for most AI agent deployments today, and they are a security liability. Just-in-time (JIT) credentials offer a fundamentally better approach.

The Case Against Static API Keys#

Static API keys stored in environment variables or configuration files have several problems:

  • Long-lived by default: A key compromised today is valid until someone remembers to rotate it.
  • No scope: The key either works or it doesn’t. There is no way to say “this key can only read customer names, not credit card numbers.”
  • No identity: All agents using the same key are indistinguishable in audit logs.
  • No revocation granularity: Revoking the key breaks every agent that uses it.

Just-in-Time Credentials for AI Agents#

JIT credentials flip this model. An agent requests credentials only when it needs to perform an action, and those credentials are:

  • Short-lived: Valid for minutes or hours, not months or years.
  • Scoped: Limited to the specific resources and actions needed for the current task.
  • Revocable: Each credential can be revoked independently without affecting other agents.
  • Auditable: Every credential request and usage is logged with full context.

The Pomerium Agentic Access Gateway implements this pattern by providing just-in-time credentials instead of static API keys, leveraging existing OAuth 2.1 and OIDC infrastructure so agent actions tie back to real users.

Zero-Trust Principles for AI Agent Access#

Zero trust is not just for human users. The same principles apply to AI agents, and arguably with greater urgency because agents operate at machine speed and scale.

Never Trust, Always Verify — For Every Agent Action#

In a zero-trust model for AI agents, every action is evaluated against policy before execution. There is no “authenticated once, trusted forever” session. Each tool call, each database query, each API request is independently authorized.

Key Zero-Trust Principles for AI Agents#

  1. Verify explicitly: Every agent action must be authenticated and authorized based on all available data points — agent identity, human identity, resource sensitivity, action type, and environmental context.

  2. Use least privilege: Agents should receive the minimum permissions needed to complete their current task, and no more. The principle of least privilege dictates that consumers should only be authorized to access what they need to do their jobs, and nothing more.

  3. Assume breach: Design your authorization system assuming that any agent credential could be compromised. Short-lived credentials, continuous verification, and comprehensive audit logging are essential.

  4. Enforce at the data layer: Authorization should be enforced as close to the data as possible. ORM-layer authorization, as implemented by ZenStack, ensures that every database query is checked regardless of who wrote it or who is calling it.

ORM-Layer Authorization: Enforcing Access Control at the Data Level#

Authorization scattered across application code is fragile. A new API endpoint, a refactored service, or a coding agent that forgets to add a permission check can create a data exposure vulnerability. ORM-layer authorization solves this by enforcing access control at the data access layer.

How ORM-Layer Authorization Works#

ZenStack, built on top of Kysely, enforces access control policies directly in the ORM. Every query — regardless of who wrote it or which code path triggered it — is checked against the policy before returning results. This approach is database-agnostic, unlike PostgreSQL Row-Level Security (RLS), and supports RBAC, ABAC, and relation-based policies.

When an AI coding agent generates a database query, the ORM layer automatically applies the policy — the agent cannot forget to add a permission check because the check is not optional.

MCP Authorization: Filling the Gap in the Model Context Protocol#

The Model Context Protocol (MCP) has become the standard for connecting AI agents to tools and data sources. However, the MCP specification focuses on tool discovery and interaction, not authorization. This creates a security gap that must be filled by additional infrastructure.

The MCP Authorization Problem#

When an agent connects to an MCP server, the server exposes a set of tools. Without per-request authorization, any agent that can reach the server can call any tool. There is no way to express:

  • “Agent A can read customer records but not delete them”
  • “Agent B can only access records belonging to its assigned human user”
  • “Agent C can call the email tool but only during business hours”

Solutions for MCP Authorization#

Several approaches are emerging to fill this gap:

  1. MCP Gateway with policy enforcement: The Permit MCP Gateway provides fine-grained authorization and Identity Governance and Administration (IGA) integration at the MCP tool surface. Every tool call passes through the gateway, which evaluates policy before forwarding to the backend.

  2. Identity-aware proxy: The Pomerium Agentic Access Gateway acts as a reverse proxy in front of MCP servers, adding context-aware policy checks at each step. It leverages existing OAuth 2.1 and OIDC identity infrastructure.

  3. Grantex MCP integration: The Grantex protocol provides SDKs that integrate with MCP, adding per-agent identity and scoped authority to MCP tool calls.

Compliance and Regulatory Landscape (EU AI Act, DPDP, NIST AI RMF)#

Regulatory pressure is accelerating the adoption of AI agent authorization frameworks. Three major regulatory frameworks are driving compliance requirements:

EU AI Act#

The EU AI Act classifies AI systems by risk level and imposes requirements for transparency, human oversight, and accountability. For AI agents that access user data, the Act requires:

  • Clear documentation of data access patterns
  • Human oversight mechanisms for high-risk actions
  • Audit trails for all AI system decisions

The Grantex protocol provides control mappings that align with EU AI Act requirements, making it easier for organizations to demonstrate compliance.

DPDP Act 2023 (India)#

India’s Digital Personal Data Protection Act 2023 imposes strict requirements for data processing by automated systems. Key requirements include:

  • Consent management for data processing
  • Data subject rights (access, correction, erasure)
  • Data breach notification
  • Purpose limitation — data can only be used for the purpose for which consent was given

AI agent authorization frameworks must enforce purpose limitation at the policy level, ensuring that agents cannot access data for purposes beyond the original consent.

NIST AI Risk Management Framework#

The NIST AI RMF provides a framework for managing AI risks, including authorization controls. Key functions include:

  • GOVERN: Establish policies for AI risk management
  • MAP: Understand the context of AI system use
  • MEASURE: Assess and monitor AI risks
  • MANAGE: Treat and respond to AI risks

The Compliant-LLM project demonstrates how to audit AI agents for compliance with NIST AI RMF, including authorization controls.

Implementation Patterns and Best Practices#

Based on the emerging ecosystem of AI agent authorization tools and frameworks, here are actionable implementation patterns:

Pattern 1: Deploy an Authorization Gateway#

Place an authorization gateway between your agents and your data. The gateway evaluates every request against policy before forwarding to the backend. This is the simplest pattern to implement because it requires no changes to existing agent code.

Best for: Organizations with existing agent deployments that need to add authorization retroactively.

Pattern 2: Implement Dual-Subject Authorization#

For every agent action, evaluate authorization for both the agent identity and the human identity. Use OPA/Rego to encode policies that check both subjects.

Best for: Organizations with mature IAM infrastructure and clear human-to-agent mapping.

Pattern 3: Adopt Just-in-Time Credentials#

Replace static API keys with short-lived, scoped credentials that agents request per-task. Use a credential broker that integrates with your existing identity provider.

Best for: Organizations building new agent architectures from scratch.

Pattern 4: Enforce Authorization at the ORM Layer#

Use ORM-layer authorization (ZenStack or similar) to ensure that every database query is checked against policy, regardless of which code path triggered it.

Best for: Organizations where AI coding agents generate database queries and need guardrails against missing authorization checks.

Pattern 5: Adopt a Delegated Authorization Protocol#

Use a protocol like Grantex that provides per-agent identity, scoped authority, and revocation granularity. This is the most comprehensive approach but requires more integration effort.

Best for: Organizations building multi-agent systems with complex delegation chains.

Conclusion — Building a Secure Authorization Layer for AI Agents#

The shift from “authenticate” to “authorize” is not just a semantic change — it is a fundamental architectural decision that determines whether your AI agent deployment is secure or exposed. Authentication tells you who the agent claims to be. Authorization tells you what the agent is actually allowed to do.

The emerging ecosystem of AI agent authorization tools — Grantex for delegated authorization, AGBAC for dual-subject control, OPA/Rego for policy-as-code, Pomerium for identity-aware gateways, ZenStack for ORM-layer enforcement, and Permit for MCP gateway authorization — provides a comprehensive toolkit for building secure agent architectures.

The key takeaway: authorize every agent action, not just the initial authentication. Implement dual-subject authorization that checks both the agent and the human. Use just-in-time credentials instead of static API keys. Enforce policy at the data layer. And build for zero trust, because in an AI agent world, the boundary between internal and external access has disappeared.

Your user data belongs in your database — not exposed through an agent that was authenticated but never authorized.

FAQ#

What is the difference between authentication and authorization for AI agents?#

Authentication verifies the identity of an AI agent — confirming who or what the agent is. Authorization determines what actions that agent is permitted to perform, what data it can access, and under what conditions. For AI agents, authorization is the critical control plane because agents execute autonomous actions that authentication alone cannot govern.

Why are static API keys dangerous for AI agents?#

Static API keys are long-lived, have no scope or identity, and cannot be revoked granularly. If a static key is compromised, every agent using that key is affected, and there is no way to distinguish between legitimate and malicious usage in audit logs. Just-in-time credentials solve this by providing short-lived, scoped tokens per task.

What is dual-subject authorization for AI agents?#

Dual-subject authorization, introduced by the AGBAC specification, requires that every action be authorized for both the AI agent AND the human it acts for. This means a single action produces two authorization decisions — one for the agent’s capabilities and one for the human’s permissions — and both must pass for the action to proceed.

How does OPA/Rego help with AI agent authorization?#

OPA (Open Policy Agent) with its Rego policy language provides a deterministic, auditable, and replayable authorization engine. Policies are written as code, version-controlled, and tested independently of application logic. OPA makes authorization decisions via REST API, so any agent framework can use it without coupling to a specific programming language.

What is the MCP authorization gap and how do I fix it?#

The Model Context Protocol (MCP) focuses on tool discovery and interaction but does not define per-request authorization. This means any agent connected to an MCP server can potentially call any tool. You can fix this by deploying an authorization gateway (like Permit MCP Gateway or Pomerium Agentic Access Gateway) in front of MCP servers, or by using a delegated authorization protocol like Grantex that integrates with MCP.
