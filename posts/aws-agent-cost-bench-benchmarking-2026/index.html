What Is agent-cost-bench?#

AWS Agent Cost Bench (agent-cost-bench) is an open-source benchmarking framework released by AWS Samples on June 26, 2026, that provides a standardized methodology for measuring the cost, quality, and duration of AI coding agents. It solves a critical problem that engineering teams have faced since the explosion of coding agents in 2024–2026: there was no standardized, objective way to compare different coding agents, models, and CLIs using the same tasks and verification criteria. Teams had to rely on vendor benchmarks, anecdotal evidence, or expensive in-house evaluations. agent-cost-bench changes that by offering a repeatable, extensible, and transparent benchmarking platform that any team can run on their own infrastructure.

Two Benchmark Modes: model-compare vs cli-compare#

agent-cost-bench supports two distinct benchmarking modes, each designed to answer a different question.

model-compare keeps the CLI constant and varies the underlying model. This answers the question: “Which model gives me the best results in my preferred CLI?” For example, you can run the same tasks through Kiro CLI using Anthropic’s Sonnet 5, Opus 4.8, and Haiku 4.5 to see which model delivers the best balance of cost, speed, and accuracy.

cli-compare keeps the model constant and varies the CLI. This answers: “Which CLI tool gives me the best results with my preferred model?” You can run the same model — say Sonnet 5 — through Kiro CLI, Claude Code, GitHub Copilot, OpenAI Codex, and Cursor to compare how each CLI’s system prompts, tool-use patterns, and execution strategies affect outcomes.

ModeConstant VariableQuestion Answered
model-compareCLI (same tool)Which model performs best in my CLI?
cli-compareModel (same LLM)Which CLI performs best with my model?

How It Works#

agent-cost-bench operates on a clean, isolated architecture designed to produce reproducible results. Each task runs in its own workspace directory, preventing cross-task contamination. The framework creates a temporary directory, copies the task’s source files into it, and hands control to the agent CLI being tested.

The key architectural decisions that make agent-cost-bench reliable are:

Hidden Test Verification. This is the most important design choice. Each task includes tests that are hidden from the agent during execution. The agent works on the task description and source code, but the verification criteria are stored separately and only applied after the agent signals completion. This prevents models from gaming the benchmark by self-reporting favorable results or optimizing for known test cases. Verification can use pytest for Python tasks, Docker container builds for infrastructure tasks, custom scorer scripts for domain-specific validation, or LLM judge rubrics for subjective quality assessment.

Cost Auto-Detection. The framework automatically detects and records cost information from each CLI’s output. Costs are reported in both USD and the CLI’s native billing units — credits for Kiro, AI Credits for Claude Code, tokens for OpenAI-based tools. This dual reporting is essential because different CLIs use different billing models, and raw unit costs change over time.

Checkpoint Progress Monitoring. agent-cost-bench writes checkpoint files after each task completes, allowing real-time progress monitoring during long benchmark runs. If a run is interrupted, you can see which tasks completed and which need to be retried.

Supported CLIs and Models#

agent-cost-bench currently supports five major coding agent CLIs:

  • Kiro CLI — AWS’s own coding agent CLI, deeply integrated with AWS services
  • Claude Code — Anthropic’s terminal-based coding agent
  • GitHub Copilot — GitHub’s AI pair programmer with CLI capabilities
  • OpenAI Codex CLI — OpenAI’s coding agent (in beta)
  • Cursor — AI-first IDE with agent mode

Any model that these CLIs expose can be tested. In practice, the most commonly benchmarked models are Anthropic’s Claude family (Sonnet 5, Opus 4.8, Haiku 4.5) and OpenAI’s GPT-4o series. The framework does not restrict which models you can test — if your CLI supports it, agent-cost-bench can benchmark it.

Built-in Tasks#

The framework ships with 15 built-in tasks spanning multiple programming languages and domains:

CategoryLanguages/ToolsTask Types
Application DevelopmentPython, TypeScript, Java, C#Greenfield feature implementation, bug fixing, refactoring
InfrastructureDocker, Terraform, HelmConfiguration generation, deployment script creation
DevOpsShell scripting, CI/CD configsPipeline setup, monitoring configuration

The tasks cover both greenfield (building something from scratch) and brownfield (modifying existing code) scenarios. This diversity is important because agents perform differently on different types of work — a model that excels at Python feature implementation may struggle with Terraform configuration generation.

For teams that want to benchmark against their own codebase, agent-cost-bench supports a bring-your-own-repo (BYOR) feature. You can point the framework at any Git repository, define custom tasks and verification criteria, and run the same benchmarking pipeline against your actual code. This makes the framework uniquely practical for enterprise evaluation compared to synthetic benchmarks that may not reflect real-world workloads.

Real Results: model-compare (AWS Japan)#

AWS Japan Senior Solutions Architect Riku Inada published the first detailed model-compare results using Kiro CLI. The benchmark ran 6 tasks × 3 repeats = 54 total runs across three Claude models: Sonnet 5, Opus 4.8, and Haiku 4.5.

The most surprising finding: Opus 4.8 costs approximately 1.7× Sonnet 5 on average, but this cost difference is driven by token consumption rate, not reasoning depth. Opus generates more verbose outputs and requests more tool calls, consuming more tokens per task. Both models achieved 100% pass rates, meaning the extra cost of Opus did not translate into better results for these tasks.

Haiku 4.5 showed the lowest variance in credit consumption (standard deviation of 0.02–0.12 credits), making it the most predictable model for budgeting purposes. However, its 78% pass rate means one in five tasks failed — a significant reliability gap for production use.

Sonnet 5 emerged as the sweet spot: 100% pass rate at roughly half the cost of Opus 4.8, with latency only 3.3 seconds slower than Haiku.

Real Results: cli-compare (NTT DATA)#

NTT DATA published a complementary analysis using cli-compare mode, comparing Kiro CLI against Claude Code with both Sonnet 5 and Haiku 4.5. They ran 4 tasks × 3 repeats = 24 runs per model, totaling 48 runs.

All 48 runs passed — on these relatively simple tasks, there was no quality difference between CLIs. The cost differences, however, were dramatic. Kiro CLI with Sonnet 5 was 5.5× cheaper than Claude Code with the same model ($0.0234 vs $0.1289 per run). With Haiku 4.5, Kiro CLI was 6.2× cheaper ($0.0068 vs $0.0420).

Claude Code showed slightly lower latency with Sonnet 5 (22.2s vs 25.1s), but Kiro CLI was faster with Haiku 4.5 (17.2s vs 19.1s). The latency differences were relatively small compared to the cost gap.

Important caveat: The cost comparison uses different billing bases — Kiro CLI reports costs in credits (converted to USD at $0.04/credit), while Claude Code reports total_cost_usd directly. These billing models may have different underlying assumptions about token pricing, system prompt overhead, and caching behavior.

The Bigger Picture: 1,127 Agent Runs Analyzed#

Beyond the agent-cost-bench results, AgentMeter published an analysis of 1,127 real-world agent runs across Claude, GPT-4o, and Gemini models that provides essential context for understanding coding agent costs.

Total spend across all runs: $4,281.39. The mean cost per run was $3.80, but this average is dangerously misleading. The median was just $1.22, while the 95th percentile reached $22.14 and the 99th percentile hit $61.87. The p95/p50 ratio of 18× means that the most expensive 5% of runs cost 18 times more than a typical run. For budgeting purposes, average cost estimates will significantly underestimate your actual spend.

Where does the money go? The analysis revealed that 52% of total agent spend goes to context re-reads — the LLM re-processing the conversation history on each turn. This is the quadratic cost curve in action: as conversations grow longer, each subsequent turn costs more because the model must re-read everything that came before. Tool call execution accounts for only 7.4% of spend on average, but this can spike to 30% or more in retry cascades when agents get stuck in error-recovery loops.

Three runaway runs — just 0.27% of all runs — accounted for 8.3% of total spend ($354.20). These are the agent equivalent of runaway cloud instances: a single stuck agent consuming disproportionate resources. This is why budget caps and timeout limits are essential safety measures.

Model cost comparison: Gemini Flash was 12× cheaper than Sonnet at the median cost per run, but its success rate dropped from 94% (Sonnet) to 87%. The 7 percentage point reliability gap may be acceptable for low-stakes tasks but problematic for critical production work.

The highest-ROI optimization identified by AgentMeter is mixed-model routing: using a cheap model (Gemini Flash) for classification and simple analysis steps, and routing only complex reasoning tasks to an expensive model (Sonnet). This approach achieved a 60% cost reduction while maintaining a 93% success rate — nearly matching Sonnet’s 94% at a fraction of the cost.

Key Metrics Explained#

Understanding the metrics that agent-cost-bench reports is essential for interpreting results correctly.

Pass Rate is the percentage of tasks where the agent produced a correct solution as verified by the hidden tests. This is the most straightforward quality metric, but it doesn’t tell the whole story — a model with 100% pass rate at 10× the cost may be a worse choice than a model with 90% pass rate at 1/10 the cost.

Cost per Run is the average cost of executing a single task, including all agent turns, tool calls, and context processing. This is useful for operational budgeting but can be misleading because it doesn’t account for failures.

Cost per Success is the most actionable metric. It divides the total cost of all runs by the number of successful runs. If a model costs $0.05 per run but only succeeds 50% of the time, the cost per success is $0.10 — you’re paying for the failures. This metric directly informs model selection decisions.

Latency measures the wall-clock time from task start to completion. This matters for developer productivity — a model that takes twice as long may not be acceptable even if it’s cheaper.

How to Run Your Own Benchmark#

Running agent-cost-bench requires a clean environment to avoid system prompt contamination from previous runs. AWS Japan’s setup guide recommends using a fresh EC2 instance or Docker container.

Prerequisites:

  • Python 3.11 or later
  • Docker (for container-based verification tasks)
  • The CLI tools you want to benchmark (Kiro CLI, Claude Code, etc.)
  • API keys for the models you want to test

Basic setup:

git clone https://github.com/aws-samples/sample-agent-cost-bench.git
cd sample-agent-cost-bench
pip install -r requirements.txt

Running model-compare:

kiro agent-cost-bench model-compare \
  --tasks python-hello,dockerfile,terraform-s3 \
  --models sonnet-5,haiku-4.5 \
  --repeats 3

Running cli-compare:

kiro agent-cost-bench cli-compare \
  --tasks python-hello,dockerfile \
  --model sonnet-5 \
  --clis kiro,claude-code \
  --repeats 3

Best practices for reliable results:

  • Start small: 2 tasks × 1 repeat to validate your setup before scaling up
  • Use a clean environment for each run to avoid system prompt contamination
  • Check /tmp disk capacity — agent workspaces can consume significant space
  • Set budget caps on your API keys to prevent runaway costs
  • Use checkpoint files to monitor progress in real time during long runs

Limitations and Caveats#

agent-cost-bench is a powerful tool, but its results must be interpreted with several important caveats.

Task selection bias. The 15 built-in tasks may not represent your specific workload. A model that excels at Python feature implementation may struggle with Terraform configuration or Java refactoring. Always supplement built-in tasks with your own repositories using the BYOR feature.

Model pricing changes. The cost data in this article reflects pricing as of July 2026. Model providers change pricing frequently, and the relative cost rankings between models can shift dramatically with new releases or pricing updates.

CLI-specific system prompts. Each CLI adds its own system prompts, tool definitions, and execution strategies on top of the underlying model. Differences in benchmark results may reflect CLI design choices rather than model capabilities. This is by design — cli-compare measures the full tool experience, not just the raw model.

Billing model differences. Different CLIs use different billing units (credits, AI Credits, tokens) with different conversion rates to USD. Cross-CLI cost comparisons should be treated as directional rather than precise.

Hidden test design matters. The quality of hidden tests directly affects the validity of pass rate measurements. Poorly designed tests may pass incorrect solutions or fail correct ones. Review the test criteria for any tasks you add.

Who Should Use agent-cost-bench#

Engineering teams evaluating coding agents will find agent-cost-bench invaluable for making data-driven tooling decisions. Instead of relying on vendor claims or anecdotal evidence, you can run standardized benchmarks against your actual codebase and measure what matters for your team.

Platform teams optimizing costs can use agent-cost-bench to identify the most cost-effective model-CLI combinations for different task types. The Cost per Success metric directly informs routing decisions in multi-model agent platforms.

Enterprises standardizing on tooling can use agent-cost-bench as part of their evaluation framework. The bring-your-own-repo feature allows benchmarking against proprietary codebases, and the objective verification methodology provides defensible evidence for procurement decisions.

Researchers and analysts studying AI agent economics will find agent-cost-bench’s standardized methodology useful for producing comparable, reproducible results across different models and time periods.

Conclusion#

AWS Agent Cost Bench fills a critical gap in the coding agent ecosystem. Before its release, teams evaluating coding agents had no standardized way to compare cost, quality, and duration across different CLIs and models using the same tasks and objective verification. The hidden test approach prevents models from gaming benchmarks — a key differentiator from self-reported results that have dominated agent performance discussions.

The early results from AWS Japan and NTT DATA reveal actionable insights: Sonnet 5 hits the sweet spot of 100% pass rate at roughly half the cost of Opus 4.8; Kiro CLI delivers comparable quality to Claude Code at 5–6× lower cost on simple tasks; and the long-tail cost problem (18× p95/p50 ratio) means average cost estimates are dangerously misleading for budgeting.

The broader AgentMeter analysis of 1,127 runs adds another layer: 52% of agent spend goes to context re-reads, three runaway runs accounted for 8.3% of total spend, and mixed-model routing (Gemini Flash for classification + Sonnet for analysis) achieves 60% cost reduction with 93% success rate.

For any team using or evaluating AI coding agents in 2026, agent-cost-bench provides the objective measurement layer that the ecosystem has been missing. Run your own benchmarks, measure what matters, and let data — not vendor claims — drive your tooling decisions.
